# HTML Entity Encoder and Decoder — preparatory BRIEF v0.1

Specification documentation only; no product claim, readiness event or implementation. Full normative contract is SPEC.md.

## 1. Goal
Anyone who writes documentation, templates or test fixtures eventually needs to show markup as text ("write `&lt;div&gt;` in the docs") or rescue text that was double-encoded by a CMS — and general-purpose online converters each make quiet choices (named vs numeric references, how much to escape) that change the bytes. Success: the user pastes text, chooses encode or decode with explicit options, and gets a deterministic conversion under stated rules — encoding escapes exactly the characters that need it with named references where the tool's table provides them, decoding resolves named, decimal and hexadecimal references and reports the ones it cannot resolve instead of silently dropping them — with the result copyable and the character-level changes reviewable.

## 2. Scope and functional distinction
Encode: the mandatory five (`&` first, then `<`, `>`, `"`, `'`) plus an option to also encode all non-ASCII characters; output form option: named references where the tool's bundled table has one for the character, else decimal numeric, else hexadecimal numeric — the table is the WHATWG named-character-reference set shipped as data in the repo (the SPEC pins how completeness is checked against that list rather than hand-typing a subset). Decode: named references (requiring the semicolon — the SPEC addresses the HTML spec's legacy semicolon-less cases by excluding them with a stated reason), decimal `&#…;` and hex `&#x…;` numeric references with range validation (surrogates, values above U+10FFFF, and the C1 remapping table of the HTML standard handled exactly as the standard prescribes, since browsers do this and a decoder that disagrees with browsers misleads), unknown named references left byte-identical and listed as unresolved, and a double-encoding detector hint (if the decoded output still contains decodable references, the UI offers "decode again" rather than looping silently). A diff-style review lists each replacement (position, original, replacement) for both directions. Excluded: full HTML parsing/sanitising (this converts text, it does not make markup safe — the page must say that encoding output for display is not the same as sanitising untrusted HTML), URL encoding (a different tool family), and file upload.

Existing tools: Text Workbench transforms text cases/formats; the JWT tool decodes tokens; nothing converts HTML character references with a standards-pinned table and unresolved-reference reporting. Initial catalog/spec/task scope contains no entity converter; fresh registry/path/draft check remains mandatory before admission. Fixtures include the tricky standard cases: `&notin;` vs `&not` handling, `&#150;` (C1 remap to U+2013), `&#xD800;` (surrogate → U+FFFD), and a double-encoded `&amp;lt;` sample.
