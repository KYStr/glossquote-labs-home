# HTML Entity Encoder and Decoder — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Conversion rules follow the WHATWG HTML Standard's character-reference rules; where this tool deliberately narrows them (semicolon-required named references), the narrowing is stated and visible in the product.

## 1. Goal
Primary audience: developers, technical writers, support engineers and QA staff who move text between markup and plain contexts — documenting code samples, repairing CMS double-encoding, building fixtures. The recurring problem: converters disagree silently — one escapes everything to numbers, another drops references it does not know, a third disagrees with browsers on numeric edge cases — and the user cannot tell what happened to their text. Success is observable: the user encodes or decodes with explicit options and receives the converted text plus a per-replacement change list (what matched, what it became, and which references could not be resolved), so the conversion is auditable character by character. Non-goals: HTML parsing, sanitising or making untrusted markup safe (the page states that encoding text for display is not sanitisation), URL percent-encoding, and file processing.

Assumptions: a modern desktop browser; text is pasted, up to the stated size cap; no network at runtime.

## 2. Scope and functional distinction
Two modes. Encode: input text → escaped text under section 4's rules, with options (a) escape only the mandatory five, or also every non-ASCII character; (b) reference style: named-where-available (falling back to decimal), decimal-only, or hexadecimal-only. Decode: input text → decoded text under section 4, with a change list and an unresolved list; when the decoded output itself still contains a decodable reference, a "looks double-encoded" hint offers an explicit Decode-again action (never automatic). Both modes show input/output character counts and a copy button for the output. The named-reference table is the complete WHATWG named character reference set (the production vendors it as data — 2,231 semicolon forms at the time of writing — and the build verifies its entry count and a checksum recorded in the provenance notes; a hand-typed subset is a defect).
Excluded: semicolon-less legacy named references (e.g. `&amp` without `;` stays literal — browsers accept some of these in text content for historical reasons, but a converter that guesses creates corrupt documentation; the narrowing is stated on the page), attribute-context parsing rules, and any DOM parsing of the input (conversion is a pure text function; the input is never inserted into a document).
Distinction from existing work: Text Workbench performs case/format transforms, not reference conversion; the UTF-8 Base64 codec handles a different encoding entirely; the JWT inspector decodes token structure. None implements the HTML character-reference algorithm with its C1 remapping and replacement-character rules. No catalog entry, reserved specification or registry task at admission time converts HTML entities; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: mode = Decode (the more common rescue task) with empty panes, options visible, and the two honesty notes present: "Decoding shows you what the text says — it does not make markup safe to insert" and its encode counterpart. Conversion runs on input (debounce ≤200 ms) or on option change; input and output panes are side by side with the change list below.
The change list shows one row per replacement: input position (character index), the matched source text, and the result (character + code point, e.g. `– U+2013`). The unresolved list (decode) shows each token that looked like a reference but was not converted, with the reason (unknown name / invalid number / out of range handled per rule — noting that out-of-range numerics are converted to U+FFFD by rule and so appear in the change list, not here). When both lists are empty the area says "no references found" rather than showing a blank.
Size cap: 100,000 characters of input; beyond it the input is refused with the count shown (not truncated silently). Copy copies the output pane exactly. Nothing is stored; leaving or reloading discards the text. Encode followed by decode (same options family) is an identity for any input — this round-trip property is stated and tested.

## 4. Conversion rules (normative)
Encode: a single left-to-right pass over the input by Unicode code point. For each character: if it is one of `& < > " '` → emit its named reference (`&amp;` `&lt;` `&gt;` `&quot;` `&apos;`) regardless of style option. Else, if the "encode non-ASCII" option is on and the code point is > 0x7E (or a C0 control other than tab/LF/CR): emit per style — named: the table's name for that code point if exactly one canonical name exists in the table (the table maps some code points from multiple names; the canonical choice is the shortest name, ties broken lexicographically — deterministic and stated), else decimal `&#N;`; decimal style: `&#N;`; hex style: `&#xH;` with uppercase hex digits and no leading zeros. All other characters pass through unchanged. Because the pass is over the input only, the encoder never re-escapes its own output (an input `&amp;` encodes to `&amp;amp;` — correct, and the change list shows the `&` replacement).
Decode scanning: left-to-right; at each `&` attempt, in order: (1) numeric: `&#` followed by 1+ ASCII digits then `;`, or `&#x`/`&#X` followed by 1+ hex digits then `;` — convert per the numeric rules below; a numeric form missing the final `;` (digits run to end of input or a non-digit, non-`;` character) is still converted (browser-compatible) but the change-list row is flagged "missing semicolon". (2) named: match `&` + `[A-Za-z][A-Za-z0-9]*` + `;` and look the name up in the semicolon-form table; on a hit, emit the mapped character(s) (some references map to two code points — emitted in full). On a miss, the whole token goes to the unresolved list and is emitted unchanged. (3) if neither shape matches, emit `&` unchanged and continue (not an unresolved entry — a bare ampersand is ordinary text; but `&` followed by letters/# and terminated by `;` within 32 characters that failed both shapes IS an unresolved entry, e.g. `&notreal;` or `&#xZZ;`).
Numeric value rules (the HTML Standard's, restated): let v be the value. v = 0 → U+FFFD. v in 0xD800–0xDFFF (surrogates) → U+FFFD. v > 0x10FFFF → U+FFFD. v in 0x80–0x9F → remapped through the Standard's C1 table (shipped as data; e.g. 0x96 → U+2013, 0x80 → U+20AC; the entries the Standard maps to themselves stay). Any other v (including other controls and noncharacters) is emitted as that code point. Each application of the FFFD or C1 rules is noted in its change-list row by rule name ("surrogate → replacement character", "C1 remap"), so a lossy conversion is never silent.
Change-list positions are code-point indices into the input string (not UTF-16 units) — stated because astral characters would otherwise shift every later position.
Worked fixtures (normative): Encode (mandatory five, named style): `Tom & "Jerry" <3 'ok'` → `Tom &amp; &quot;Jerry&quot; &lt;3 &apos;ok&apos;`. Encode with non-ASCII on, named style: `café —` → `café` becomes `caf&eacute;` and `—` becomes `&mdash;`. Decode: `&notin;` → `∉` (U+2209); `&not;` → `¬`; `&notreal;` → unchanged + unresolved (unknown name); `&#150;` → `–` (U+2013, C1 remap noted); `&#xD800;` → U+FFFD (surrogate rule noted); `&#0;` → U+FFFD; `&amp;lt;` → `&lt;` with the double-encoded hint shown; `Fish & Chips` → unchanged, no unresolved entries.

## 5. Implementation and safety
Architecture (future production): a pure core (encoder, decoder scanner, tables as data modules, change-list builder) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. The named table ships as a generated data module produced from the WHATWG entities list at build time with its source URL and retrieval date in PROVENANCE.md — the build script records the entry count and SHA-256 of the source JSON, and `check` fails if the shipped table's count differs from the recorded one.
Privacy/security: input text renders as text only (both panes are textareas/plain text regions — decoded output that happens to be markup is inert); no network, no storage; nothing is logged. The not-a-sanitizer note is permanent UI in both languages.
Bilingual and accessibility: full zh-TW (default) and English UI; change and unresolved lists are real tables with headers; positions and code points are text; keyboard-only operation completes both modes; option changes re-run conversion without losing the input or focus.
Performance bounds: conversion is a single pass, O(n) with table lookups; 100,000 characters convert in <200 ms; the change list renders at most the first 500 rows with a total count shown if longer (the conversion itself is never capped by the display cap). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host after build.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages and modes; all option combinations; copy exactness; decode-again hint flow; round-trip identity on the fixture corpus.
- boundaries: cap at 100,000 and one over; empty input; input that is only `&`; numeric edges 0 / 0x7F / 0x80 / 0x9F / 0xA0 / 0xD7FF / 0xD800 / 0xDFFF / 0x10FFFF / 0x110000; missing-semicolon numeric flagged.
- privacy: zero network after load; no storage; text absent from URL/title; nothing copied without a click.
- security: markup-bearing input/output inert in both panes; no DOM parsing anywhere (source audit); no external resources.
- usability: a writer repairs a double-encoded paragraph and can point to the change-list rows that prove what happened; the not-a-sanitizer note is understood (spot-check).
- accessibility: labelled panes and option groups, real tables for change/unresolved lists, keyboard-complete, counts and hints in text.
- localization-seo: zh-TW and en pages complete and equivalent including notes and rule names; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the vendored table's count/checksum in PROVENANCE.md matches the shipped data (checked, not asserted).
- compatibility: current Chrome/Edge/Firefox/Safari desktop; decode results for the C1/surrogate fixtures match what a browser's own HTML parser produces for the same references (verified via a test page in evidence).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) every section 4 fixture exactly, including change-list contents (positions as code-point indices — one fixture places an astral character before a reference to pin this); (b) the numeric boundary sweep listed in section 6, each with its expected code point and rule note; (c) C1 table: all 32 entries asserted against the Standard's mapping as transcribed independently in the test data; (d) named table conformance: count check plus a sample of 50 names across the alphabet verified against the WHATWG list, including one two-code-point reference; (e) unresolved taxonomy: unknown name, malformed numeric, bare ampersand (no entry), `&notreal;`; (f) round-trip: encode→decode identity over a corpus mixing markup, entities, CJK and astral characters; (g) missing-semicolon numeric conversion + flag.
GUI/evidence tests (desktop, real browser): fixtures through the real UI in both languages; the browser-parser cross-check of section 6 (a test page whose parsed text is compared to the tool's decode); change-list display cap behaviour. Timing: full core suite under 60 seconds; no network in any test (the WHATWG source is fetched at build/authoring time only, never at test or runtime).
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
