# Sleep Cycle Calculator — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Backwards clock arithmetic across midnight is exactly where mental maths fails, and cycle calculators fail with it when they silently absorb falling-asleep time into the first cycle or show a bare "23:15" with no hint that it means tonight, not tomorrow morning. This specification pins the unwrap-and-label rule for day boundaries and keeps latency strictly outside the cycles, in both directions.

## 1. Goal
Primary audience: anyone setting an alarm for an early start, shift workers choosing between sleep options, students before an exam morning, and parents planning around a child's wake time. The recurring problem: doing "seven and a half hours before 7, minus falling-asleep time" backwards across midnight in your head, at bedtime, tired — and generic calculators that hide whether their suggestion includes the time it takes to fall asleep, or that present the 90-minute cycle as a fact about the user's body. Success is observable: in one direction the user enters a wake time and receives four bedtimes (for 6, 5, 4 and 3 cycles) with cycle counts, sleep durations and day labels; in the other the user enters a bedtime — or taps the "going to sleep now" button — and receives the four matching wake times. Everywhere, the page states that 90 minutes is a conventional planning average, that real cycles vary, and that the suggestions are not medical advice. Non-goals: tracking, diagnosing, or improving anyone's sleep; setting alarms; and any claim about sleep stages.

Assumptions: a modern desktop or mobile browser; the user plans by clock time on a single night (no dates, no time zones — all times are the device's local clock face); no network at runtime.

## 2. Scope and functional distinction
Included: (a) two directions, selected by a toggle — "I need to wake at…" (bedtime suggestions) and "I'm going to bed at…" (wake suggestions); (b) a 24-hour time input (HH:MM) in each direction; (c) fall-asleep latency in whole minutes, 0–60, default 15, shared by both directions; (d) exactly four suggestion rows per calculation, defined in section 4, each showing the suggested time, its day label, the cycle count, total sleep (cycles × 90 minutes) and total time in bed (latency + sleep); (e) the 5- and 6-cycle rows visually marked as the commonly recommended range, with the general note that most adults are commonly advised 7–9 hours and individual needs vary; (f) in the wake direction, a "going to sleep now" button that fills the bedtime with the device's current local time (HH:MM, seconds dropped) and recomputes. Excluded: dates, calendars and reminders; alarms or notifications; saving or history of any kind; nap planning and split-sleep schedules; cycle lengths other than 90 minutes (the constancy is the tool's stated simplification, not an oversight); seconds in any input or output.
Distinction from existing work: Date Calculator performs calendar-day arithmetic between dates; this tool plans clock times within one night by 90-minute cycles and never touches dates. Focus Timer runs a live countdown for work sessions; this tool answers a what-time question and runs no timer. The Metronome schedules audio clicks. No catalog entry, reserved specification or registry task at admission time plans bed or wake times by sleep cycles; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: wake direction selected, wake time 07:00, latency 15 — the four bedtimes (21:45 and 23:15 labelled previous evening; 00:45 and 02:15 labelled same morning) already computed, with the 6- and 5-cycle rows marked recommended. Switching direction preserves the latency; each direction remembers its own last time during the page session only. Editing the time or latency recomputes the four rows together.
The day labels are part of the result, never decoration: in the wake direction a suggested bedtime is labelled "previous evening" when it falls before midnight relative to the wake day and "same morning" when it falls after midnight on the wake day itself; in the bed direction a suggested wake time is labelled "next morning" when it falls after midnight relative to the bedtime's evening and "same evening/night" when it does not (the exact label strings are localised; the distinction is normative). Rows are ordered latest-cycle-count first in the wake direction (6, 5, 4, 3 — most sleep first) and earliest wake first in the bed direction (3, 4, 5, 6 cycles).
Error states: an empty or malformed time (the HH:MM expectation is restated); latency non-whole or outside 0–60. While an error stands the rows freeze at the last valid state marked "out of date". The "going to sleep now" button reads the clock once per tap; the page does not tick or auto-update. Nothing persists across reload; times never appear in the URL or title.

## 4. Computation rules (normative)
Model: all times are minutes since midnight, 0–1439, parsed from HH:MM (hours 0–23, minutes 0–59, both exactly two digits in the input's value). Latency L is a whole number 0–60. One cycle = 90 minutes exactly.
Wake direction (given wake time W): for each cycle count n in {6, 5, 4, 3} in that row order: raw = W − L − 90n; suggested bedtime = raw mod 1440, displayed HH:MM; day label = "previous evening" if raw < 0, otherwise "same morning". Sleep duration = 90n minutes, displayed as H:MM (e.g. 7:30); time in bed = L + 90n, displayed the same way.
Bed direction (given bedtime B): for each n in {3, 4, 5, 6} in that row order: raw = B + L + 90n; suggested wake time = raw mod 1440; day label = "next morning" if raw ≥ 1440, otherwise "same evening/night". Sleep and time-in-bed displays as above. (raw cannot reach 2880 within the input bounds: maximum B = 1439, L = 60, 90n = 540 gives 2039.)
The mod operation is the mathematical (non-negative) modulo: −135 mod 1440 = 1305. No other rounding exists in this tool; all values are whole minutes end to end.
Recommended marking: rows with n = 5 or n = 6 carry the "commonly recommended" mark in both directions; rows with n = 3 carry a plain-language caution ("short night — below the commonly advised range") — wording localised, presence normative.
Worked fixtures (normative, re-derived by script during drafting):
- S1: wake 07:00, L = 15 → 6 cycles: raw −135 → **21:45, previous evening**, sleep 9:00, in bed 9:15; 5 cycles: raw −45 → **23:15, previous evening**, sleep 7:30, in bed 7:45; 4 cycles: raw 45 → **00:45, same morning**, sleep 6:00, in bed 6:15; 3 cycles: raw 135 → **02:15, same morning**, sleep 4:30, in bed 4:45.
- S2: bedtime 23:00, L = 15 → 3 cycles: raw 1665 → **03:45, next morning**; 4 cycles: **05:15, next morning**; 5 cycles: **06:45, next morning**; 6 cycles: **08:15, next morning** (sleep 4:30 / 6:00 / 7:30 / 9:00; in bed 4:45 / 6:15 / 7:45 / 9:15).
- S3: wake 06:30, L = 0 → 6 cycles: **21:30, previous evening**; 5 cycles: **23:00, previous evening**; 4 cycles: **00:30, same morning**; 3 cycles: **02:00, same morning** — with latency zero, sleep and time-in-bed are identical, and both are still shown.

## 5. Implementation and safety
Architecture (future production): a pure core (minutes arithmetic, row builder returning time, label key, cycle count, sleep and in-bed durations) with zero DOM access; the day label is returned as an enum key, never as a pre-baked string, so both languages label identically; a controller; a thin DOM layer. The 90-minute cycle, latency bounds and row cycle-count orders appear once as auditable constants matching section 4. Runtime dependencies: none.
Privacy/security: no network, no storage, no analytics; the "sleep now" reading of the device clock stays on the page and is never transmitted; inputs render as text only; no eval/Function; no external resources.
Honesty rules (normative, testable): the explainer text states that a cycle is about 90 minutes on average and varies by person and by night, and that results are planning estimates, not medical advice; no text may claim the user will wake "refreshed", "in light sleep", or any stage-specific outcome — the only claim allowed is the arithmetic one: the suggested times are whole cycles plus the entered latency from the entered time.
Bilingual and accessibility: full zh-TW (default) and English UI, including day labels, recommended and short-night marks, and the honesty explainer. Suggestions are a real table or list with text labels (the recommended mark is text/icon plus text, never colour alone); the time inputs are native and labelled; keyboard-complete flow; the "sleep now" result is announced as text.
Performance bounds: four rows of integer arithmetic per edit. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages and both directions; latency honoured identically in both directions; "going to sleep now" fills from the device clock and recomputes; every section 4 fixture reproduced exactly (times, labels, both duration columns).
- boundaries: latency 0 and 60 accepted, 61 and −1 and 15.5 refused; wake 00:00 and 23:59 handled with correct wrap labels; a bedtime of 23:59 with latency 60 (raw well past midnight) labelled correctly; the S3 identity (latency 0 → sleep = time in bed, both shown) visible.
- privacy: zero network after load; no storage; the device-clock reading and entered times absent from URL/title and never transmitted.
- security: field content containing markup renders inert; no external resources; no eval/Function.
- usability: a tired first-time user gets a bedtime for a 07:00 alarm without instructions, and can say which row gives the most sleep and what the day label on 21:45 means (spot-check).
- accessibility: rows readable as text with labels and marks as text, not colour alone; native labelled time input; keyboard-complete; recomputed rows announced politely as text.
- localization-seo: zh-TW and en pages complete and equivalent (including day labels, marks and the honesty explainer); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the 90-minute cycle, bounds and row orders appear once as auditable constants matching section 4.
- compatibility: current Chrome/Edge/Firefox/Safari desktop and mobile-width layout; identical outputs for the fixture corpus across browsers (the "sleep now" reading naturally reflects each device's own clock).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) fixtures S1, S2 and S3 exactly — every row's time, label, sleep and in-bed values, and row order in both directions; (b) wrap arithmetic: negative raw values map by mathematical modulo (the −135 → 1305 case is asserted, not just displayed); raw exactly 0 and exactly 1440 boundary cases in the two directions with their labels; (c) latency extremes 0 and 60 in both directions, and the refusal classes (61, −1, non-integer); (d) time parsing: 00:00 and 23:59 accepted; 24:00, 7:00 (single-digit hour in the strict value), and empty refused with the format restated; (e) marks: n = 5 and 6 marked recommended, n = 3 carrying the short-night caution, n = 4 unmarked, in both directions.
GUI/evidence tests (desktop, real browser): fixtures entered through the real UI in both languages and both directions; the "going to sleep now" button tapped with the device clock read at that moment compared against the filled value (allowing the minute to tick between tap and read); direction switching preserving latency; stale-state behaviour on a malformed time. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
