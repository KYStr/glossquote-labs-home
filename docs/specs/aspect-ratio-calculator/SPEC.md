# Aspect Ratio Calculator — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. A ratio calculator has one job — arithmetic that can be trusted — so this specification pins exact integer/rational computation: simplification is by gcd, solving is by exact fractions, and rounding happens only at display, in stated places, never inside the arithmetic.

## 1. Goal
Primary audience: video editors and streamers sizing exports and overlays, photographers and designers cropping and setting canvases, front-end developers writing responsive embeds, and students meeting ratios in class. The recurring problem: mental long division, and "helpful" online tools that snap 1366×768 to "16:9" when its true simplified ratio is 683:384 — close enough to look right, wrong enough to distort a crop. Success is observable: the user enters dimensions or a ratio plus one dimension and receives the exact simplified ratio, the decimal form, and the solved dimension as both a usable rounded number and (when it is not an integer) the exact reduced fraction — with any nearby famous preset labelled as *near*, never substituted. Non-goals: resizing or cropping actual images, unit/DPI/print calculations, generating CSS or embed code, comparing two images, and saving sizes.

Assumptions: a modern desktop browser; numbers typed as text; no network at runtime.

## 2. Scope and functional distinction
Included: (a) Mode A — dimensions to ratio: integer width and height, each 1–100,000; outputs the simplified ratio a:b, the decimal width/height to 4 places, and height as a percentage of width to 2 places; (b) Mode B — ratio plus one dimension: ratio parts are numbers > 0 and ≤ 10,000 with at most 3 decimal places (e.g. `2.39`, `1`, `16`); the given dimension is an integer 1–100,000 or a decimal with at most 2 places; outputs the simplified ratio (after the section 4 scaling), and the solved other dimension rounded to 2 decimals plus its exact reduced fraction when non-integer; (c) a closed preset list filling Mode B: 1:1, 5:4, 4:3, 3:2, 16:10, 16:9, 1.85:1, 2.39:1, and the portrait mirrors 4:5, 3:4, 2:3, 9:16 — presets are input shortcuts only; (d) a nearest-preset note in Mode A: when the decimal ratio differs from a preset's decimal by ≤ 0.01 but is not exactly equal, the page may show "close to 16:9 (differs by 0.0011)" — the note NEVER replaces the computed ratio, and when the ratio is exactly a preset, it says "exactly 16:9". Excluded: non-terminating manual ratio inputs beyond 3 decimals (refused with the rule stated), zero or negative values, unit conversion, and persistence.
Distinction from existing work: Print Size converts pixels to physical print size using DPI and paper; this tool has no units and no printers — it simplifies and solves pure ratios. Box Fit / object-fit work concerns how content is placed and cropped inside a container (geometry and offsets); this tool computes no placement. The Image Resizer changes files; this tool touches no files. No catalog entry, reserved specification or registry task at admission time does ratio simplification/solving; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: Mode A with 1920×1080 prefilled, showing 16:9, decimal 1.7778, height 56.25% of width, and the note "exactly 16:9". Mode switching keeps the last values of each mode. Every edit recomputes immediately; there is no calculate button.
In Mode B, choosing "solve for height" vs "solve for width" is an explicit toggle; the given dimension's field is labelled accordingly, and the solved value is read-only output (never an editable field pretending to be input). A "use as dimensions" button copies a Mode B result pair into Mode A when both values are integers; when the solved value is fractional, the button is disabled with the reason stated (Mode A takes integers) — the fraction is shown so the user can decide their own rounding.
Errors are per-field and specific: empty, not a number, zero or negative, above the cap, too many decimal places (which field, which limit). While any field in the active mode is invalid, that mode's outputs freeze at the last valid values marked "out of date"; the other mode is unaffected. Nothing persists across reload; numbers never appear in the URL or title.

## 4. Computation rules (normative)
All arithmetic is exact: integers and rationals (numerator/denominator pairs) internally; no floating-point value ever feeds a simplification or a fraction. Rounding is display-only, half away from zero, at the stated places.
Simplification: for integers w, h: g = gcd(w, h) (Euclid's algorithm); the simplified ratio is (w/g) : (h/g). Decimal ratio parts in Mode B are first scaled: each part × 1000 must be an integer by construction (≤3 decimal places), giving integers W′, H′; the pair is then simplified by gcd as above — so `2.39:1` becomes 2390:1000 → **239:100**, and `21:9` becomes 21000:9000 → **7:3** (displayed solved ratio is the simplified one; the user's typed form is also shown so the equivalence is visible, e.g. "21:9 = 7:3").
Solving: with simplified ratio a:b and given width W, height H = W × b / a as an exact fraction, reduced; given height H, width W = H × a / b. A decimal given dimension (≤2 places) is converted to an exact fraction (×100) before solving. Display: if the fraction is an integer, display it plainly; otherwise display the value rounded to 2 decimals AND the reduced fraction `p/q` beside it. Decimal ratio (Mode A) = w/h rounded to 4 places; percentage = h/w × 100 rounded to 2 places.
Nearest-preset note: presets compared as exact fractions; "exactly" when the simplified ratios are equal; "close to X (differs by d)" when |decimal − presetDecimal| ≤ 0.01 and not equal, with d displayed to 4 places; no note otherwise. Only the single nearest preset is named.
Worked fixtures (normative, re-derived during drafting): (1) 1920×1080 → gcd 120 → **16:9**; decimal **1.7778**; height = **56.25%** of width; note "exactly 16:9". (2) 1366×768 → gcd 2 → **683:384**; decimal **1.7786**; note "close to 16:9 (differs by 0.0009)" — and the output MUST NOT present it as 16:9. (3) 2560×1080 → gcd 40 → **64:27**; decimal 2.3704; no preset note (21:9 = 2.3333 differs by 0.0370 > 0.01). (4) Mode B ratio `2.39:1` → simplified **239:100**; with width 1000 → height = 100000/239 → displayed **418.41** with fraction **100000/239**. (5) Mode B ratio 16:9, width 1280 → height **720** (integer, no fraction shown). (6) Mode B ratio 21:9 (shown as 7:3), width 1000 → height = 3000/7 → displayed **428.57** with fraction **3000/7**. (7) Mode B ratio 4:3, height 600 → width **800**. (8) Mode B ratio `1.85:1` → simplified 1850:1000 → **37:20**.

## 5. Implementation and safety
Architecture (future production): a pure core (parser to exact integers/fractions, gcd, solver, formatter) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. gcd and fraction reduction MUST be implemented over integers (Number is exact up to 2^53, far above the caps: the largest intermediate is 100,000 × 10,000,000 (scaled ratio part) = 10^12, and fraction cross-products stay under 10^17 — the implementation MUST use BigInt for cross-multiplied comparisons and solving to stay exact at the caps; using floating point for any equality or simplification decision is a defect).
Privacy/security: numbers only; no network, no storage; input renders as text; no eval/Function; no external resources.
Bilingual and accessibility: full zh-TW (default) and English UI, including the exact/close-to distinction (translated so the honesty survives: 「正好是 16:9」 vs 「接近 16:9（差 0.0009）」); outputs in text with labels; the mode and solve-direction toggles are native radio groups; all fields labelled; keyboard-complete.
Performance bounds: arithmetic is trivial; no debounce requirement. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; both modes; solve in both directions; all presets fill correctly; the exactly/close-to/no-note logic; use-as-dimensions in both its enabled and disabled states.
- boundaries: dimensions 1 and 100,000 and 100,001 refused; ratio parts with exactly 3 decimals and with 4 refused; ratio part 0 and negative refused; given dimension with 2 decimals exact-fraction path; co-prime dimensions (e.g. 683:384 from 1366×768) unsimplified further.
- privacy: zero network after load; no storage; numbers absent from URL/title.
- security: field text with markup renders inert; no external resources; no eval/Function.
- usability: an editor who knows their target width reads the required height without instructions; the fraction display is understood as "the exact value" (spot-check).
- accessibility: labelled fields and radio groups; outputs as labelled text; keyboard-complete; out-of-date state conveyed in text.
- localization-seo: zh-TW and en pages complete and equivalent (including the exact/close wording); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the preset list ships as auditable data matching section 2 exactly.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical simplified ratios and fractions across browsers at the input caps (BigInt path exercised).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) all eight section 4 fixtures exactly — simplified ratios, decimals, percentages, fractions and notes; (b) gcd sweep: equal numbers (→1:1), one dividing the other (→n:1 / 1:n), large co-primes, and the cap-corner pair (100000, 99999); (c) scaling: ratio parts 0.001 (→1 after scaling with its partner per the rule), 2.39, 1.85, and a part with trailing zeros (2.390 = 2.39); (d) solving both directions with integer, terminating-decimal and non-terminating results, asserting the fraction is reduced and the rounded display matches half-away-from-zero; (e) decimal given-dimension path (e.g. width 12.50 with ratio 1:1 → height 12.50 exactly, fraction 25/2 displayed as "12.50 (25/2)"); (f) nearest-preset selection when two presets are within 0.01 (name only the nearer).
GUI/evidence tests (desktop, real browser): fixtures entered through the real UI in both languages and both modes; preset clicks; the disabled use-as-dimensions case for fixture 6 with its stated reason. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
