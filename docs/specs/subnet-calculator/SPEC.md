# IPv4 Subnet Calculator — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. IPv4 only: IPv6 is excluded by design in this version and the page MUST say so where a user might expect it, rather than failing mysteriously on a colon.

## 1. Goal
Primary audience: network administrators, IT support technicians, and networking students (CCNA-style coursework and on-the-job checks). The recurring problem: subnet facts — broadcast address, usable range, split blocks — are worked out on scrap paper or on ad-heavy calculator sites, and a slip becomes a misconfigured DHCP scope, an overlapping VLAN plan or an exam answer marked wrong. Success is observable: the user enters an address and prefix and sees every derived fact computed exactly under the rules of section 4, including the /31 and /32 special cases explained instead of silently applying a minus-two formula; splits a network into child subnets with the total count always visible; and checks whether a second address belongs to the subnet. Non-goals: IPv6, network scanning or discovery, ping/DNS/DHCP operations, address ownership or geolocation lookup, saving entered addresses, and classful routing instruction beyond the clearly-labelled historical class label.

Assumptions: a modern desktop browser; addresses typed by the user are planning or study values; all computation is local integer arithmetic; no network at runtime.

## 2. Scope and functional distinction
Included: (a) single-subnet analysis — network address, broadcast address, netmask and wildcard mask, total addresses, usable hosts with first/last usable addresses, prefix length, a binary view with the network/host boundary marked, address class (historical label) and special-range classification per the section 4 table; (b) split mode — child prefix selection and the child subnet list with a stated display cap and uncapped total count; (c) membership check for a second address; (d) input flexibility: separate address + prefix fields, address + dotted netmask fields kept in sync, or a pasted `a.b.c.d/n` CIDR string in the address field. Excluded: IPv6 in any form, non-contiguous masks as a feature (they are an error, not a mode), subnet aggregation/supernetting, VLSM planning across multiple requirements, importing/exporting lists, and any persistence.
Distinction from existing work: the integer-representation explorer teaches bases and encodings; it performs no mask arithmetic or range logic. The unit converter converts physical units. Neither classifies address ranges or enumerates child subnets. No catalog entry, reserved specification or registry task at admission time computes subnets; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: empty address field, prefix 24 prefilled as an editable value (clearly a starting value, not a result), results area showing a hint; no result is displayed for empty input. Typing a valid address computes immediately (debounce ≤150 ms); the two mask representations (prefix and dotted netmask) stay in sync — editing either updates the other, and a pasted CIDR string fills both.
Invalid input shows a field-level error naming the exact problem (which octet, what rule) and replaces any previous result with the error state — a stale result MUST NOT remain visible under an invalid address. Mode switching (analysis / split / membership) preserves the entered address and prefix.
Split mode: a child-prefix control (only values longer than the current prefix are accepted; equal or shorter is an inline error explaining why); the list renders per section 4 with its cap notice when applicable. Membership mode: a second address field and a one-line verdict with the subnet's network–broadcast range restated.
Everything is recomputed deterministically: same inputs, same outputs, byte-identical textual results. Leaving or reloading discards the inputs; nothing is stored. A copy button copies the analysis summary as plain text (user gesture only), in the active language, with the same values as on screen.

## 4. Parsing, arithmetic and exact output
Address parsing (normative): a dotted quad is exactly four dot-separated octets; each octet is a canonical decimal integer 0–255 with no sign, no spaces and no leading zeros unless the octet is exactly `0` (leading zeros are rejected with a specific message because of historical octal ambiguity — `192.168.01.1` is an error, not a guess). Fewer/more parts, empty parts, non-digits, or an octet above 255 are each named errors identifying the octet position. A pasted CIDR `a.b.c.d/n` in the address field is split at the single `/`; a malformed suffix is an error in the prefix field's terms. Prefix: integer 0–32. Netmask field: a dotted quad parsed by the same octet rules, additionally required to be contiguous (some number of 1 bits followed by only 0 bits); a non-contiguous mask (e.g. 255.255.0.255) is the specific error "netmask is not contiguous".
Arithmetic (normative): addresses are unsigned 32-bit integers; all operations MUST be exact (JavaScript bitwise operators with unsigned coercion, or BigInt — either is acceptable if results match). mask = the prefix's mask; network = ip AND mask; broadcast = network OR (NOT mask within 32 bits); total = 2^(32−prefix), displayed as an exact integer (for /0 this is 4,294,967,296 — floating-point approximations or scientific notation are defects).
Usable-host rules (normative): prefix ≤30 → usable = total − 2, first usable = network + 1, last usable = broadcast − 1. prefix = 31 (RFC 3021 point-to-point) → usable = 2, first = network, last = broadcast, and the result carries a note that both addresses are usable on point-to-point links. prefix = 32 → usable = 1, network = broadcast = first = last = the address, noted as a host route. Wildcard mask = bitwise NOT of the netmask, displayed dotted.
Classification (normative; the entered address is classified; first matching row wins, in this order): 0.0.0.0/8 "this network" (software); 10.0.0.0/8 private (RFC 1918); 100.64.0.0/10 CGNAT shared address space (RFC 6598); 127.0.0.0/8 loopback; 169.254.0.0/16 link-local; 172.16.0.0/12 private (RFC 1918); 192.0.2.0/24 documentation (TEST-NET-1); 192.168.0.0/16 private (RFC 1918); 198.51.100.0/24 documentation (TEST-NET-2); 203.0.113.0/24 documentation (TEST-NET-3); 224.0.0.0/4 multicast; 240.0.0.0/4 reserved (includes 255.255.255.255 broadcast, which is named when the address is exactly that); otherwise public. The class label (A: 0–127, B: 128–191, C: 192–223, D: 224–239, E: 240–255 by first octet) is displayed separately and labelled "historical class" so it is never confused with the classification.
Binary view: the 32 bits of the address in four octet groups; bits left of the prefix boundary are labelled network bits and right of it host bits, in text as well as colour (never colour alone); the boundary falls between bits for non-octet prefixes (e.g. /26 shows 26 network bits).
Split mode (normative): given parent prefix p and child prefix q with p < q ≤ 32, child count = 2^(q−p); children are enumerated in ascending address order starting at the parent's network address, each with network, broadcast, and first/last usable under the same usable rules (applied at q). Display cap: at most the first 256 children are listed; when the count exceeds 256 the header states "showing first 256 of N subnets" with N exact, and no control pretends the rest are shown. q ≤ p is an error explaining that the child prefix must be longer than the parent prefix.
Membership: the second address is in the subnet iff its network computation under the same prefix equals the subnet's network address; the verdict line restates the network–broadcast range and, when outside, says so without suggesting the "nearest" subnet.
Worked fixtures (normative): `192.168.1.64/26` → netmask 255.255.255.192, wildcard 0.0.0.63, network 192.168.1.64, broadcast 192.168.1.127, total 64, usable 62, first 192.168.1.65, last 192.168.1.126, classification private. `192.0.2.5/31` → network 192.0.2.4, broadcast 192.0.2.5, total 2, usable 2 (RFC 3021 note), classification documentation. `203.0.113.9/32` → all addresses 203.0.113.9, total 1, usable 1. `0.0.0.0/0` → network 0.0.0.0, broadcast 255.255.255.255, total 4,294,967,296, usable 4,294,967,294. Split `192.168.0.0/24` at /26 → 4 children: .0, .64, .128, .192 with broadcasts .63, .127, .191, .255. Membership: 192.168.1.100 in 192.168.1.64/26 → inside; 192.168.1.128 → outside.

## 5. Implementation and safety
Architecture (future production): a pure core (parser, mask arithmetic over exact integers, classification table as data, split enumerator with cap, membership, formatting) with zero DOM access; a controller binding the synced fields and modes; a thin DOM layer. Runtime dependencies: none; the classification table ships as reviewable data in the repository.
Privacy/security: no network, no storage; typed addresses never enter URLs, titles or filenames; all rendering via text nodes; the copy summary is generated from the result model, not scraped from the DOM.
Bilingual and accessibility: full zh-TW (default) and English UI; networking terms keep their standard English forms alongside translations where that is the clearer practice (e.g. broadcast 廣播位址）; every output row is a labelled text row (term + value) readable without the binary colour coding; errors identify the field and octet; all controls keyboard reachable; the child-subnet list is a real table with headers.
Performance bounds: analysis is O(1); split enumeration is capped for display and counting is O(1) arithmetic — computing a /0 → /32 split count (4,294,967,296) MUST be instant and must not attempt enumeration beyond the cap. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all three modes; prefix/netmask sync and CIDR paste; copy summary matches the screen exactly.
- boundaries: prefixes 0, 1, 30, 31, 32; octet 0 and 255; leading-zero rejection; non-contiguous mask error; split count at cap 256 and one over.
- privacy: zero network after load; no storage; addresses absent from URL/title; nothing copied without a gesture.
- security: inputs render as text only; strict parser (no implicit numeric coercion accepting `0x` or exponents); no external resources.
- usability: a networking student reproduces every section 4 fixture without instructions; the /31 note prevents the classic minus-two confusion; errors name the octet.
- accessibility: labelled term/value rows; binary boundary conveyed in text; full keyboard flow; table semantics for split results.
- localization-seo: zh-TW and en pages complete and equivalent; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; classification table ships as data and is diffed against section 4 in review.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; exact-integer display of the /0 totals identical across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) every section 4 fixture exactly, including counts as integers; (b) parser sweep: each octet error class, leading zeros, CIDR paste forms, prefix −1/33/non-integer, contiguous-mask validation across all 33 valid masks plus named invalid ones; (c) arithmetic cross-check against an independent bit-string implementation inside the test (string-based, written separately from the core) over a seeded sweep of (address, prefix) pairs; (d) classification: one address per table row plus boundary addresses just inside/outside 172.16/12 and 100.64/10; (e) split: counts for (p,q) pairs including q−p = 20 (count 1,048,576 with the 256 display cap), child boundary addresses; (f) usable-rule branches at /30, /31, /32.
GUI/evidence tests (desktop, real browser): fixtures through the real UI in both languages, sync behaviour between prefix and netmask fields, error replacement of stale results, keyboard-only completion. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
