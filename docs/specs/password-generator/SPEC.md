# Password Generator and Strength Checker — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The page MUST state in both languages that strength figures are estimates from the explicit model in section 4 — not a guarantee — and that generated passwords should be kept in a reputable password manager, because this tool stores nothing.

## 1. Goal
Primary audience: anyone creating or rotating an account password at home or at work, including users who have reused one weak password everywhere and are fixing that one account at a time. The recurring problem: online generators require trusting a remote server with the very secret being created, and strength meters give unexplained verdicts ("strong!") with no model behind them. Success is observable: the user generates a password or passphrase whose entropy in bits is shown and reproducible from the stated pool and wordlist sizes, copies it with one click, and — when checking an existing password — sees the estimate decomposed into the base entropy and each penalty that was subtracted, so the advice "make it longer, drop the dictionary word" is concrete. Non-goals: breach-database lookup, password storage or vault features, account integration, auto-fill, synchronisation, and any percentage-style "safety score".

Assumptions: a modern desktop browser exposing `crypto.getRandomValues`; the user pastes the generated secret into their own password manager; nothing about the session may persist after the tab closes.

## 2. Scope and functional distinction
Included: (a) random-password generation — length 8–128 (default 20), toggles for lowercase, uppercase, digits and the fixed symbol set of section 4, an exclude-ambiguous option, a guarantee of at least one character from every enabled set, batch generation of 1–10 items shown as a list, per-item copy button, and displayed entropy per item; (b) passphrase generation — 3–10 words from the bundled wordlist specified in section 4, separator choice (hyphen, space, underscore, dot, none), optional capitalisation of exactly one word, optional single trailing digit, batch of 1–10, displayed entropy; (c) strength checking of a user-typed password under the section 4 model with itemised penalties and a banded verdict; (d) a wipe control that clears generated lists and the check field immediately.

Excluded: any network operation (including hashed breach lookups), storage of any kind (localStorage, cookies, history), password editing/merge tools, policy templates for specific sites, QR or file export of secrets, printing, and generating with a non-cryptographic random source under any fallback — if `crypto.getRandomValues` is unavailable the tool MUST refuse to generate and say why.

Distinction from existing work: Text Redactor replaces chosen strings inside a document the user is editing; it does not create secrets. Random Groups samples a person's list into groups with no entropy contract and no secrecy lifecycle. Text Workbench counts and cleans text. None of them generates credentials, models guessing entropy, or is defined by a never-transmit/never-persist lifecycle. No catalog entry, reserved specification or registry task at admission time generates passwords or estimates their strength; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: password mode selected, defaults as above, no generated items; the strength-check field is empty and masked. The three modes (Password / Passphrase / Check) are tabs; switching tabs does not clear the other modes' in-memory state during the session, but generated items are never carried anywhere else.
Generating replaces the current batch (it does not append) — the user is told the count before generating if a batch already exists ("Generate replaces the 10 shown passwords"). Each generated row shows the secret in a monospace field, its entropy in bits, and a copy button; copying shows a transient "copied" note and MUST NOT also copy anything else. Entropy updates live when length/toggles change (before generation) as "expected entropy".
Checking: typing or pasting into the masked field updates the estimate after a ≤150 ms debounce; a show/hide toggle switches masking; the breakdown lists base bits, each triggered penalty with its amount, and the final banded verdict. The checked value is never rendered anywhere except the masked field itself — the breakdown refers to features ("contains a dictionary word", "4-digit year") without quoting the password or its substrings.
Wipe: one control clears generated batches in both modes and empties the check field and its breakdown; leaving or reloading discards everything by construction (nothing was stored). All operations are local and repeatable; generation is intentionally non-deterministic in output but exact in its stated distribution and entropy accounting.

## 4. Generation rules, entropy model and exact output
Character sets (exact): lowercase `abcdefghijklmnopqrstuvwxyz` (26); uppercase `ABCDEFGHIJKLMNOPQRSTUVWXYZ` (26); digits `0123456789` (10); symbols `!@#$%^&*()-_=+[]{};:,.<>?/` (26). Combined pool is the union of enabled sets (max 88). Exclude-ambiguous removes exactly `l`, `I`, `1`, `O`, `0` from whichever sets are enabled (pool sizes become 25/24/8/26 for the four sets).
Sampling (normative): indices come from `crypto.getRandomValues` bytes with rejection sampling — for pool size p, accept byte b only when b < ⌊256/p⌋×p, index = b mod p; bytes are drawn in blocks as needed. `Math.random` MUST NOT be used anywhere. A candidate password is drawn position-by-position from the combined pool; if any enabled set is unrepresented, the ENTIRE candidate is discarded and redrawn (no insertion/patching, which would bias the distribution); after 100 failed redraws the tool reports an internal error (unreachable in practice for valid settings; length MUST be ≥ the number of enabled sets, enforced as a field error, e.g. length 3 with 4 sets enabled).
Entropy displayed for a generated password: bits = length × log2(poolSize), shown rounded to one decimal. For the default (length 20, all sets, pool 88): 20 × log2(88) = 129.2 bits.
Passphrase wordlist: a bundled data file of exactly 7,776 unique lowercase a–z words (the production task MUST ship the list as a reviewable artefact with its source licence recorded; the specification fixes the size, not the words). Word selection uses the same rejection sampling over indices 0–7775. Entropy = words × log2(7776) = words × 12.92 bits (shown to one decimal: e.g. 5 words = 64.6 bits). Options add exactly: capitalising one uniformly chosen word adds log2(wordCount) bits; appending one uniformly chosen digit adds log2(10) = 3.3 bits; the separator adds 0 bits and the display MUST NOT pretend otherwise. The joined passphrase uses the chosen separator between every pair of words; no leading/trailing separator.
Strength model for the checker: base pool = union of classes actually present in the checked password (lowercase 26, uppercase 26, digits 10, symbols 32 if any symbol outside the generator's set appears count symbols as 32, any non-ASCII character adds a flat +20 to the pool and is noted). Base bits = length × log2(basePool) (length in Unicode code points). Penalties, each applied at most the stated number of times and itemised: dictionary word (a substring of length ≥4 that appears in the bundled 7,776-word list, case-insensitive): −20 per distinct word, max 2 counted; repeat run (≥3 identical consecutive characters): −10, max 1; ascending or descending sequence of length ≥4 within digits or letters: −10, max 1; keyboard walk of length ≥4 on a stated QWERTY row layout: −10, max 1; a 4-digit substring in 1900–2099: −8, max 1; length under 8: −10. Final = max(0, base − total penalties), one decimal. Verdict bands: <28 "very weak", 28–35.9 "weak", 36–59.9 "fair", 60–79.9 "strong", ≥80 "very strong" — always paired with the sentence that this is a model estimate. Worked fixture (normative): `password` ⇒ pool 26, base 8 × log2(26) = 37.6, dictionary penalty −20 ⇒ 17.6, very weak. `Xq7!mZ2#` ⇒ pool 88, base 8 × 6.46 = 51.7, no penalties ⇒ 51.7, fair. (log2 values rounded for display; comparisons in tests use the exact formula with a 0.05 tolerance on the displayed decimal.)
Output rules: generated items render as text only; entropy always accompanies an item (a bare password with no bits figure is a defect); copy writes exactly the item string, nothing else.

## 5. Implementation and safety
Architecture (future production): a pure core (pool construction, sampler over an injectable byte source, entropy arithmetic, strength model, wordlist access) with zero DOM access; the byte source interface lets tests drive the sampler deterministically. The wordlist ships as a static data module in the repository. Runtime dependencies: none; no network; no storage APIs called at all.
Security/privacy (the point of the tool): `crypto.getRandomValues` is the only randomness source; generated and checked secrets live only in page memory and the user's clipboard after an explicit copy click; they MUST NOT appear in the URL, title, console logs, error messages, analytics (none exist) or any DOM attribute beyond the display field; the check field uses `type="password"` with `autocomplete="off"` and spellcheck disabled; the page sets no cookies. The specification acknowledges the residual risk honestly in the UI: a screenshot or shoulder-surfer can still see a generated password while it is on screen.
Bilingual and accessibility: full zh-TW (default) and English UI; verdict band names and every penalty label are translated, not left in one language; controls are native inputs with labels; generated rows are reachable and copyable by keyboard; entropy and verdict changes are announced via `aria-live="polite"` without reading secrets aloud (announcements say "generated, 129.2 bits", never the secret). Performance bounds: generating 10 × 128-character passwords completes within 100 ms; strength re-evaluation per keystroke within 20 ms for inputs up to 1,024 characters (inputs longer than that are an error in check mode, not truncated silently). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all three modes; toggles/length/word-count edge settings; entropy figures match section 4 formulas on sampled outputs; copy writes the exact item.
- boundaries: length 8 and 128; length below enabled-set count (error); all sets off (error — at least one set required); passphrase 3 and 10 words; check input 1,024 chars and 1,025 (error).
- privacy: zero network after load; no storage writes (verified by storage inspection); secrets absent from URL/title/logs; wipe actually clears all three modes.
- security: sampler uses only crypto.getRandomValues (code-audited and distribution-tested); rejection-sampling bound correct for pool 88 and 7776; checked password never quoted in the breakdown.
- usability: a first-time user generates, understands the bits figure, and copies within seconds; the checker breakdown makes the top improvement obvious.
- accessibility: keyboard-complete flows; polite announcements that never speak secrets; masked-field toggle operable and labelled.
- localization-seo: zh-TW and en pages complete and equivalent including the model disclaimer; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; wordlist artefact present with size 7,776 verified by test and its licence/source recorded.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical sampler behaviour across browsers given the same injected byte stream (core-level test).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) sampler determinism — an injected byte stream with known rejection cases (bytes ≥ bound discarded) produces the exact expected indices for pools 88, 26 and 7776; (b) distribution sanity over a fixed large byte fixture (chi-square style bounds stated in the test, not tuned to pass); (c) entropy arithmetic fixtures from section 4 (129.2 default; 64.6 five-word; option additions); (d) strength fixtures: the two worked examples plus constructed cases triggering each penalty once and in combination, and the max-count caps; (e) set-guarantee: a rigged byte source that first yields a candidate missing a set must produce a full redraw, and the output must equal the second candidate exactly; (f) ambiguous-exclusion pool contents.
GUI/evidence tests (desktop, real browser): generate/copy/wipe flows in both languages with synthetic values only; verdict breakdown rendering; keyboard-only completion; storage/network inspection screenshots. Timing: full core suite under 60 seconds; no network in any test; NO real password of any person may be used as a fixture or typed during evidence capture.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
