# Text-to-Speech Reader — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The tool is a controller over the platform's Web Speech API; where platform behaviour varies, this specification fixes what the tool does and requires the tool to be honest about what it cannot control.

## 1. Goal
Primary audience: people who proofread by ear, language learners shadowing pronunciation, readers with low vision or reading fatigue, and parents generating a quick read-aloud of a pasted story. The recurring problem: cloud TTS services require uploading the text (a draft contract, a diary entry, a child's worksheet) to a remote server, and built-in OS read-aloud features are buried and inconsistent. Success is observable: the user pastes text, chooses among the voices the browser actually offers — each labelled with its language and whether it is a local or network voice — and hears the text read with predictable play/pause/resume/stop, a visible highlight tracking the current sentence, and progress they can check. Non-goals: SSML control, audio recording or file export (the platform API cannot capture its own output; the page MUST say so instead of offering a fake download), translation, voice cloning, and fetching text from URLs or files other than a plain-text file the user picks locally.

Assumptions: a modern desktop browser exposing `speechSynthesis`; the user accepts that available voices depend on their OS/browser; no network is used by the tool itself, though a network voice chosen by the user sends text to that voice's provider — this is disclosed, per section 3.

## 2. Scope and functional distinction
Included: (a) text input (typing, paste, or a local .txt file) up to the section 4 limit; (b) sentence segmentation and chunking per section 4, displayed as a sentence list preview; (c) voice selection from `getVoices()` with name, language tag and local/network label; (d) rate (0.5–2.0) and pitch (0.0–2.0) controls with numeric readouts; (e) transport — play from start, play from a clicked sentence, pause, resume, stop — under the section 3 state machine; (f) current-sentence highlight and progress (sentence n of N); (g) clear control. Excluded: word-by-word karaoke timing (boundary events are too inconsistent across platforms; sentence-level is the contract), background playback guarantees when the tab is hidden (platform-dependent, noted in help), pronunciation dictionaries, and any storage of text or settings.
Distinction from existing work: the subtitle tools process caption files and timing; the media tools handle recorded media. None drives speech synthesis, segments text for utterance queues, or manages a playback state machine over platform voices. No catalog entry, reserved specification or registry task at admission time reads text aloud; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial states: if `speechSynthesis` is unavailable, the page shows only an unsupported-browser panel (no dead controls). Otherwise: empty text area, voice list loading state until `voiceschanged`/first `getVoices()` resolves (a 1-second fallback re-poll is specified so the list never hangs empty when voices exist), transport disabled until text and a voice exist.
Voice list: each entry shows voice name, language tag (e.g. zh-TW, en-US), and `localService` rendered as 本機/local or 網路/network. Default selection: the first voice whose language matches the UI language; else the browser default voice; else the first voice. The first time the user selects a network voice, an inline notice appears: text read with this voice is sent to its provider — the tool itself sends nothing anywhere.
Playback state machine (normative): states idle, speaking, paused. Play (from start or a sentence) cancels any current queue, then enqueues chunks one at a time: the controller speaks chunk k, and only on its `end`/`error` event enqueues k+1 — this makes Stop immediate and makes voice/rate/pitch changes take effect from the next chunk, both stated in help. Pause calls `speechSynthesis.pause()` (state paused; if a platform ignores pause for local voices, the help notes the known variance and the highlight/progress remain correct at chunk granularity). Resume reverses it. Stop cancels the queue and returns to idle with progress reset to the start sentence. Natural completion returns to idle with progress showing N of N.
Editing text during playback stops playback (a stale queue reading deleted text is a defect). Clicking a sentence in the preview list while idle starts playback from that sentence. The highlight marks exactly the sentence containing the current chunk; when a sentence was split into multiple chunks, the highlight stays on that sentence until its last chunk ends.
Errors: an utterance `error` event (e.g. voice unavailable mid-run) stops playback, returns to idle, and shows the error name in plain language with a suggestion to pick another voice; it never loops retries. Leaving the page cancels speech (`cancel()` on unload); reloading starts empty; nothing is stored.

## 4. Text, segmentation and playback rules
Input: text up to 20,000 characters (code points); over-limit input is a named error, not a truncation. A picked .txt file is read locally and decoded as UTF-8 (a decode failure is a named error suggesting re-saving as UTF-8). Whitespace-only text counts as empty (error prompting for text).
Segmentation (normative, pure function): the text is split into sentences by scanning left to right; a boundary occurs (a) after one of `。！？` including any immediately following closing quotes/brackets `」』”’）】`, (b) after one of `.!?` when followed by whitespace and then an uppercase letter, digit, or opening quote, or by end of text (the whitespace is consumed as separator, not spoken), (c) at every newline (the newline is a separator). Decimal numbers (`3.14`) and the bundled abbreviation list (`Mr.`, `Mrs.`, `Dr.`, `e.g.`, `i.e.`, `etc.`, `vs.`) do not create boundaries — the list is closed and shipped as data. Segmentation is a display/chunking heuristic: the SPEC states that an occasional over- or under-split changes highlight granularity only, never the words spoken, because chunks are concatenated in original order with original spacing normalised to a single space at joins.
Chunking (normative): any sentence longer than 200 characters is split into chunks of at most 200 characters at the last clause separator `，、；：,` within the limit; if none exists, at the last space within the limit; if none, a hard cut at 200 characters. Every chunk records its source sentence index (for highlight) and its ordinal. The full ordered chunk list is a deterministic function of (text) — voice/rate/pitch do not affect it.
Utterance parameters: each chunk is spoken with the selected voice, and rate/pitch snapshotted at the moment that chunk is enqueued (hence mid-playback changes apply from the next chunk, per section 3). Rate steps 0.1 within 0.5–2.0 (default 1.0); pitch steps 0.1 within 0.0–2.0 (default 1.0); volume is fixed at 1.0 (no control in this version).
Progress: "sentence k of N" uses the current chunk's sentence index; a character progress (characters in chunks fully spoken / total characters) is shown as a percentage rounded down. Both derive from the chunk list, not from boundary events, so they are identical across browsers for the same text.
Normative fixtures: the zh text `你好嗎？我很好。今天天氣不錯。` segments into exactly 3 sentences. The en text `Dr. Lee paid 3.14 dollars. Then he left.` segments into exactly 2 sentences. A 450-character single zh sentence with clause commas at known positions chunks per the 200-char rule into 3 chunks whose concatenation (single-space joins removed) reproduces the sentence. Empty and whitespace-only inputs produce the empty error; 20,001 characters produce the limit error.

## 5. Implementation and safety
Architecture (future production): a pure core (segmentation, chunking, abbreviation data, progress arithmetic) with zero DOM and zero speech-API access; a speech controller implementing the section 3 state machine over an injected synthesis interface (so the state machine is unit-testable with a fake engine); a thin DOM layer. Runtime dependencies: none.
Privacy/security: text lives only in page memory; no storage, no analytics, no tool-initiated network; the network-voice disclosure of section 3 is part of the privacy contract; file input reads only the user-picked file; text is rendered as text nodes (the sentence list can never inject markup from pasted HTML).
Bilingual and accessibility: full zh-TW (default) and English UI — fittingly, every control is operable by users who cannot easily read the screen: real buttons with text labels, a logical focus order (text → voice → transport), state changes announced via `aria-live="polite"` ("playing, sentence 3 of 12"), and the highlight is paired with the text progress so it is not colour-only. Keyboard shortcuts are not required in this version (stated, to avoid conflicts with assistive tech).
Performance bounds: segmentation+chunking of the maximum 20,000 characters completes within 50 ms; the sentence list renders at most 20,000/1 entries and MUST remain usable at the maximum (a plain list is acceptable). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs from a static host or file:// subject to platform voice availability.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance. Audible correctness is verified by the manual listening check named in section 7; everything automatable must be automated, and the manual check is recorded as manual evidence, not silently assumed.
- functionality: both languages; the state machine transitions of section 3 (against the fake engine and in a real browser); play-from-sentence; mid-playback rate change applying at the next chunk; unsupported-browser panel.
- boundaries: empty/whitespace text; 20,000 vs 20,001 characters; a single 5,000-character sentence's chunking; voice list arriving late (voiceschanged) and empty.
- privacy: zero tool-initiated network; no storage; network-voice disclosure appears exactly when a network voice is first selected; picked-file reading stays local.
- security: pasted markup renders as text in the sentence list; no innerHTML path for user text; no external resources.
- usability: a first-time user pastes a paragraph and hears it read within seconds; stop is immediate; the no-export limitation is stated where users look for it, not buried.
- accessibility: screen-reader announcements of state and progress; full keyboard operation; highlight not colour-only.
- localization-seo: zh-TW and en pages complete and equivalent; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; the abbreviation list ships as reviewable data.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; known platform variances (pause behaviour, voice availability) documented in help and observed in the smoke pass, not treated as tool defects when the platform is at fault — each variance claim needs the browser/version noted as evidence.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) every section 4 segmentation fixture verbatim, plus abbreviation and decimal cases, CJK closing-quote attachment, and newline boundaries; (b) chunking: the 450-character fixture, clause-separator preference order, no-separator hard cut, chunk→sentence index mapping, and the concatenation invariant over randomised-but-seeded inputs; (c) progress arithmetic.
Controller tests with a fake synthesis engine: play enqueues exactly one chunk and advances on end; pause/resume calls; stop cancels and resets; edit-during-playback stops; utterance error path returns to idle with the error surfaced; play-from-sentence starts at the right chunk.
GUI/evidence tests (desktop, real browser): one manual listening check per language (zh-TW and en short fixtures) recorded as manual evidence with browser and voice named; automated smoke for list population, transport enablement, highlight movement using a local voice if available; keyboard-only completion; both languages screenshotted. Timing: core+controller suites under 60 seconds; no network in automated tests (a network voice is never selected in automation).
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
