# Regex Tester and Replacer — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The engine is the browser's ECMAScript `RegExp`; the page MUST state that flavour plainly, because patterns are not portable between flavours and a user verifying a pattern here is verifying JavaScript behaviour specifically.

## 1. Goal
Primary audience: developers, students, QA and support engineers, and data-entry staff who must confirm that a pattern extracts or validates exactly what they intend before it ships in code or a form. The recurring problem: the test loop otherwise happens against production data, or on online testers that ask users to paste log lines and record data into a remote service. Success is observable: the user enters a pattern and flags, pastes sample text, and sees every match highlighted in place with its position, its capture groups (named groups by name), and — in replace mode — the exact resulting text and replacement count, all matching what the same JavaScript engine would do in their own program. Non-goals: other regex flavours (PCRE, Python, Java, .NET), pattern generation or "AI explanation", saving/sharing patterns via accounts or URLs, and any promise to stop a pathological pattern mid-run (impossible for JavaScript regular expressions — see the honesty rule in section 3).

Assumptions: a modern desktop browser; sample text is pasted by the user and may be sensitive, which is exactly why nothing leaves the page; no network at runtime.

## 2. Scope and functional distinction
Included: (a) pattern input with flag toggles g, i, m, s, u, y; (b) match mode — highlighted test text, a match list (index, matched text, group table), and a count; (c) replace mode — replacement-string input with ECMAScript substitution semantics, full result preview and replacement count; (d) four bundled presets (email-like address, ISO date, order number, log timestamp) that fill pattern+text only when clicked; (e) pattern syntax-error display with the engine's message; (f) clear control. Excluded: flavour conversion, pattern libraries/accounts, step-through debugger visualisation, generating code snippets, and fetching anything.
Distinction from existing work: Text Diff aligns two texts; Text Workbench applies fixed transformations; neither evaluates a user-supplied pattern, enumerates capture groups, or implements substitution semantics. No catalog entry, reserved specification or registry task at admission time tests regular expressions; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.
Flavour notes the help MUST include: ECMAScript supports lookbehind and named groups `(?<name>…)`; it does not support possessive quantifiers, atomic groups, balancing groups or `\G`; `\d` is ASCII-only even under the u flag; `.` excludes line terminators unless the s flag is set.

## 3. User flow and lifecycle
Initial state: empty pattern, flags g on and others off, empty test text, replace mode collapsed, an explanatory line (engine flavour + privacy: runs locally). Any change to pattern, flags or text recomputes after a ≤200 ms debounce.
If the pattern is invalid, the results area shows the error state: the engine's `SyntaxError` message verbatim, and the test text is shown unhighlighted; there is never a silent "0 matches" for an unparseable pattern. If the pattern is valid but matches nothing, the result is an explicit "no matches" — distinguishable from the error state.
Match list: matches are numbered from 1; selecting a match in the list scrolls the highlighted text to it (and vice versa where feasible); each match expands to its group table. A results footer states match count and the evaluation time in milliseconds (measured, rounded to whole ms) so a slow pattern is visible as slow.
Honesty rule: above the inputs, a permanent one-line warning states that a pathological pattern can freeze the tab because JavaScript regex cannot be interrupted, and that the input limits of section 4 are the mitigation. The tool MUST NOT display a "timeout" or "safe mode" claim.
Replace mode: expanding it reveals the replacement input and the result pane; the count shown equals the number of substitutions actually performed; with g off exactly the first match is replaced, per engine semantics.
Leaving or reloading discards everything; nothing is stored; presets are constants shipped with the page. Re-evaluation with identical inputs is deterministic (same list, same order, same expansion), evaluation time excepted.

## 4. Matching, indices and substitution rules
Limits (violations are named errors, nothing is truncated silently): pattern ≤500 characters; test text ≤50,000 characters; replacement string ≤1,000 characters. Character counts are Unicode code points.
Flags: the toggles map one-to-one to RegExp flags; the constructed flag string order is fixed as `gimsuy` filtered to enabled flags, so behaviour never depends on toggle click order.
Enumeration (normative): matches are produced by repeated `exec` on a single RegExp instance. With g or y: iterate from lastIndex 0; after a zero-width match, advance lastIndex by one code unit before the next exec (the ECMAScript AdvanceStringIndex rule, respecting the u flag for surrogate pairs) — this prevents infinite loops and is part of the contract. With y (sticky), enumeration stops at the first position where exec fails, per sticky semantics. Without g and without y: exactly one exec from index 0. Enumeration caps at 1,000 matches; hitting the cap stops iteration and shows a notice "stopped at 1,000 matches" alongside the partial results — a partial list is labelled partial, never presented as complete.
Indices: for each match, report start and end in UTF-16 code units (the engine's native index) and in code points, where code-point index = the number of Unicode code points in `text.slice(0, unitIndex)`. Groups: group 0 is the whole match; numbered groups follow in opening-parenthesis order; a group that did not participate is displayed as "— (did not participate)", visually and textually distinct from a group that matched the empty string, which displays as "(empty)". Named groups are listed by name in addition to their numbers. Optional groups inside a quantified construct follow the engine's capture semantics exactly — the tool reports the engine's result, it does not reinterpret it.
Highlighting: the test text is rendered as escaped text with `<mark>` elements around each match (zero-width matches render as a thin caret marker element with a tooltip/title "zero-width match at N"); marks never nest or overlap by construction of the enumeration. Match text containing HTML is inert (text nodes only).
Substitution (replace mode, normative = ECMAScript GetSubstitution): `$$` → `$`; `$&` → the whole match; `` $` `` → the portion before the match; `$'` → the portion after the match; `$n` / `$nn` (1–99) → the group if it exists (two-digit form is used only when that group number exists, otherwise the one-digit form, otherwise the characters are literal); `$<name>` → the named group (an unknown name is an error state in the result pane naming the group, not a silent literal). The result is built by the core from the same enumeration as match mode, so the preview and the count cannot disagree. A non-participating group substitutes as the empty string.
Worked fixtures (normative): pattern `(\d{4})-(\d{2})-(\d{2})`, flags g, text `due 2026-11-02, was 2025-01-30` ⇒ 2 matches; match 1 at code-unit 4–14 with groups 2026 / 11 / 02. Pattern `(?<word>[a-z]+)` on `ab cd` ⇒ match 1 group name `word` = `ab`. Pattern `(?=b)` on `ab b` ⇒ zero-width matches at code-unit indices 1 and 3. Replace: pattern `(\w+)@example\.com`, replacement `$1 [at] example.com`, text `write to sam@example.com` ⇒ result `write to sam [at] example.com`, count 1. Pattern `a{2,1}` ⇒ the error state (engine SyntaxError), never "no matches".

## 5. Implementation and safety
Architecture (future production): a pure core (flag assembly, match enumeration over an injected RegExp factory, index conversion, substitution expansion, result model) with zero DOM access; a controller; a thin DOM layer that renders text/mark spans from the result model (never by string-concatenating unescaped HTML). Runtime dependencies: none.
Privacy/security: pattern and text are data, rendered only as text nodes; no storage, no network; the pattern is never placed in the URL (no share links in this version, by design); clipboard actions are per-button user gestures copying exactly the displayed result.
Bilingual and accessibility: full zh-TW (default) and English UI including flag descriptions and the flavour notes; flag toggles are real checkboxes with per-flag explanations; the match list is a table/list with text positions (highlighting is never the only carrier of the result); errors are announced and tied to the pattern field; keyboard-only operation completes both modes. The evaluation-time footer and cap notice are text, not colour cues.
Performance bounds: at the maximum inputs (500-char pattern, 50,000-char text) a non-pathological pattern evaluates within 200 ms on a mid-range laptop; the ReDoS caveat of section 3 governs pathological cases honestly instead of a fake bound. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host. Engine note: because the engine is the host browser's, the production tests in section 7 run the core in Node (same ECMAScript semantics) plus a browser smoke pass.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; match and replace modes; flags individually and combined; presets; error state distinct from no-match state; cap notice at 1,000 matches.
- boundaries: zero-width matches (including at end of text); empty pattern (valid — matches everywhere per engine); empty text; limits at and one over; sticky flag stopping early; non-participating vs empty groups.
- privacy: zero network after load; no storage; pattern/text absent from URL, title and logs.
- security: markup in text/pattern renders inert; no innerHTML path for user strings; no external resources.
- usability: a first-time developer verifies a date-extraction pattern without instructions; group table answers "what did group 2 capture" at a glance; the ReDoS warning is understandable.
- accessibility: text-carried results, labelled toggles with explanations, keyboard-complete flows, announced errors.
- localization-seo: zh-TW and en pages complete and equivalent including flavour notes; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; core tests assert the section 4 fixtures verbatim.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; any engine difference between Node test runs and a browser is investigated, not waved through.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) every section 4 worked fixture exactly (indices in both unit systems, groups, substitution result and count); (b) enumeration: zero-width advance rule on `(?=a)` over a run of a's, sticky early stop, no-g single match, the 1,000 cap with a constructed many-match input; (c) substitution edge cases: `$10` when group 10 exists vs when only group 1 exists, `$<name>` unknown (error), `$$`, `` $` `` and `$'` in a multi-match replace; (d) index conversion with astral characters (emoji) before the match; (e) each flag's isolated effect (i on case, m on ^/$, s on dot, u on astral classes); (f) limit errors.
GUI/evidence tests (desktop, real browser): the fixtures through the real UI in both languages, highlight alignment on a match after an emoji, error-state screenshot, keyboard-only completion. Timing: full core suite under 60 seconds; no network in any test; sample texts are synthetic (example.com/example domains, fake log lines).
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
