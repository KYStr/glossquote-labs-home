# JWT Decoder and Claims Inspector — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The governing honesty rule of the whole tool: it decodes, it never verifies. Any wording, colour or layout that lets a user walk away believing a forged token was authenticated is a defect of the highest severity in this specification.

## 1. Goal
Primary audience: developers, QA engineers and support staff debugging authentication and authorisation (an expired session, a missing scope, a wrong audience). The recurring problem: inspecting a token means pasting a live credential into a third-party web page, or squinting at raw base64. Success is observable: the user pastes a compact token and sees its header and payload decoded as readable JSON, the registered time claims translated into local human times with a clear "expired at the current device time" / "not yet valid" / "within its stated window" readout, and the signature segment identified as present-but-unverified — all locally, with the token gone when the tab closes. Non-goals: signature verification or creation, key/JWK handling or fetching, JWE decryption, token issuance, session management, and any storage, history or sharing of tokens.

Assumptions: a modern desktop browser; the user pastes tokens they are authorised to inspect; the device clock is the reference for time readouts and is labelled as such (a wrong device clock yields a wrong readout — stated in help).

## 2. Scope and functional distinction
Included: (a) decoding of one compact token with exactly three base64url parts; (b) header and payload rendered as pretty-printed JSON preserving the source key order, plus a claims table annotating the registered claims (iss, sub, aud, exp, nbf, iat, jti) and any others by name; (c) NumericDate conversion for exp/nbf/iat to local date-time (with the UTC instant also shown) and relative phrasing (e.g. "expired 3 hours ago", "expires in 42 minutes") computed at decode time; (d) a time-status summary: EXPIRED (now ≥ exp), NOT YET VALID (now < nbf), WITHIN STATED WINDOW (neither), or NO TIME CLAIMS, always worded as statements about the claims versus the device clock, never as token validity; (e) header summary (alg, typ, kid when present); (f) signature segment display: its encoded text (truncatable visually with full text selectable) and its decoded byte length; (g) structural error reporting per section 4.
Excluded: any cryptography; `alg=none` receives no special trust (it is displayed like any other alg value, under the same not-verified banner); five-part input is recognised as probable JWE and explained, not decoded; tokens above the size cap are rejected, not truncated.
Distinction from existing work: the UTF-8 Base64 Text Codec converts arbitrary text with strict Base64 — it has no token structure, no JSON claim semantics and no trust framing; the JSON Workbench formats standalone JSON. Neither implements the three-part model, NumericDate handling or the not-verified contract. No catalog entry, reserved specification or registry task at admission time inspects JWTs; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: an empty token field, the permanent banner visible before any input: "Decoded locally in your browser. The signature is NOT verified — anyone can forge these contents. Never paste a token you would not show a colleague." (and its zh-TW equivalent). The banner is part of the page, not a dismissible toast.
Pasting or typing a token decodes on input (debounce ≤200 ms) when the field is non-empty: on success the three sections appear — Header, Payload (JSON + claims table), Signature (encoded text + byte length) — and the time-status line. On failure the results area shows the specific structural error (section 4) and no partial decode is presented as if complete (a decodable header may be shown only inside the error panel, explicitly labelled as partial).
The claims table lists each claim name, its raw JSON value, and where applicable its annotation (for exp/nbf/iat: local time, UTC time, relative phrase; for aud: the string or list rendered in full). Unknown claims appear without annotation — the tool never invents meanings.
A "clear" button empties the field and results. Nothing is stored; the token is never placed in the URL, title or any log; leaving or reloading discards it. Decoding the same token twice yields identical output (the relative phrases and time status excepted, as they depend on the clock, and they are labelled with the evaluation time).
The decoded JSON panes offer a copy button per pane (user gesture) copying exactly the displayed pretty JSON of that pane.

## 4. Input rules and exact output
Input limits: the pasted text is trimmed of leading/trailing ASCII whitespace; internal whitespace anywhere is an error ("token contains whitespace"). Maximum length 16,384 characters; over the cap → the size error. Empty after trim → the empty state, not an error.
Structure: the text MUST split on `.` into exactly 3 parts; 5 parts produce the JWE explanation error; any other count produces the part-count error naming the count found. The header and payload parts MUST be non-empty; the signature part MAY be empty (byte length 0, displayed as "empty signature segment") — `alg` values are reported, never judged.
Base64url decoding (normative, per part): the alphabet is `A–Z a–z 0–9 - _`; any other character (including `+`, `/`, whitespace, or `=` anywhere except trailing padding) is an error naming the part ("header"/"payload"/"signature") and the character position. Padding: zero, one or two trailing `=` are accepted when they make the length valid; a part whose unpadded length mod 4 equals 1 is an error (no valid decoding exists). Decoding is byte-exact; header and payload bytes MUST then decode as UTF-8 (a UTF-8 failure is a named error) and parse as JSON whose top level is an object — a JSON array, string, or number at the top level is the "not a JSON object" error; a JSON parse failure reports the parser's position when available. Duplicate keys inside a JSON object follow `JSON.parse` semantics (last wins) and this is stated in help, since the pretty printer cannot show both.
Pretty printing: `JSON.stringify` with 2-space indent over the parsed value, preserving parsed key order (which for JSON.parse is source order for string keys). Numbers render as parsed; the raw payload JSON text is not retained or shown.
Claims annotation: exp/nbf/iat, when present, MUST be JSON numbers (NumericDate); a non-number in one of these claims is an annotation-row warning ("exp is not a NumericDate — shown raw") rather than a decode failure, and no time status is derived from it. Time status (only from valid NumericDate exp/nbf): EXPIRED when exp present and now ≥ exp; else NOT YET VALID when nbf present and now < nbf; else WITHIN STATED WINDOW when at least one of exp/nbf is valid; else NO TIME CLAIMS. Boundary rule: a token whose exp equals now exactly is EXPIRED (per RFC 7519, the token MUST NOT be accepted at or after exp — the readout mirrors that wording as a statement about the claim). Local times are formatted in the active UI language with the device's timezone named; relative phrases round to the largest unit among days/hours/minutes/seconds with floor semantics (e.g. 89 minutes → "1 hour 29 minutes" is NOT produced; the rule is: ≥48 h → whole days; ≥120 min → whole hours; ≥60 s → whole minutes; else whole seconds — the chosen single unit and value are shown).
Header summary: alg (string; a non-string alg is shown raw with a note), typ and kid when present; `cty` and any other header parameters appear in the JSON pane without annotation.
Signature display: the encoded segment verbatim and `N bytes` from its decoding (0 allowed). The words under it are fixed: "Signature is not verified by this tool."
Worked fixture (normative): the token `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTEyMzQiLCJpc3MiOiJodHRwczovL2lzc3Vlci5leGFtcGxlIiwiYXVkIjoiZ2xvc3NxdW90ZS1sYWJzIiwiaWF0IjoxNzYyMDAwMDAwLCJuYmYiOjE3NjIwMDAwMDAsImV4cCI6MTc2MjAwMzYwMCwianRpIjoiZml4dHVyZS0wMDAxIiwic2NvcGUiOiJyZWFkOmRlbW8ifQ.ZHVtbXktc2lnbmF0dXJlLWZvci1maXh0dXJlLW9ubHk` decodes to header {alg HS256, typ JWT}; payload with sub `user-1234`, iat = 2025-11-01T12:26:40Z, exp = 2025-11-01T13:26:40Z; signature 32 bytes. With the evaluation clock pinned at 2025-11-01T13:00:00Z the status is WITHIN STATED WINDOW; pinned at exactly 13:26:40Z it is EXPIRED. This fixture's signature segment is a dummy string, not a real HMAC — the specification says so wherever the fixture appears, modelling the honesty the product must show.

## 5. Implementation and safety
Architecture (future production): a pure core (part splitting, strict base64url decoder, JSON/object validation, claim annotation model, time-status computation over an injected clock) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. The base64url decoder is implemented in-repo (not via `atob` alone, whose leniency differs) so the strictness of section 4 holds; UTF-8 decoding uses `TextDecoder` with `fatal: true`.
Security/privacy (the point of the tool): zero network, zero storage; token and decoded contents render as text only (JSON pretty-printing goes through text nodes — a claim value containing markup is inert); per-pane copy is the only clipboard path; the not-verified banner is non-dismissible in both languages; the UI MUST NOT use a green-check/"valid" presentation for the time status (status colours, if any, are neutral, with an explicit "times only — signature not verified" caption adjacent to the status line).
Bilingual and accessibility: full zh-TW (default) and English UI, including the banner, status phrases and error texts; claim names stay in their standard forms; decoded panes are labelled regions; errors are announced and tied to the input; keyboard-only operation completes decode, pane copy and clear.
Performance bounds: decode of a maximum-size token is effectively instant (<50 ms); no debouncing may delay an error for malformed input beyond the stated 200 ms. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; the section 4 fixture decodes exactly; claims table annotations (aud as list, NumericDate rows) correct; pane copy matches the display byte for byte.
- boundaries: part counts 1/2/4/5 (JWE message)/6; empty signature; padding variants; length mod 4 = 1; non-object JSON; non-NumericDate exp warning path; size cap at and over.
- privacy: zero network after load; no storage; token absent from URL/title/logs; banner present before input; clear actually empties all panes.
- security: markup-bearing claim values render inert; strict decoder rejects `+`/`/` and misplaced padding; no eval/Function; the UI contains no "valid"-style affirmation anywhere (checked by string audit of both locales).
- usability: a developer identifies why a session failed (expired vs wrong claims) within seconds; the not-verified framing is understood — a first-time user asked "is this token genuine?" answers "the tool cannot tell" (this comprehension check is part of the usability evidence).
- accessibility: labelled panes and banner, announced errors and status, keyboard-complete flow, status never conveyed by colour alone.
- localization-seo: zh-TW and en pages complete and equivalent including banner and help; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; fixture tokens in tests are the synthetic ones from section 4 plus independently generated dummies.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical decode output across browsers for the fixture set (clock pinned where relevant).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) the section 4 fixture at both pinned clocks, asserting the JSON panes, the claim annotations, the 32-byte signature and both statuses; (b) decoder strictness sweep: each error class with part/position identity, padding acceptances (0/1/2 `=`), mod-4=1 rejection, `+` and `/` rejection, UTF-8 failure (a payload part decoding to invalid UTF-8 bytes), non-object JSON (array, string), duplicate keys (last wins); (c) time-status truth table: exp only, nbf only, both, neither, non-number exp, exact-boundary equality; (d) relative-phrase unit selection at the stated thresholds; (e) JWE five-part message and other part counts; (f) whitespace and size-cap errors.
GUI/evidence tests (desktop, real browser): fixture token through the real UI in both languages with the system clock set or the evaluation time otherwise pinned and recorded; error panels screenshotted; keyboard-only completion; a string audit screenshot/search of the shipped locale files for forbidden validity wording. Timing: full core suite under 60 seconds; no network in any test; NO real token from any real system may be used in tests, screenshots or evidence — synthetic fixtures only.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
