# JWT Decoder and Claims Inspector — preparatory BRIEF v0.1

Specification documentation only; no product claim, readiness event or implementation. Full normative contract is SPEC.md.

## 1. Goal
Developers debugging authentication need to look inside a JSON Web Token — which user it names, when it expires, what scopes it carries — and the reflex is pasting it into a website, effectively handing a live credential to a third party's page and its analytics. Success: the user pastes a token and immediately sees the header and payload decoded and pretty-printed, the registered time claims (exp, iat, nbf) rendered as human local times with a plain expired / not-yet-valid / currently-valid readout relative to the device clock, and the algorithm and key id from the header — all computed locally, with a permanent, unmissable statement that the signature is NOT verified and decoded content is unauthenticated data that anyone could have forged. The tool decodes; it never trusts.

## 2. Scope and functional distinction
Compact JWS tokens of exactly three base64url parts (header.payload.signature). Decoding: strict base64url validation per part (alphabet, no padding required but tolerated exactly as specified, length rules), UTF-8 JSON parsing of header and payload, pretty printing with sorted or source-order keys per the stated rule, claim annotations for the registered claims (iss, sub, aud — including array audiences, exp, nbf, iat, jti) with NumericDate values shown as local date-time plus relative phrasing. The signature part is shown only as its encoded text and byte length; there is no verification, no key input, no JWK fetching, no algorithm implementation — and the UI must never use the words "valid token": the time readout says "not expired at the current device time" rather than "valid", a distinction the SPEC pins. Structural errors are specific: wrong part count, a part that is not base64url (naming the part and the bad character position), header/payload not JSON, JSON that is not an object, a NumericDate claim that is not a number. A token builder/encoder is excluded (this tool inspects; it does not mint tokens), as are encrypted JWEs (five parts — recognised and explained, not decoded), password/key handling of any kind, and storage or history of pasted tokens.

Existing tools: the UTF-8 Base64 Text Codec converts raw text to and from strict Base64 — it knows nothing of JWT structure, JSON claims, or NumericDate semantics; the JSON Workbench formats JSON documents. Neither assembles the three-part token model, the claim annotations, or the not-verified trust framing that defines this tool. Initial catalog/spec/task scope contains no JWT tool; fresh registry/path/draft check remains mandatory before admission. All fixture tokens are synthetic, generated for the specification with throwaway payloads and a dummy signature segment — never a real credential.
