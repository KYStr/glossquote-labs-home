# SVG to PNG Converter — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. An SVG file is markup, and markup from the clipboard is untrusted: this specification's centre of gravity is a closed sanitisation contract and an exact intrinsic-size rule set, so that what the user previews is byte-for-byte what gets rasterised, and any difference from the source file is counted and explained on the page.

## 1. Goal
Primary audience: designers and developers exporting logos and icons at exact pixel sizes, teachers and office staff putting diagrams into slides and documents, marketplace sellers whose listing tools refuse vector files, and students submitting artwork to systems that accept PNG only. The recurring problem: online converters upload the artwork to a stranger's server, add watermarks, rasterise at a size the user did not choose, or silently drop parts of the file (scripts, external images, fonts) so the PNG differs from the source with no explanation. Success is observable: the user pastes SVG markup or drops an .svg file, sees a preview rendered from the sanitised document only, is told exactly how many items sanitisation removed and why, chooses the output size by width, height or scale, optionally sets a background, and downloads a PNG whose pixel dimensions match the numbers on the page. Non-goals: editing or optimising the SVG, converting raster images (a different tool), batch conversion, JPEG/WebP output, and font embedding — the page MUST state permanently that an SVG rendered as an image cannot load page or web fonts, so text inside the artwork is drawn with locally available fonts and may differ from the author's design tool.

Assumptions: a modern desktop browser with canvas PNG export; one file at a time within the caps below; no network at runtime.

## 2. Scope and functional distinction
Included: (a) input by pasted markup (≤200,000 characters) or by file selection/drag-drop (a single .svg file, ≤2,000,000 bytes); (b) XML parsing and the intrinsic-size resolution of section 4; (c) the closed sanitisation of section 4, applied once, whose output serialisation is the single source for preview, rasterisation and the displayed SVG size facts; (d) three mutually exclusive output sizing modes — by width, by height, by scale percentage — with the rounding, floors and pre-render caps of section 4; (e) background choice: transparent (default), white, or one custom colour given as hex; (f) PNG download named `svg-converted-<W>x<H>.png` where W and H are the exact output pixel dimensions; (g) facts displayed before download: intrinsic size and how it was determined (attributes / viewBox / derived), sanitised item count by category, output dimensions, and background. Excluded: multiple files, SVG animation playback (an animated SVG rasterises at its initial state; stated, not hidden), linked external assets of any kind (they are removed by sanitisation, never fetched), and persistence.
Distinction from existing work: Image Resizer accepts raster images (PNG/JPEG/WebP) and scales an existing pixel grid; it never sees markup. This tool accepts vector markup only, so sanitisation and intrinsic-size resolution exist here and nowhere else in the catalog, and output resolution is independent of any input pixels. The SVG Dash Cycle Explorer (consumed specification) is an interactive learning tool for stroke-dash animation values, not a file converter. Print Size computes physical dimensions for printing raster images. No catalog entry, reserved specification or registry task at admission time rasterises SVG; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: an empty paste area and file drop zone, plus a built-in sample SVG (a simple three-shape badge) loaded and previewed so the sizing controls can be explored before the user trusts the tool with real artwork. Pasting markup or dropping a file runs, in order: size caps → XML parse → root check → sanitisation (count shown) → intrinsic-size resolution → preview and output-size computation. Every later edit (mode, dimension, scale, background) recomputes the output dimensions and re-renders the preview at the chosen background.
Error states are distinct and non-destructive: input over a cap (which cap, actual size shown); not well-formed XML (parser's line/column shown when available); parsed but root element is not `<svg>` in the SVG namespace (what was found instead); intrinsic size undeterminable (no usable width/height and no viewBox — section 4 rule 4); output size over a cap (computed dimensions shown, with the instruction to reduce width/height/scale); canvas export failure (browser refusal reported as-is). While an error stands there is no preview and no download — the tool never falls back to rendering the raw, unsanitised input "to be helpful". Switching input replaces the previous document completely; nothing persists across reload; artwork never appears in the URL, title or any request. The removed-items summary stays visible next to the download button whenever the count is above zero, in plain language ("removed 3 items: 1 script element, 1 event-handler attribute, 1 external reference").

## 4. Input, sanitisation and sizing rules (normative)
Parsing: the input text is parsed as XML (`image/svg+xml`). A parser error is the not-well-formed error. The document element MUST be `svg` in the SVG namespace (`http://www.w3.org/2000/svg`); an `svg` element without the namespace, or any other root, is the root error.
Sanitisation (closed; applied to the parsed document before any rendering; every removal is counted in exactly one category):
- Banned elements — removed with their subtrees, counted per element: `script`, `foreignObject`, `iframe`, `frame`, `frameset`, `embed`, `object`, `applet`, `link`, `meta`, `base`, `form`, `input`, `button`, `audio`, `video`, `source`, `track`, and any element in the XHTML namespace.
- Event-handler attributes — any attribute whose local name, lowercased, begins with `on`, on any element: removed, counted per attribute.
- References — `href` and `xlink:href` attributes: the value, trimmed, is allowed only if it begins with `#` or is a `data:image/png`, `data:image/jpeg`, `data:image/gif` or `data:image/webp` URL; any other value causes the attribute to be removed (the element stays), counted per attribute. `data:image/svg+xml` references are NOT allowed (no nested untrusted SVG).
- Style content — in `style` elements and `style` attributes: any `@import` rule is removed, and any `url(...)` whose target is not an allowed `data:image/` value of the previous rule has its declaration removed; each removed rule/declaration counts as one item.
- Nothing else is altered: sanitisation MUST NOT rewrite paths, round numbers, reorder attributes or minify; the serialised sanitised document differs from the input only by the removals above (plus XML serialisation normalisation, stated).
Rendering source: the preview and the rasteriser both load the serialised sanitised document from a `blob:` URL as an image. The raw input text MUST never be assigned to any DOM sink, and the page MUST NOT contain the input as live markup at any point.
Intrinsic size (from the sanitised root; a width/height attribute counts only if it is a plain number or a number with a `px` suffix, value > 0; any other unit or a percentage makes that attribute count as absent): (1) both width and height usable → intrinsic = (width, height); (2) exactly one usable and a viewBox present → the other dimension = usable × (viewBox cross-ratio), kept unrounded for output computation; (3) neither usable and a viewBox present → intrinsic = (viewBox width, viewBox height), i.e. 1 unit = 1 px; (4) otherwise → the undeterminable error. A viewBox with width or height ≤ 0 counts as absent. The page states which rule fired.
Output sizing: modes — width W (integer 16–8192), height H (integer 16–8192), scale P (percent, 10–1000, one decimal allowed). The unchosen dimension = chosen × (intrinsic cross-ratio), rounded half away from zero, minimum 1. Scale mode applies P/100 to both intrinsic dimensions with the same rounding. Before rendering, both output dimensions MUST be ≤ 8192 and their product ≤ 33,554,432 pixels; exceeding either is the over-cap error (no partial render, no silent clamping).
Background and rasterisation: the canvas is created at the output dimensions; if a background is chosen it is filled first (white, or the custom hex colour validated as `#RRGGBB`); the sanitised SVG image is drawn at 0,0 at the output size; the PNG is the canvas export. With transparency chosen, no fill occurs and the PNG keeps its alpha channel.
Worked fixtures (normative; sizes re-derived by script during drafting):
- F1: `<svg xmlns="http://www.w3.org/2000/svg" width="200" height="100" viewBox="0 0 200 100"><rect width="200" height="100" fill="#3366cc"/></svg>` → rule 1, intrinsic 200×100; width mode 400 → **400×200**; scale 50% → **100×50**; height mode 50 → **100×50**.
- F2: viewBox-only `<svg xmlns="…" viewBox="0 0 24 24">…</svg>` → rule 3, intrinsic 24×24; width mode 96 → **96×96**.
- F3: `width="150"` with `viewBox="0 0 300 150"` → rule 2, intrinsic 150×75; scale 200% → **300×150**.
- F4: `<svg xmlns="…"><circle r="10"/></svg>` (no size, no viewBox) → rule 4 error, no preview.
- F5 (rounding): intrinsic 3×2, width mode 100 → height = round(100 × 2/3) = round(66.67) = **67**, output 100×67.
- F6 (sanitisation): a document containing one `<script>` element, one `onclick` attribute and one `<image>` whose `href` is `https://example.com/x.png` → removed count **3** (1 element, 1 attribute, 1 reference), itemised exactly so in the summary; the remainder still renders.
- F7 (caps): intrinsic 200×100 with scale 1000% → 2000×1000 = 2,000,000 px, allowed; width mode 8192 on intrinsic 200×100 → height 4096, product 33,554,432, allowed exactly at the cap; width 8192 on a square intrinsic → 8192×8192 exceeds the product cap → over-cap error before rendering.

## 5. Implementation and safety
Architecture (future production): a pure-ish core operating on the parsed document (sanitiser returning the cleaned document plus the itemised removal counts; intrinsic-size resolver; sizing maths) with the DOM parser/serialiser behind a thin adapter; a controller; a thin DOM layer. The serialised sanitised string is kept as the single source of truth — preview image, raster image and any "copy sanitised SVG" affordance (if present) all derive from it. Runtime dependencies: none.
Privacy/security: no network at runtime, no storage, no analytics; the artwork is never fetched, uploaded or logged; external references are removed, never resolved — the tool MUST NOT fetch a URL found inside an SVG for any reason. Canvas export is safe by construction: the raster source is a `blob:` image of a document whose external references were removed, so no cross-origin taint can occur; if a browser still refuses export, that is the export-failure error, not a retry with weaker rules. No eval/Function; no external fonts or images in the page itself.
Bilingual and accessibility: full zh-TW (default) and English UI, including the font-fallback note, the removed-items summary and every error class. The preview carries an aria-label describing it as a preview of the user's SVG at the output size; all controls are native, labelled and keyboard-operable; the drop zone is also reachable and operable by keyboard via its file input; output dimensions and removal counts are ordinary text, announced on change.
Performance bounds: input caps bound parsing; rasterisation is a single draw at the capped canvas size; recompute on control changes reuses the already-sanitised document (sanitisation runs once per input, not per size change). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host (file input and paste both work from file://).

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; paste and file paths; all three sizing modes; all three background choices; downloaded PNG dimensions and content match the displayed output size and preview for every section 4 fixture.
- boundaries: caps at exactly 200,000 pasted characters / 2,000,000 file bytes and one unit over; width/height 16 and 8192; scale 10% and 1000%; the F7 product-cap boundary (exactly at cap renders, one step over errors); intrinsic rules 1–4 each exercised.
- privacy: zero network after load, including when the input SVG contains external references (they are removed, never fetched — verified in the network log); no storage; artwork absent from URL/title.
- security: the F6 document and a hostile corpus (script, foreignObject with HTML, `javascript:` href, external `<use>`, style @import) render with every vector neutralised and counted; raw input never reaches a DOM sink; canvas export succeeds on the sanitised corpus.
- usability: a designer converts a logo to a 512 px PNG without instructions and, when an item is removed, understands from the summary what was removed and why (spot-check).
- accessibility: preview aria-labelled; drop zone keyboard-operable; dimensions and removal summary as text, announced on change; labelled native controls; keyboard-complete flow.
- localization-seo: zh-TW and en pages complete and equivalent (including font note and removal summary wording); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the banned-element list and href allowlist appear once as auditable data matching section 4.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical output dimensions and removal counts for the fixture corpus across browsers (pixel-identical rasterisation is NOT required — antialiasing may differ, and the tests must not demand it).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) sizing: fixtures F1, F2, F3, F5 and F7 exactly, including the rounding rule at a constructed x.5 case; (b) intrinsic resolution: each rule 1–4, attribute-with-unit cases (`width="10mm"` counts as absent; `width="50%"` counts as absent), degenerate viewBox (zero width) counts as absent; (c) sanitiser: F6's exact itemised counts, plus one test per banned element, per attribute rule, per reference class (fragment allowed, raster data allowed, svg data refused, https refused), and style @import / external url() removal; a benign document (shapes, gradients with fragment references, text) passes through with count 0 and a serialisation equal modulo XML normalisation; (d) errors: malformed XML, wrong root, namespaceless svg, over-cap input, over-cap output — each producing its distinct error.
GUI/evidence tests (desktop, real browser): fixtures pasted and loaded via file in both languages; the sample explored; a PNG downloaded and its dimensions and a centre-pixel colour verified mechanically against the fixture (e.g. F1's PNG is 400×200 and uniformly #3366cc except antialiased edges — F1 has none); network log captured during the hostile-corpus run showing zero requests after load; the font note visible next to the download. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
