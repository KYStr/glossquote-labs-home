# Decision Wheel Random Picker — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. A picker tool lives or dies on trust, and it fails in two specific ways: a biased draw (modulo bias from a raw random integer, or worse, Math.random habits) and an animation that appears to decide the result, so users suspect the spin was steered. This specification therefore separates decision from presentation absolutely: one uniform index is drawn by a pinned rejection-sampling rule, and only then does the wheel animate to that slice.

## 1. Goal
Primary audience: friends choosing a restaurant, teachers picking a student fairly, teams ordering presentations or on-call turns, streamers and event hosts running a visible pick. The recurring problem: trivial group decisions stall, and any human pick invites "you chose your favourite". Success is observable: the user pastes or types a list of options, presses spin, watches the wheel land on one option, and can read on the page exactly how the pick was made — equal slices, a cryptographically strong uniform draw, no weights. In elimination mode the same fairness narrows a list down pick by pick until one option remains. Non-goals: deciding anything consequential (the page says the tool is for everyday low-stakes choices, not gambling, admissions, employment or anything with money or rights at stake); rigging outcomes; or storing lists.

Assumptions: a modern desktop or mobile browser with crypto.getRandomValues (universal in modern browsers; its absence is a hard error state, never a fallback to a weaker source); no network at runtime.

## 2. Scope and functional distinction
Included: (a) an options editor: a textarea, one option per line, with a live count; entries are derived by the parsing rule of section 4; (b) a wheel rendering one equal slice per active entry, labelled with the entry text; (c) a spin action performing one draw by the section 4 rule and animating the wheel to the drawn slice, then announcing the pick as text; (d) an elimination toggle: when on, each pick is removed from the active entries after being announced, the pick history lists picks in order, and when exactly one active entry remains it is announced as the "final remaining" entry (it is never drawn and never called a pick); (e) a reset action restoring the active list to the full parsed entries and clearing the history; (f) a fairness explainer stating the method in plain language (equal probability, rejection sampling, crypto source, result drawn before the animation). Excluded: weighted slices or probabilities; picking several winners at once; saving, loading or sharing lists; sound; seeded/rigged modes; editing entries mid-elimination (the editor locks while an elimination run is in progress; reset unlocks); images on slices.
Distinction from existing work: Random Groups partitions all people into groups — every participant is placed and the randomness is over the partition; this tool singles out one entry from a list and can eliminate it. Decision Matrix ranks options by weighted criteria with no randomness at all. The Dice Sum Distribution specification (another actor's) computes the exact probability distribution of dice totals and picks nothing. No catalog entry, reserved specification or registry task at admission time picks a single option uniformly from a user list; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: the editor pre-filled with four example entries （壽司 / 拉麵 / 火鍋 / 義大利麵 in zh-TW; Sushi / Ramen / Hot pot / Pasta in English), elimination off, the wheel already drawn with four equal slices, no history. Editing the list re-parses and redraws the wheel immediately (outside an elimination run); with fewer than 2 parsed entries the spin action is disabled with the reason stated as text.
Spin: the draw happens first (section 4), then the wheel animates 3–5 seconds with an ease-out rotation ending with the pointer inside the drawn slice, and the pick is announced as text and added to the history (in elimination mode the entry then leaves the wheel and the wheel redraws with the remaining entries). Under prefers-reduced-motion there is no spin animation: the wheel highlights the drawn slice immediately and the announcement is identical. Spinning while an animation is running is impossible (the control is disabled until the announcement completes).
Elimination end state: one entry remains — it is announced as the final remaining entry with its own wording, the spin action disables, and reset is offered. Reset restores the parsed list in full and clears the history in both modes.
Error states: fewer than 2 entries and more than 50 entries (the cap and the current count are stated); an entry longer than 60 characters after trimming (the offending line number is named); absence of crypto.getRandomValues (a hard error explaining the browser is unsupported — no draw is ever made from a weaker source). Nothing persists across reload; the list never appears in the URL or title.

## 4. Computation rules (normative)
Parsing: entries = the textarea's lines, each trimmed of leading/trailing Unicode whitespace, empty results dropped, in original order. An entry longer than 60 characters (counted in Unicode code points after trimming) is a validation error naming its 1-based line number in the original text. The active list must hold 2–50 entries to spin. Duplicates are kept as separate entries with separate slices — a text appearing twice has exactly twice the probability of a text appearing once, and the explainer states this rule; no deduplication ever occurs silently.
The draw (the only randomness in the tool): to pick uniformly from n active entries, repeatedly draw one unsigned 32-bit integer v from crypto.getRandomValues until v < limit, where limit = ⌊2³² ÷ n⌋ × n; the pick index = v mod n (0-based, in list order). This is exact: every index has probability precisely 1/n. Math.random, Date-based seeds, and any other entropy source are forbidden anywhere in the product. One spin consumes draws until one value is accepted; the number of rejected values is not displayed (it carries no meaning for the user) but the core exposes it for tests.
Animation mapping: the final wheel rotation MUST place the pointer within the drawn slice's arc; the rotation amount (whole turns plus the offset) is presentational and may use additional non-crypto randomness or a fixed 4-turn constant — it cannot change which slice is selected, because the slice is fixed by the draw before the animation is computed.
Elimination: after the announcement, the drawn entry (that specific occurrence, not all equal texts) is removed from the active list; history records the pick text and its pick number (1-based). When the active list reaches 1, that entry is the final remaining entry.
Worked fixtures (normative; randomness-dependent fixtures use an injected scripted byte source, which the core MUST accept as a substitutable dependency precisely so these tests are deterministic):
- W1 parsing: the text " 壽司 \n\n拉麵\n  \n火鍋 \n壽司" parses to exactly [壽司， 拉麵， 火鍋， 壽司] — 4 entries, the duplicate kept, count displayed 4.
- W2 index mapping, n = 3: limit = 4,294,967,295; the scripted value 4,294,967,295 is rejected; the next scripted value 4,294,967,294 is accepted → index 4,294,967,294 mod 3 = **2**.
- W3 index mapping, n = 6: limit = 4,294,967,292; scripted values 4,294,967,292 and 4,294,967,295 are both rejected; scripted 4,294,967,291 accepted → index = 4,294,967,291 mod 6 = **5**.
- W4 elimination: entries [A, B, C, D], scripted accepted indices [2, 0, 1] → picks in order **C, A, D**, final remaining **B**; history shows C (1), A (2), D (3) and B labelled final remaining, never as pick 4.

## 5. Implementation and safety
Architecture (future production): a pure core (parser; the draw function taking an injectable uint32 source; elimination state machine) with zero DOM access; a controller; a thin DOM layer (editor, wheel rendering by SVG or canvas with a text-equivalent list, history). The wheel's visual labels never replace text: the active entries and the result are always present as ordinary text for assistive technology. Runtime dependencies: none.
Privacy/security: no network, no storage, no analytics; option texts are rendered as text only (an entry containing markup shows as literal characters on its slice); no eval/Function; no external resources.
Honesty rules (normative, testable): the fairness explainer states the method accurately (crypto source, rejection sampling, equal slices, duplicates count separately, result drawn before the animation); no copy may claim the wheel is "provably fair" beyond that method statement, and the low-stakes note (not for gambling or consequential decisions) is permanently visible.
Bilingual and accessibility: full zh-TW (default) and English UI, including the explainer, the final-remaining wording and error messages. The spin control is a real button; the result is announced via a polite live region as text; prefers-reduced-motion removes the spin animation while keeping the identical draw; keyboard-complete flow; slice colours are decoration — entries are distinguished by their text labels.
Performance bounds: at most 50 slices; draws are single-digit in expectation (rejection probability < n/2³²). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; fixtures W1–W4 reproduced exactly through the injected source; a real spin announces one of the active entries; elimination and reset behave as specified.
- boundaries: 2 and 50 entries spin, 1 and 51 refused with counts stated; a 60-character entry accepted, 61 refused with its line number; whitespace-only lines dropped; the W2/W3 rejection values handled exactly.
- privacy: zero network after load; no storage; the option list absent from URL/title and never transmitted.
- security: an entry containing markup renders as inert literal text on slice and in history; no external resources; no eval/Function; no Math.random anywhere in the shipped code (source-audited).
- usability: a first-time user enters four lunch options and gets a pick without instructions, and can explain from the explainer why the pick is fair and what a duplicated entry does (spot-check).
- accessibility: result announced as text via live region; entries and history readable as text without the wheel; reduced-motion produces an instant, identical-in-method result; keyboard-complete.
- localization-seo: zh-TW and en pages complete and equivalent (including explainer, low-stakes note and final-remaining wording); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the parsing limits (2–50 entries, 60 characters) and the draw rule appear once as auditable constants/code matching section 4.
- compatibility: current Chrome/Edge/Firefox/Safari desktop and mobile-width layout; scripted-source fixtures give identical picks across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) fixtures W1–W4 exactly, through the injected source; (b) the draw rule: for every n in 2..50, the computed limit equals ⌊2³²/n⌋×n; a long scripted run of accepted values maps each index class for n = 3 (residues 0, 1, 2 all reachable, counts over a scripted uniform cycle exactly equal); rejection never returns an index from a rejected value; (c) parsing: trimming (including full-width spaces), blank-line dropping, duplicate retention, the 60/61-character line-number error, the 50/51-entry caps; (d) elimination state machine: an entry occurrence (not all copies) is removed — with duplicates [X, X, Y], a scripted draw of index 0 removes one X leaving [X, Y]; final-remaining triggers at exactly 1; reset restores the parsed list and clears history; (e) a distribution sanity check over the real crypto source: 60,000 draws at n = 6, each index count within a pre-declared tolerance band (e.g. ±5% of 10,000) — a smoke check only, never presented as proof of fairness (the proof obligation is the algorithm audit, not statistics).
GUI/evidence tests (desktop, real browser): a full spin observed end-to-end (wheel lands with the pointer inside the announced slice); reduced-motion emulation giving an instant result; elimination played to completion; editor lock during an elimination run; error states for 1 entry and for a 61-character line. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
