# Shoe Size Converter — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Shoe-size conversion is a domain where confident memory is worthless: the systems have different zero points and units, published tables disagree, and brands deviate from all of them. This specification therefore forbids the two easy implementations — a formula invented from the barleycorn/Paris-point relationships, and a table typed from the author's memory — and mandates a single transcribed data file with a named source, recorded row counts and a recorded SHA-256, verified at build time and spot-checked by the independent reviewer against the source. The pivot is foot length (Mondopoint millimetres); every conversion selects exactly one row and reads every system off that row.

## 1. Goal
Primary audience: shoppers buying shoes from foreign stores, parents buying kids' shoes across markets, and travellers replacing shoes abroad. The recurring problem: a "size 9" names three different lengths in three systems, the shopper's own foot length is the only system-independent fact they have, and free web converters silently mix tables from different makers, producing answers that are off by a full size with no way to tell. Success is observable: the user picks a category, enters a foot length or any one system's label, and gets all systems' labels from one table row, with the foot length the row represents, the table's source named on the page, and an honest note that brands vary and this is the generic ISO-based table. Non-goals: recommending a size to buy (fit depends on width, shape and brand — the tool converts labels, it does not fit feet), or reproducing any individual brand's chart.

Assumptions: a modern desktop or mobile browser; the user can measure a foot in centimetres or knows one system's label; no network at runtime; nothing is stored.

## 2. Scope and functional distinction
Included: (a) three categories — men, women, kids — each backed by the data file of section 4; (b) two input modes: foot length in cm (10.0–35.0, 0.1 steps), or a size label picked from selects populated from the active category's data (US, UK, EU, JP); (c) outputs: the selected row's foot length (mm and cm), and the label in each of US / UK / EU / JP for the active category, all read from that single row; (d) the provenance block of section 5 (source named, brand-variation note). Excluded: width letters and fittings; brand-specific tables; infant sizes below the kids table's first row; any interpolation, formula-based conversion or extrapolation beyond a table's first/last row (out-of-range is a stated result, never a computed guess); purchase advice.
Distinction from existing work: Unit Converter converts physical quantities by exact formula (inches ↔ cm) — shoe labels are not quantities: the offset between US and UK differs by category, EU steps are not commensurate with US half sizes, and no formula reproduces the standard table; that is precisely why this tool is table-driven with provenance instead of arithmetic. Aspect Ratio and other calculators share only generic form handling. No catalog entry, reserved specification or registry task at admission time converts shoe sizes; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: category men, foot-length mode, 27.0 cm entered, and the result already showing fixture D1's row, so the provenance block and a checked example are visible on first load. Switching category keeps the entered foot length and re-selects the row in the new category's table (labels genuinely differ by category; the foot length is the invariant). Switching to label mode offers selects whose options are exactly the active table's labels per system; choosing any label selects its row and fills the foot-length display from that row. A foot length beyond the table (above the last row, or — for the chosen category — below the first row's coverage as defined in section 4) shows the out-of-range message naming the table's covered range, with no guessed label. Results always show the row's foot length so the user can sanity-check against their own measurement. Nothing persists across reload; no value appears in the URL or title.

## 4. Computation rules (normative)
Data file (normative provenance): all tables ship in ONE data file in the tool repository, transcribed from this single named source: the conversion tables in the Wikipedia article "Shoe size" (en.wikipedia.org/wiki/Shoe_size), which reproduce the ISO/TS 19407 conversion system, as fetched on 2026-11-02. Alongside the data file, a DATA-SOURCE.md in the same repository MUST record: the source name and URL, the access date, the row count of each table, and the SHA-256 of the data file. The build MUST verify the row counts and the checksum and fail on any mismatch. A hand-typed table without the recorded checksum matching, or any row altered without updating DATA-SOURCE.md and re-verifying against the source, is a defect. The independent reviewer MUST spot-check at least five rows, including the fixture rows, against the source.
Adult table (normative shape): 22 rows, Mondopoint 215–320 mm in 5 mm steps; each row: mondo (mm), EUR, UK, US men, US women — transcribed from the source's Mondopoint conversion table (which begins 215 → EUR 34, UK 2.5, US men 3.5, US women 4.5 and ends 320 → EUR 50, UK 15, US men 16, US women 17). Category men reads the US-men column; women reads US-women; UK and EUR columns are shared. Kids table: rows keyed by Mondopoint in 5 mm steps with US kids, UK kids and EUR columns, transcribed from the same article's children's tables under the identical provenance gate; its row count is whatever the source table contains and is recorded in DATA-SOURCE.md at transcription (this specification deliberately asserts no kids label values — they enter the product only through the verified transcription).
JP label: JP = mondo ÷ 10, displayed in cm with exactly one decimal (270 → "27.0"). This is definitional (the Japanese size is the foot length in cm) and is the only computed value in the tool.
Lookup: foot length L cm → mm = L × 10 (exact tenths). The selected row is the smallest row whose mondo ≥ mm (round UP to the next size step — the ISO convention for conversions, so a converted size is never too small). Coverage: if mm > the table's last mondo, or mm ≤ (first mondo − 5) — i.e. the length rounds up past the first row's step from below the table's intended span — the result is out of range for the category. (For adults: lengths 210.1–320 mm resolve to rows; 325 mm does not.) Label lookup is exact row selection; every label in the selects exists in the table by construction.
Fixtures (transcribed from the source table at drafting; implementations MUST reproduce exactly):
- D1: men, foot 27.0 cm (270 mm, an exact row) → EU 42.5, UK 9, US 10, JP 27.0.
- D2 (round up): men, foot 26.3 cm (263 mm) → row 265 → EU 41.5, UK 8.5, US 9.5, JP 26.5.
- D3: women, label US 8 → row 245 → foot 24.5 cm, EU 38.5, UK 6, JP 24.5.
- D4: men, label EU 44 → row 280 → foot 28.0 cm, UK 10, US 11, JP 28.0.
- D5 (range): men, foot 32.5 cm (325 mm) → out of range (adult table ends at 320), no label shown; men, foot 21.0 cm (210 mm) → out of range (≤ 215 − 5); foot 21.1 cm → row 215 → EU 34, UK 2.5, US 3.5, JP 21.5.
- D6 (round trip): for every adult row, selecting by its US label, its EU label or its exact foot length selects the same row; and for any in-range foot length, converting the selected row's JP label back as a foot length (JP cm = length) selects the same row.

## 5. Implementation and safety
Architecture (future production): a pure core (row selection and readout over the loaded data tables) with zero DOM access; a controller; a thin DOM layer. The data file and DATA-SOURCE.md are part of the candidate and are hashed like code. Runtime dependencies: none; the data file is bundled at build, not fetched.
Privacy/security: no network, no storage, no analytics; there is no free text anywhere (all inputs are numeric fields or selects populated from data); no eval/Function; no external resources.
Honesty rules (normative, testable): (1) The provenance block, always visible with the results, names the table's source (ISO/TS 19407-based, via the cited article) and states that shoe sizing is not fully standardised, brands' own charts differ, and the converted label is a starting point for trying on — never a fit guarantee; the words "exact fit" or "guaranteed" MUST NOT appear. (2) Out-of-range is reported as out of range; the tool never extrapolates a label. (3) The active category is always labelled on the result (a US 10 in men is not a US 10 in women, and the page must make the category impossible to miss).
Bilingual and accessibility: full zh-TW (default) and English UI, including the provenance block and range messages. Native labelled inputs and selects; results as a real table or definition list with the category stated in text; keyboard-complete flow. Performance bounds: trivial table scans (≤ a few dozen rows). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages and categories; fixtures D1–D6 reproduced exactly, including the round-up and both out-of-range cases.
- boundaries: adult rows 215 and 320 selectable; foot 320 mm resolves, 321 mm is out of range; 210 mm out of range, 211 mm resolves to the first row; label selects contain exactly the table's labels (no orphan options).
- privacy: zero network after load (the data file is bundled); no storage; values absent from URL/title.
- security: no external resources; no eval/Function; no injectable free text exists.
- usability: a shopper converts their measured foot length and their known US size and gets consistent rows, and can state which table the answer came from (spot-check).
- accessibility: labelled native controls; category and provenance in text; results structured as a table/list with headings; keyboard-complete.
- localization-seo: zh-TW and en pages complete and equivalent (including the provenance block); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the build verifies the data file's row counts (adult exactly 22) and SHA-256 against DATA-SOURCE.md and fails on mismatch; the reviewer spot-checks ≥5 rows against the cited source, including D1 and D4 rows; Node 24.
- compatibility: current Chrome/Edge/Firefox/Safari desktop and mobile-width layout; fixtures give identical results across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) fixtures D1–D5 exactly; (b) the D6 round-trip property evaluated over every row of the shipped adult table and a sample of kids rows; (c) the round-up rule: for each adult row boundary, a length 1 mm above a row's mondo selects the next row, and a length equal to a row's mondo selects that row; (d) out-of-range at both ends for each category; (e) the checksum/count gate: the test suite itself recomputes the data file's SHA-256 and row counts and compares them with DATA-SOURCE.md, so a silent table edit fails tests even if the build gate is bypassed; (f) JP derivation: JP = mondo/10 with one decimal for every row.
GUI/evidence tests (desktop, real browser): entering 26.3 cm in men shows the 265 row with the round-up visible (the displayed foot length is the row's 26.5 cm, so the user sees the step taken); switching category at the same foot length shows the women's labels from the same row; the provenance block is visible with the results on a mobile-width viewport. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
