# Word and Character Frequency Counter — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Frequency numbers are only useful when the counting rule is fixed: this specification pins tokenisation per script, and requires the product to display the rule next to the results.

## 1. Goal
Primary audience: writers and editors checking repetition, translators and language teachers analysing texts, researchers doing quick corpus exploration, and students studying vocabulary distribution. The recurring problem: online counters each tokenise differently (especially for Chinese, where most simply split on spaces that do not exist and report garbage), hide their stopword lists, and give percentages with no stated base. Success is observable: the user pastes text and gets ranked tables whose every number can be reproduced by hand from the rules in section 4 — word counts for letter/number tokens outside the CJK classes (Latin, Greek, Cyrillic and other scripts), Han character counts and Han bigram counts for Chinese runs — with filters (stopwords, minimum count/length, numbers on/off) and a CSV export of exactly what is shown. Non-goals: word segmentation for Chinese (explained as a research problem this tool honestly sidesteps with characters+bigrams), stemming/lemmatisation, readability or sentiment scoring, file upload, and saving texts or lists.

Assumptions: a modern desktop browser; pasted text up to the cap; no network at runtime.

## 2. Scope and functional distinction
Included: (a) three tables computed from one input — Words (tokens made of Unicode letters/numbers **outside** the CJK classes defined in section 4: Latin, Greek, Cyrillic and every other script's letters and digits are in scope for this table — it is *not* a Latin-only table, and must never be labelled one), Characters (Han/kana/Hangul single characters), Bigrams (adjacent Han pairs) — with tabs or sections to switch; an input with no tokens of a kind shows that table's empty state; (b) options: stopwords toggle with an editable session list (bundled defaults shipped as data: common English function words; common Chinese particles/ pronouns as single characters for the character table), minimum count (default 1), minimum word length for the Words table (default 1), include numbers toggle (default on); (c) totals per table (total counted tokens, unique items, and the input character count); (d) CSV export of the currently displayed (filtered) table; (e) the counting rules summarised beside the results in both languages. Excluded: segmentation dictionaries, part-of-speech, collocations beyond Han bigrams, multi-document comparison, and persistence.
Distinction from existing work: Text Workbench transforms text (case, whitespace, line operations) and Text Diff aligns two texts; neither tokenises by script or counts. The Subtitle tools process timed cues. No catalog entry, reserved specification or registry task at admission time counts frequencies; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: empty input with the rules summary visible; results area shows the empty state. Pasting or typing computes on input (debounce ≤300 ms — counting is fast, but large pastes should not thrash). Changing any option recomputes from the same input; the input is never modified by the tool.
Each table shows rank, item, count, and percentage (share of that table's total counted tokens), sorted per section 4. A "show all / top 100" toggle controls display length (default top 100 with the full count of rows noted); CSV always exports the full filtered table regardless of display length. The stopword editor is a textarea prefilled with the bundled list (one entry per line); editing it recomputes; a "restore defaults" resets it for the session. Nothing persists across reload.
Size cap: 200,000 characters (code points); beyond it the input is refused with the count shown rather than truncated. Empty or token-free input shows totals of zero and empty tables — never an error.

## 4. Tokenisation and counting rules (normative)
Script runs: the input is scanned by code point and classified: Han (U+4E00–U+9FFF, U+3400–U+4DBF), kana (U+3040–U+30FF), Hangul (U+AC00–U+D7AF), word characters (any code point with the Unicode Letter or Number property that is not in the three classes above — this covers Latin, Greek, Cyrillic, Arabic, Hebrew, Devanagari and all other scripts' letters and digits alike), apostrophe `'` (U+0027) and `'` (U+2019), and everything else = separator. Consecutive same-class characters form runs; counting proceeds per the class rules, and a run boundary always ends the current token/bigram chain.
Words table (word runs): a word is a maximal sequence of word characters that may contain internal apostrophes — an apostrophe joins only when it has a word character on both sides (`don't` = one token; `'tis` → `tis`; `rock 'n' roll` → `rock`, `n`, `roll`). Hyphens and all other punctuation are separators (`well-known` = two tokens). Matching is case-insensitive under **Unicode simple case folding, which is the normative fold of this specification**: the key of a token is computed code point by code point from the simple case fold mappings (status C and F entries) of the Unicode `CaseFolding.txt` for a Unicode version the product states and ships as auditable data. Simple case folding is **not** `toLowerCase()`, and implementations MUST NOT substitute `toLowerCase()`, `toUpperCase()` or any locale-sensitive casing: the operations diverge exactly where this table needs determinism — Greek final sigma. Under simple case folding Σ (U+03A3) folds to σ (U+03C3) and ς (U+03C2) **also** folds to σ, so Σ, ς and σ are one key; under `toLowerCase()` ς maps to itself, so an implementation using it counts a different table (fixture 4 is the discriminating test). The fold is locale-independent by construction: there is no Turkish-i special case (`I` folds to `i`; İ (U+0130) has no simple fold mapping and is unchanged by the fold). The display form is the most frequent original casing of the token, ties broken by first occurrence. Pure-digit tokens (and mixed letter-digit tokens are NOT pure) are counted unless the numbers toggle is off, in which case tokens containing no letter are excluded. Minimum length applies to the folded token's code-point length.
Characters table: every Han, kana and Hangul character is one token of itself (no folding, no composition — the input is used as-is; a note states that visually identical text in different Unicode normalisation forms can count differently, and the tool does not normalise). Stopwords for this table match single characters.
Bigrams table: within a Han run of length L, the L−1 overlapping adjacent pairs, counted as two-character tokens. Runs of length 1 contribute none. Kana/Hangul do not form bigrams in this version (stated).
Stopwords: applied after tokenisation, before counting totals — a stopword token is excluded from its table entirely (totals shrink accordingly; the UI labels totals as "after filters"). Matching is exact against the folded form for words, exact character for the characters table; bigrams are filtered if either character is a stopword character (stated rule). The bundled English list and Chinese character list ship as data files in the repository and are printed in the product's help, so the defaults are auditable.
Ordering and percentages: sort by count descending, then by first-occurrence position ascending (position = index of the token's first appearance among that table's counted tokens). Ranks are sequential positions in the sorted order (1, 2, 3…; tied counts do not share a rank — the tie-break makes the order total). Percentage = count ÷ table total × 100, displayed with one decimal, rounded half away from zero; percentages of a filtered table are relative to the filtered total. CSV: header `item,count,percent`; percent as a plain number with one decimal (e.g. `30.0`); fields quoted per RFC 4180 when they contain comma/quote/newline (an apostrophe does not trigger quoting); LF line endings, final LF; filename `frequency.csv`, MIME `text/csv;charset=utf-8`.
Worked fixtures (normative): (1) Input `The cat sat. The cat ran, and the dog ran.` → Words in sorted order: the 3 (30.0%), cat 2 (20.0%), ran 2 (20.0%), sat 1 (10.0%), and 1 (10.0%), dog 1 (10.0%). Cat precedes ran among the 2-count items (first occurrence earlier), and the 1-count items order sat, and, dog by first occurrence. The folded key `the` covers occurrences `The`, `The`, `the`, so the display form is `The` (majority casing, 2 of 3). Total 10, unique 6. (2) Input `我喜歡台灣，台灣喜歡我。` → Characters: 我 2, 喜 2, 歡 2, 台 2, 灣 2 — each 20.0%, ordered by first occurrence as listed; total 10, unique 5. The punctuation breaks the Han run, so Bigrams come from each 5-character run separately (4 per run): 喜歡 2 (25.0%), 台灣 2 (25.0%), 我喜 1, 歡台 1, 灣喜 1, 歡我 1 (12.5% each) — total 8; 喜歡 precedes 台灣 among the 2-count items because its first occurrence is earlier, and there is no 灣台 bigram because the comma ends the run. (3) `don't don't DON'T` → one unique word, count 3, display form `don't` (2 of 3), folded key `don't`. (4) Greek sigma merge (the fold discriminator): `Σ ς σ ΣΣ` → Words: σ 3 (75.0%), σσ 1 (25.0%); total 4, unique 2. Under `toLowerCase()` the same input would give σ 2, ς 1, σσ 1 — a different table; that output is non-conforming. (5) Greek word casing: `ΑΒΓ αβγ Αβγ` → one unique word, folded key αβγ, count 3 (100.0%), display form `ΑΒΓ` (each casing occurs once; the tie goes to first occurrence). (6) Greek in scope: `Ω ω Ω` → one unique word, folded key ω, count 3 (100.0%). (7) Cyrillic in scope: `Ж ж Ж` → one unique word, folded key ж, count 3 (100.0%). Fixtures 6 and 7 exist to prove the Words table is not Latin-only: Greek and Cyrillic tokens are counted there, as section 2 states.

## 5. Implementation and safety
Architecture (future production): a pure core (classifier, tokenisers, counters, filters, CSV serialiser) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. Counting uses hash maps keyed by the folded token; first-occurrence indices are recorded at first sight.
Privacy/security: pasted text renders as text (table cells via text nodes — an item containing markup characters is inert); no network, no storage; the stopword edits are session-only.
Bilingual and accessibility: full zh-TW (default) and English UI, including the rules summary and help (the CJK explanation is written natively in both, not translated word-for-word into nonsense); tables are real tables with headers; option controls are native and labelled; keyboard-only operation completes everything.
Performance bounds: a 200,000-code-point input counts in <500 ms and renders the top 100 rows without layout thrash; the full table is available via the toggle and CSV. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all three tables (the Words table demonstrably counting Greek and Cyrillic tokens — fixtures 5–7 — not only Latin); the normative simple case fold applied as the token key, including the Σ/ς/σ merge of fixture 4; option combinations (stopwords on/off + edited, min count/length, numbers); CSV matches the filtered table exactly.
- boundaries: cap at 200,000 and one over; empty and separator-only input; single Han character (no bigrams); apostrophe edges (`'tis`, trailing apostrophe); hyphen splitting; astral characters in separators.
- privacy: zero network after load; no storage; pasted text absent from URL/title; stopword edits discarded on reload.
- security: markup-bearing items render inert; no external resources; no eval/Function.
- usability: a writer finds their most repeated word and a teacher the most common character without instructions; the Chinese character/bigram explanation is understood on first read (spot-check).
- accessibility: real tables with headers, labelled controls, keyboard-complete flow, totals and empty states in text.
- localization-seo: zh-TW and en pages complete and equivalent; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; bundled stopword lists ship as auditable data and match the help text; the simple case folding table ships as auditable data derived from a stated Unicode `CaseFolding.txt` version, and the fold demonstrably is not `toLowerCase()` (fixture 4 passes, which a `toLowerCase()` build cannot do).
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical counts for the fixture corpus across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) the seven section 4 fixtures exactly, including ordering, display forms and percentages; (b) tokeniser sweep: apostrophe joins/boundaries, hyphen split, digits with numbers on/off, mixed-script run boundaries (a Han character inside an English sentence starts its own run and breaks the word token), kana/Hangul character counting, Greek and Cyrillic tokens landing in the Words table (fixtures 6, 7); (c) filters: stopword removal shrinking totals, bigram filter rule (either character), minimum length/count; (d) tie-breaking by first occurrence with equal counts; (e) CSV serialisation including an item containing a comma (from a stopword-edited… items cannot contain commas by construction — the CSV test instead covers an apostrophe item and asserts no spurious quoting) and the final LF; (f) case folding, with expected outputs stated so two implementers cannot diverge: fixture 3 (majority display form), fixture 4 (Σ/ς/σ merge — asserted as the discriminating test that a `toLowerCase()`-based build fails), fixture 5 (Greek word, first-occurrence casing tie-break), fixtures 6 and 7 (Ω and Ж keys).
GUI/evidence tests (desktop, real browser): fixtures pasted through the real UI in both languages; a 200,000-character paste completing within the stated bound; CSV downloaded and diffed against the on-screen filtered table. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
