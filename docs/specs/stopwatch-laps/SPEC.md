# Stopwatch with Laps — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. A lap stopwatch has one quiet cheat available to it: timing each lap with its own start/stop readings, so rounding and clock behaviour make the laps fail to add up to the split total. This specification forbids that. There is exactly one time base and one stored list of split readings; every lap duration, statistic, display and export is derived from that list, so the parts always sum to the whole and two views of the same run can never disagree.

## 1. Goal
Primary audience: runners and cyclists doing interval sessions, coaches with a clipboard, teachers timing rotating group activities, speedcubers and anyone who times repeated rounds of the same task. The recurring problem: a simple elapsed timer answers "how long overall" but not "which round was fastest, and are the rounds getting slower" — the per-lap structure is the information, and reconstructing it afterwards from memory or video defeats the purpose. Success is observable: the user starts the stopwatch, presses Lap at each round, and immediately sees a table of laps with each lap's duration and cumulative split, the fastest and slowest laps marked, and the average lap; pausing for a break does not pollute the timing; at the end the table exports to CSV for a log. Non-goals: counting down to a deadline, sounding cues, recording sessions across visits, or sensing anything — the user presses the buttons.

Assumptions: a modern desktop or mobile browser; millisecond timing is adequate (the display shows centiseconds); no network at runtime; nothing is stored.

## 2. Scope and functional distinction
Included: (a) one stopwatch with states idle, running and paused, driven by the monotonic rule of section 4; (b) Start/Pause/Resume/Reset controls and a Lap control enabled only while running; (c) a lap table (lap number, lap duration, split) in press order, up to 500 laps; (d) statistics over completed laps: fastest lap, slowest lap, average lap, under the exact rules of section 4; (e) a current-lap readout (time since the last split) while running or paused; (f) CSV export of the lap table under the exact format of section 4; (g) keyboard shortcuts (section 5) in addition to buttons. Excluded: countdown mode, alarms or audio; multiple simultaneous stopwatches or athletes; saved sessions, history or accounts; GPS, motion or any sensor input; rounding the display upward (section 4 truncation is normative).
Distinction from existing work: Focus Timer counts *down* toward a target duration and structures work/break intervals in advance; this tool counts *up* from zero and derives its structure from lap presses after the fact — opposite direction, different state machine, different outputs. Metronome emits audio clicks on a schedule; nothing here emits sound or schedules anything. Meeting Cost Calculator's timer mode accumulates elapsed time to multiply it by a burn rate; it has no lap concept and no per-lap statistics — the shared monotonic-clock discipline is a technique, not a feature overlap. Typing Speed Test times one fixed attempt and scores text; it has no laps and no export of timings. No catalog entry, reserved specification or registry task at admission time provides a lap stopwatch; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: idle, main display 00:00.00, lap table empty, statistics area hidden, Lap disabled, Start enabled. Start moves to running: the display advances on the monotonic base and Lap enables. Pressing Lap appends a row (number, derived duration, split) and the statistics appear/update; the main display keeps running — a lap press never pauses or resets anything. Pause freezes the display at the exact elapsed; while paused, Lap is disabled (a lap at a frozen reading would create a zero-length or duplicated split — refused by state, not by an error message). Resume continues from the frozen elapsed; the paused interval never counts. Reset — available in any state — returns to the initial state, clearing all laps and statistics; Reset while running stops the clock (it does not keep running in the background). Reaching 500 laps: the 501st Lap press is refused with a visible note that the lap limit is reached; the stopwatch itself keeps running and all existing laps remain exportable. Export is available whenever at least one lap exists, in any state, and downloads the CSV of section 4. Closing or reloading discards everything; nothing persists, nothing appears in the URL or title.

## 4. Computation rules (normative)
Time base: a monotonic clock (performance.now() in production; an injected fake clock in tests), read in milliseconds as a real number and stored from the segment rule below. Wall-clock (Date.now) MUST NOT be used: a wall-clock change during a run MUST NOT change any reading.
Elapsed model: the stopwatch stores `accumulatedMs` (sum of completed running segments, as an exact value) and, while running, `segmentStart` (the clock reading at the last Start/Resume). Elapsed at any instant = accumulatedMs + (now − segmentStart) while running, else accumulatedMs. Pause adds the current segment into accumulatedMs and clears segmentStart. All split readings are elapsed values, recorded as whole milliseconds by truncation (floor) of the elapsed value at the press instant.
Laps: on a Lap press while running, split_n = floor(elapsed). Lap duration d_n = split_n − split_(n−1), with split_0 = 0. Invariant (MUST hold and be property-tested): Σ_{i=1..n} d_i = split_n exactly. Two laps pressed within the same millisecond produce d = 0 for the later lap; a zero lap is legal, is listed, and participates in statistics (it can be the fastest).
Display format: a duration of T whole milliseconds displays as `MM:SS.cc` when T < 3,600,000 and `H:MM:SS.cc` when T ≥ 3,600,000, where cc = floor((T mod 1000) / 10), SS and MM are the whole seconds and minutes components, H is whole hours with no upper bound and no leading zero, MM/SS/cc are two digits zero-padded. Truncation is normative: 59,999 ms displays 00:59.99; 60,000 ms displays 01:00.00; rounding to nearest is a defect.
Statistics (over completed laps only; the in-progress lap is NEVER included): fastest = lap with minimal d_n; slowest = lap with maximal d_n; ties for either go to the earliest lap number. Average lap = split_n ÷ n computed exactly (rational), where n is the lap count — equivalently the mean of the d_i. Statistics display uses the same truncation format. With one lap, fastest = slowest = average = that lap. The current-lap readout = elapsed − split_n (or elapsed when no laps), formatted identically, and labelled as in progress.
CSV export: UTF-8 text, LF line endings, exactly: header line `Lap,Lap Time (s),Split Time (s)`, then one line per lap in number order: lap number, lap duration in seconds with exactly three decimal places (from the integer d_n: e.g. 45450 → `45.450`), split in seconds with exactly three decimal places. A final trailing newline after the last row. No other columns, no totals row.
Fixtures (independently derived; implementations MUST reproduce exactly):
- L1 (laps): splits pressed at elapsed 30,000 / 75,450 / 120,000 ms give d = 30,000 / 45,450 / 44,550 ms; Σd = 120,000 = split_3; fastest = lap 1 (30,000); slowest = lap 2 (45,450); average = 40,000 ms exactly, displaying 00:40.00.
- L2 (format): 0 → 00:00.00; 61,234 → 01:01.23; 59,999 → 00:59.99; 60,000 → 01:00.00; 3,723,456 → 1:02:03.45.
- L3 (pause): run 10,000 ms, pause for a 60,000 ms clock advance, resume and run 5,000 ms → elapsed 15,000 ms; a split pressed then reads 15,000.
- L4 (tie): two laps of exactly 20,000 ms each → fastest = lap 1, slowest = lap 1, average = 20,000 ms.
- L5 (CSV): L1's laps export exactly:
  `Lap,Lap Time (s),Split Time (s)` / `1,30.000,30.000` / `2,45.450,75.450` / `3,44.550,120.000` (each line LF-terminated).

## 5. Implementation and safety
Architecture (future production): a pure core (elapsed model, lap derivation, statistics, formatting, CSV serialisation) over an injected clock, with zero DOM access; a controller; a thin DOM layer. The 500-lap bound and format rules appear once as auditable constants matching section 4. Runtime dependencies: none.
Privacy/security: no network, no storage, no analytics; lap data never leaves the page except in the user-triggered CSV download; no user text exists to inject (all displayed values are numbers the core produced); no eval/Function; no external resources.
Honesty rules (normative, testable): the display truncates and the page states its resolution plainly (centisecond display from millisecond timing) — it MUST NOT claim photo-finish or officiating accuracy; average and extremes are defined over completed laps only and labelled as such; a paused interval is never presented as timed.
Bilingual and accessibility: full zh-TW (default) and English UI, including the lap table headers, statistics labels and the lap-limit note. Native labelled buttons; the lap table is a real table with headers; fastest/slowest marking is text (a label), not colour alone; the running display does not use a live region that announces continuously (updates announced on lap, pause and reset only). Keyboard: Space toggles start/pause, L records a lap while running, R resets — with the shortcuts listed on the page, and Space MUST NOT trigger when focus is in a button's native activation in a way that double-fires (the controller handles the focused-button case explicitly). Performance bounds: a display refresh at most every 10 ms of clock time is sufficient for centisecond display; 500 laps of arithmetic per press is trivial. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; fixtures L1–L5 reproduced exactly, including the statistics, the pause case and the byte-exact CSV.
- boundaries: lap 500 accepted, 501st refused with the note while timing continues; Lap refused while paused and while idle; Reset from every state returns to the initial state; a zero-millisecond lap is listed and can be fastest; elapsed crossing one hour switches format exactly at 3,600,000 ms.
- privacy: zero network after load; no storage; timings absent from URL/title and never transmitted except the user's own CSV download.
- security: no external resources; no eval/Function; the CSV contains only core-produced numbers and the fixed header.
- usability: a coach times three laps and reads off the fastest lap without instructions (spot-check); the in-progress lap is visibly distinct from completed laps.
- accessibility: labelled native controls; real table with headers; fastest/slowest conveyed by text labels, not colour alone; no continuous live-region announcements; keyboard shortcuts complete the whole flow and are listed on the page.
- localization-seo: zh-TW and en pages complete and equivalent (including table headers, statistics labels and the limit note); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the lap bound and format rules appear once as auditable constants matching section 4; the core demonstrably uses the injected monotonic clock (a faked wall-clock jump in tests changes nothing).
- compatibility: current Chrome/Edge/Firefox/Safari desktop and mobile-width layout; fake-clock fixtures give identical readings across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) fixtures L1–L5 exactly; (b) the sum invariant as a property test over scripted random split sequences (including repeated splits producing zero laps); (c) the pause/resume state machine on the fake clock: multiple segments summing exactly, pause spanning a large fake interval, reset while running and while paused, lap attempts in idle and paused states refused; (d) format unit tests at every L2 value plus 3,599,999 → 59:59.99 and 3,600,000 → 1:00:00.00; (e) tie-breaking for fastest and slowest; (f) the 500-lap bound and the 501st refusal.
GUI/evidence tests (desktop, real browser): a real run of ~65 seconds with two laps compared against a reference clock within one display centisecond of tolerance for human press latency, with the derivation invariant exact; keyboard-only flow (start, lap, pause, reset) completed; CSV downloaded and byte-compared against the expected fixture text. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
