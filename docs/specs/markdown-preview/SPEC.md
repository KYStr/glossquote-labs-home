# Markdown Preview and HTML Export — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The renderer is a stated subset of Markdown following CommonMark semantics where included, with every deviation listed in the deviations table in section 4; the page MUST link that subset list in its help text so users are never surprised by an unsupported construct silently rendering wrong.

## 1. Goal
Primary audience: writers, students, engineers and support staff drafting READMEs, notes, documentation and posts in Markdown. The recurring problem: online previewers send the draft to a server, surround it with ads, and each renders edge cases differently, so the user cannot trust that what they see is what a reader gets — and there is no clean way to hand someone a single finished HTML file. Success is observable: the user types or pastes Markdown, sees a live preview produced by the exact block/inline rules of section 4, checks character and word counts, and downloads one standalone HTML file that renders identically when opened offline, with a stylesheet inlined and zero external requests. Non-goals: server rendering, cloud saving, accounts, collaboration, PDF export, diagram/math/footnote extensions, emoji shortcodes, and executing or embedding any raw HTML from the source.

Assumptions: a modern desktop browser; drafts are user-supplied text; no network at runtime; the exported file is opened in a browser by its recipient.

## 2. Scope and functional distinction
Included: (a) a two-pane editor/preview with live rendering (debounce ≤200 ms) and toggleable proportional scroll synchronisation; (b) the block constructs: ATX headings 1–6, paragraphs, fenced code blocks, blockquotes, unordered/ordered/task lists, thematic breaks, pipe tables with column alignment; (c) the inline constructs: code spans, emphasis (asterisk and underscore forms per section 4), strong, strikethrough, inline links and images, full reference links, angle autolinks, backslash escapes, hard and soft line breaks; (d) counts: source characters, and rendered-text word count under the stated CJK-aware rule; (e) copy-HTML of the preview body markup; (f) download of a standalone HTML document (inlined fixed stylesheet, title from the first heading); (g) loading a bundled sample document only on an explicit button click; (h) clear control.
Excluded: raw HTML execution (source HTML is escaped and visible as text), setext headings, collapsed/shortcut reference links, bare-URL autolinking, footnotes, tables with merged cells, nested tables, syntax highlighting (code is plain with an optional language class), HTML export templates beyond the one fixed house style, and any fetching of remote images at preview time by the tool itself beyond what the browser does for an `<img>` the user included — the preview MUST set `referrerpolicy="no-referrer"` on images and the help text MUST warn that image URLs in a draft are requested by the browser when previewed.
Distinction from existing work: Text Workbench cleans and counts plain text but parses no structure. Template Merge substitutes placeholders; it does not parse Markdown or sanitise output. The UTF-8 Base64 codec converts encodings. None renders a document format into sanitised HTML with a standalone-file export. No catalog entry, reserved specification or registry task at admission time implements a Markdown previewer; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: empty editor, empty preview showing a one-line hint, counts at zero, export disabled while the document is empty. The sample button replaces the editor content with the bundled sample (after an inline confirmation if the editor is non-empty).
Typing re-renders the preview from scratch (no incremental patching) after the debounce; render failure is impossible by construction — malformed Markdown degrades to literal text per the grammar, never to an error page. The single error state is the size limit: above 200,000 source characters the preview freezes at the last valid render, an error banner names the limit and current size, and export/copy are disabled until the text is shortened.
Scroll sync: when enabled, scrolling either pane sets the other pane's scroll position to the same fraction of its scrollable height (proportional, not line-mapped); the control is a toggle, default on for the preview following the editor.
Copy HTML copies exactly the serialised preview body markup (the same markup the export embeds). Export downloads the standalone document of section 4. Leaving or reloading discards the draft; nothing is stored. Repeated export of unchanged text is byte-identical.

## 4. Grammar, safety rules and exact output
Line handling: input is split on CRLF, CR or LF (normalised to LF). Tabs in indentation expand to 4-column stops for block structure decisions.
Block grammar (normative, applied in this priority order per line group): fenced code block — a line starting with up to 3 spaces then ≥3 backticks or ≥3 tildes opens it; the info string's first word is the language label; it closes at a fence of the same character and at least the same length, or at end of input (unclosed fence is not an error); content is verbatim, escaped, no inline parsing. ATX heading — up to 3 spaces, 1–6 `#`, then a space or end of line; optional closing `#` run stripped; content parsed inline. Thematic break — up to 3 spaces, then ≥3 of the same `-`, `*` or `_` with only spaces between. Blockquote — lines prefixed by up to 3 spaces, `>`, optional space; content parsed recursively as blocks; lazy continuation lines (no `>`) belong to the quote's current paragraph. List — unordered markers `-`, `+`, `*`; ordered markers 1–9 digits followed by `.` or `)`; item content indented to the marker's content column; nested lists by further indentation; a task item is an unordered item whose content begins `[ ] ` or `[x] `/`[X] ` and renders a disabled checkbox. Table — a header line containing `|`, immediately followed by a delimiter line of cells matching `:?-{1,}:?` separated by `|`; alignment from the colons (left/right/center/none); body rows follow until a blank line or another block; cells are trimmed, inline-parsed, and rows with fewer cells are padded empty, extra cells dropped — both stated, not errors. Paragraph — consecutive lines not starting another block; ends at a blank line or an interrupting block (headings, fences, quotes, thematic breaks and lists interrupt paragraphs; tables do not interrupt — a table is only recognised at a block boundary).
Inline grammar (normative): backslash before ASCII punctuation yields that literal character. Code span — a run of n backticks matches a closing run of exactly n; content has newlines folded to spaces, and one leading/trailing space is stripped when the content both starts and ends with a space and is not all spaces; no parsing inside. Emphasis — `*`/`**`/`***` and `_`/`__` per CommonMark delimiter-run rules restricted to these: intraword underscore does NOT create emphasis (`a_b_c` stays literal); `***` renders `<em><strong>`. Strikethrough — `~~text~~` renders `<del>`, single `~` is literal. Link — `[text](destination "title")` with destination either `<...>` or a run of non-space characters with balanced parentheses one level deep; text is inline-parsed. Reference link — `[text][id]` with a definition `[id]: destination "title"` appearing anywhere in the document (definitions produce no output; matching is case-insensitive with internal whitespace collapsed); an undefined reference renders as literal source text. Image — `![alt](destination "title")`; alt is the plain-text rendering of the label. Autolink — `<https://…>`, `<http://…>` and `<email>` forms only. Hard break — a line ending with two or more spaces or a single backslash renders `<br>`; a soft break renders a newline in the HTML source.
Deviations from full CommonMark (complete list): setext headings unsupported (a `===`/`---` line under a paragraph is a paragraph continuation or thematic break by the rules above); raw HTML blocks/inline HTML escaped, never executed; collapsed `[text][]` and shortcut `[text]` reference links unsupported (literal text); bare URLs are not autolinked; HTML entities in source are passed through only for the named set `&amp; &lt; &gt; &quot; &#39; &nbsp;` and numeric character references, other `&name;` sequences render literally — each deviation is restated in the page help.
Safety rules (correctness properties, not guidelines): all source text reaches the output only as escaped text or escaped attribute values (`& < > " '` escaped in attributes; `& < >` in text). URL scheme whitelist for links: `http`, `https`, `mailto`, plus relative destinations and `#fragment`; any other scheme (including `javascript:`, `data:`, `vbscript:`, case/whitespace-obfuscated variants — the check runs after trimming ASCII whitespace/control characters and lowercasing the scheme) causes the link to render as its text only, with no `<a>` element. Images: schemes `http`, `https` and relative only; a blocked image renders as its alt text only. No element in the output may carry event-handler attributes, `style` attributes from source, or `id` attributes from source. Generated heading `id`s are NOT emitted in this version.
Rendering target: the preview DOM is built from the same serialised HTML string that copy/export produce (single source of truth): the string is generated by the pure core with the escaping above, then assigned once to the preview container. Because the string is fully escaped by construction, this is safe; the core MUST have a test proving the hostile fixture below produces no executable markup.
Standalone export: `<!DOCTYPE html>`, `<html lang="…">` matching the active UI language, `<meta charset="utf-8">`, `<meta name="viewport" …>`, `<title>` = plain text of the first ATX heading, or `Markdown document` / 在地化等價字串 when none, then the fixed house stylesheet inlined in `<style>` (the stylesheet is a versioned constant shipped in the repository; its content is part of the candidate under review), then `<body>` + preview markup + `</body></html>`. Filename: `markdown-<yyyymmdd>-<hhmmss>.html` in local time, containing no document content.
Counts: source characters = Unicode code points of the editor text. Rendered words = (count of CJK ideograph/kana/hangul characters in the rendered plain text) + (count of maximal non-whitespace runs containing at least one non-CJK character). Both update on every render.
Normative fixtures: `# Title` ⇒ `<h1>Title</h1>`; `a_b_c` ⇒ literal underscores; `**b** and ~~s~~` ⇒ `<strong>b</strong> and <del>s</del>`; a table with `|:--|--:|` ⇒ left/right aligned columns; source `<script>alert(1)</script>` ⇒ the escaped text, visible in preview as text; `[x](javascript:alert(1))` ⇒ the text `x` with no link; `- [ ] todo` ⇒ a list item with a disabled unchecked checkbox.

## 5. Implementation and safety
Architecture (future production): a pure core (block parser → AST, inline parser, HTML serialiser with escaping, plain-text extractor for counts, export builder) with zero DOM access; a controller (debounce, scroll sync, counts); a thin DOM layer. Runtime dependencies: none. A vendored Markdown library is NOT used: the subset is implemented in-repo so behaviour matches section 4 exactly, and the fixture suite is the contract.
Privacy: no storage, no network calls by the tool; the draft exists only in page memory; export/copy are user-gesture Blob/clipboard operations with object URLs revoked. The image-referrer rule and warning of section 2 are part of this privacy contract.
Bilingual and accessibility: full zh-TW (default) and English UI; the editor is a labelled `<textarea>` with a monospace font toggle-free presentation; the preview region is labelled and announced as updated only via a polite summary ("preview updated", never reading the document aloud); all controls keyboard reachable; the subset/deviation help is part of both languages' pages.
Performance bounds: rendering the maximum 200,000-character document completes within 300 ms on a mid-range laptop; pathological nesting (e.g. 10,000 unmatched `[`) MUST NOT cause exponential behaviour — the inline parser is specified as a single-pass delimiter-stack algorithm with linear-time behaviour, and a stress fixture is mandatory in section 7. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; every section 4 construct renders per the fixtures; counts follow the stated rule; copy and export produce the specified bytes.
- boundaries: 200,000-char limit behaviour; unclosed fence; empty document; table row cell-count mismatches; undefined reference; deeply nested lists/quotes.
- privacy: zero tool-initiated network requests; no storage; image referrer policy present; draft absent from URL/title/filename.
- security: hostile fixtures (script tags, event attributes, javascript:/data: URLs, obfuscated schemes) produce inert output; escaping proven by the core test suite; no source-derived attributes.
- usability: a first-time user writes, previews and exports without instructions; the deviation list prevents silent-surprise rendering; frozen-preview error state is understandable.
- accessibility: labelled editor and preview, keyboard-complete flow, polite non-reading announcements, visible focus.
- localization-seo: zh-TW and en pages complete and equivalent including help/deviations; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; fixture suite is the section 4 set plus independently derived additions.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; the exported file renders the same opened from file:// in each.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) a fixture file of input→HTML pairs covering every construct and every deviation in section 4, including all normative fixtures verbatim; (b) the hostile-input suite: script blocks, inline event attributes, obfuscated `java\tscript:` and mixed-case schemes, `data:text/html` images, attribute-breakout quotes in titles — every expectation is inert output; (c) delimiter edge cases: unmatched `*`, `**a*`, intraword underscores, code spans with multiple backtick runs; (d) table alignment/padding/dropping; (e) counts fixtures mixing CJK and Latin text; (f) export byte-determinism across two runs with a frozen clock; (g) the linear-time stress fixture (10,000 unmatched brackets, 5,000 nested emphasis openers) completing within the stated bound.
GUI/evidence tests (desktop, real browser): type the sample document and compare preview/export against opening the exported file standalone; scroll-sync behaviour; limit error state; keyboard-only completion; both languages screenshotted. Timing: full core suite under 60 seconds; no network in any test (image fixtures use relative placeholder paths that 404 harmlessly or data-free local files).
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
