# Classical Cipher Lab — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. A cipher teaching tool has one honesty obligation above all others: it must never let a user walk away believing a two-thousand-year-old shift cipher protects anything. This specification therefore makes the educational warning a permanent, non-dismissible part of the page, bans the vocabulary of real security from the product's own claims, and pins the transformation rules down to the letter — alphabet, case, key advancement — so the fixtures, including the canonical Vigenère example, are reproducible exactly and two conforming implementations can never disagree.

## 1. Goal
Primary audience: students meeting cryptography for the first time, puzzle and CTF hobbyists decoding a classical cipher they were handed, and teachers demonstrating why key space and structure matter. The recurring problem: online cipher widgets disagree with each other in the small print (does the key advance on spaces? is the text forced to uppercase? what happens to digits?), so a learner cannot check their handwork, and many present the result with the word "encrypt" and no warning, inviting real misuse. Success is observable: the user picks a cipher, enters text (and a shift or key where applicable), and gets the transformed text under the exact rules of section 4; for a Caesar ciphertext they can open the brute-force table and read all 25 candidate decryptions; and the educational banner is visible throughout. Non-goals: protecting information (explicitly), analysing modern ciphertext, or recovering anyone's password.

Assumptions: a modern desktop or mobile browser; the user understands the output is only as private as the page they typed it on — the page itself stores and transmits nothing; no network at runtime.

## 2. Scope and functional distinction
Included: (a) Caesar: shift 0–25, encrypt and decrypt directions; a ROT13 preset button that sets Caesar/shift 13 (the same engine — ROT13 encrypt and decrypt are the same operation, and the UI may say so); (b) the Caesar brute-force table: for the current input, the 25 decryptions at shifts 1–25, one labelled row per shift, unranked, with no "most likely" marking; (c) Atbash (no parameters); (d) Vigenère: key of 1–64 ASCII letters, encrypt and decrypt; (e) copy-result and swap (output becomes input) actions; input limit 10,000 characters with the count shown. Excluded: any modern algorithm (AES, ChaCha, RSA, hashing — the banner names the category as what this tool is not); frequency analysis, chi-squared scoring or any automatic plaintext detection; Beaufort and autokey variants; file input/output; key storage; any password feature.
Distinction from existing work: Password Generator exists to *create* secrets using a CSPRNG and to estimate their strength; it never transforms a user's message and never pretends a deterministic classical rule is a safeguard — this tool does the inverse job (deterministic transformation of supplied text, with an explicit not-for-security warning) and the two must not borrow each other's language. JWT Decoder and the UTF-8 Base64 Text Codec decode modern structured formats for inspection; neither performs a keyed transformation, and base64 is an encoding, not a cipher — this tool's own text says the same about its ciphers vs real encryption. Morse Code Translator maps letters to a public signalling code with no key and no secrecy concept. No catalog entry, reserved specification or registry task at admission time implements classical ciphers; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: Caesar selected, shift 3, encrypt direction, input prefilled with the worked example "Hello, World!" and the output already showing fixture V1's result, with the educational banner above the work area. Switching cipher preserves the input text and recomputes the output; switching direction likewise. The brute-force table is a separate view for Caesar mode: it lists all 25 rows for the current input (interpreted as ciphertext), each row labelled "shift N" with its candidate text, and clicking a row copies that candidate into the output area — it never replaces the input automatically. Vigenère with an empty key or a key containing any non-letter character is a field error naming the problem (outputs freeze, marked out of date); the key is never silently stripped or truncated. Text beyond 10,000 characters cannot be entered (paste is truncated at the limit with a visible note, matching the house text-tool behaviour). The banner is present in every mode and both languages and cannot be dismissed. Swap exchanges input and output for a round-trip check. Nothing persists across reload; text and key never appear in the URL or title — a key in a URL would leak it into history and logs, and is forbidden as a design rule, not just an implementation detail.

## 4. Computation rules (normative)
Alphabet and passthrough: the transformable alphabet is exactly ASCII A–Z and a–z. A letter's case is preserved individually. Every other character — digits, spaces, punctuation, and all non-ASCII characters including CJK — passes through unchanged at its original position. All operations are defined per character over Unicode code points for passthrough purposes (an astral character passes through whole, never as surrogate halves).
Caesar: for shift s (0–25), encrypt maps letter index x → (x + s) mod 26 within its case; decrypt maps x → (x − s) mod 26. Shift 0 is legal and returns the input unchanged (the UI labels it "no change"). ROT13 = s 13, an involution.
Atbash: x → 25 − x within its case; an involution with no parameters.
Vigenère: the key is normalised to uppercase; its letters give shifts k_j = index of the j-th key letter (A = 0). A key-position counter starts at 0 for each operation and advances ONLY when a letter is transformed — passthrough characters do not consume key material (normative; the alternative convention is the single largest source of inter-tool disagreement and is a defect here). Encrypt: x → (x + k) mod 26; decrypt: x → (x − k) mod 26, k taken from the counter's current key letter, cycling with period = key length.
Brute-force table: row N (N = 1..25) shows the Caesar decryption of the input at shift N, under the same alphabet/case/passthrough rules. All 25 rows are always present, in shift order, unranked.
Fixtures (independently derived; implementations MUST reproduce exactly):
- V1: Caesar encrypt, shift 3, "Hello, World!" → "Khoor, Zruog!". Decrypt of the result at shift 3 returns the input.
- V2: ROT13 "Hello" → "Uryyb"; ROT13 applied again → "Hello".
- V3: Atbash "Abc XyZ" → "Zyx CbA".
- V4: Vigenère encrypt, key LEMON, "ATTACKATDAWN" → "LXFOPVEFRNHR" (the canonical literature example); decrypt returns the input.
- V5 (key advancement): Vigenère encrypt, key KEY, "HELLO, WORLD" → "RIJVS, UYVJN" — the comma, space do not advance the key; an implementation that advances on every character gives a different string and is defective.
- V6 (passthrough and case): Caesar shift 1, "Attack at 6:30, 代號!" → "Buubdl bu 6:30, 代號!" (digits, punctuation and CJK unchanged; case preserved).
- V7 (brute table): input "Khoor", the shift-3 row reads "Hello"; the table has exactly 25 rows labelled 1–25.

## 5. Implementation and safety
Architecture (future production): a pure core (the four transforms and the table generator) with zero DOM access; a controller; a thin DOM layer. Bounds (10,000 characters, key 1–64, shift 0–25) appear once as auditable constants matching section 4. Runtime dependencies: none.
Privacy/security: no network, no storage, no analytics; input text and key never leave the page, never enter the URL/title, and are never logged; output is rendered as text (the transformed text can contain markup characters from the input and MUST be escaped); no eval/Function; no external resources. Note the boundary honestly: the tool's own safety comes from locality, and the page does not claim the ciphers add any.
Honesty rules (normative, testable): (1) The educational banner, non-dismissible and present in all modes and both languages, with this content: these are classical ciphers from before modern cryptography; they can be broken in seconds and must never be used to protect real information; for real security use modern, reviewed encryption. (2) A string audit in the test suite searches both locales for forbidden self-descriptions — "secure", "protect", "safe encryption", "military-grade" and their zh-TW equivalents — outside the banner's negations, and fails on any hit. (3) The brute-force table is never labelled with a "best" or "most likely" candidate. (4) The word "encrypt" is used only in the classical sense the banner defines; the page never offers a "strength" score for a cipher or key.
Bilingual and accessibility: full zh-TW (default) and English UI, including the banner, the table's shift labels and the key-error messages. Native labelled inputs and selects; output as selectable read-only text; the 25-row table is a real table; keyboard-complete flow. Performance bounds: 25 × 10,000 character transforms at most per table render — trivial; no debouncing tricks that show stale output as current. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages and all operations; fixtures V1–V7 reproduced exactly, including the canonical Vigenère example and the key-advancement case.
- boundaries: shift 0 and 25 accepted; key of 1 and 64 letters accepted, 65 refused; key with a digit or space refused with the named error (not stripped); input at 10,000 characters works, the 10,001st is refused/truncated with the note; empty input produces empty output, not an error.
- privacy: zero network after load; no storage; text and key absent from URL/title and never transmitted or logged.
- security: input containing markup renders inert in both the output and the brute-force table; no external resources; no eval/Function.
- usability: a student encrypts a sentence, decrypts it back with swap, and finds the plaintext row in the brute table for a classmate's shift-3 message, without instructions (spot-check).
- accessibility: labelled native controls; real table for the brute-force view; banner is readable text; keyboard-complete flow.
- localization-seo: zh-TW and en pages complete and equivalent (including banner and error texts); page titles/descriptions describe a learning tool and use no forbidden security vocabulary; correct lang attributes and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; bounds appear once as auditable constants matching section 4; the section 5 string audit runs in the build's test suite; Node 24.
- compatibility: current Chrome/Edge/Firefox/Safari desktop and mobile-width layout; fixtures give identical results across browsers, including the CJK passthrough case.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) fixtures V1–V7 exactly; (b) round-trip properties over generated texts mixing cases, digits, punctuation and CJK: decrypt∘encrypt = identity for Caesar at every shift and Vigenère with several keys; Atbash and ROT13 are self-inverse; (c) key-advancement: a text with interleaved punctuation decrypts under the same rule (V5 generalised) — an advance-on-every-character implementation fails; (d) passthrough integrity: non-letter characters are positionally identical between input and output for every operation, including an astral-plane character; (e) the string audit of section 5 over both locale tables and page metadata; (f) bounds: key length, shift range, input limit.
GUI/evidence tests (desktop, real browser): the banner is visible in every mode without scrolling on a mobile-width viewport; the brute table renders 25 labelled rows for a sample ciphertext and clicking a row fills the output; the key-error state appears for "K3Y". Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
