# Cron Expression Explainer and Next-Run Calculator — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. The dialect is standard five-field Vixie/POSIX cron; the page MUST name that dialect and its exclusions where users can see them, because silently treating a Quartz expression as cron produces wrong schedules.

## 1. Goal
Primary audience: developers, system administrators, ops/support engineers and students who write or inherit crontab entries. The recurring problem: a five-field expression is compact to the point of opacity, its day-of-month/day-of-week interaction surprises almost everyone once, and the failure mode is silent — a job that runs every minute, or never. Success is observable: the user pastes an expression and immediately reads (a) a per-field and whole-schedule explanation in their own language whose claims match the semantics of section 4 exactly, and (b) the next ten concrete firing times in local time with the timezone named; or builds the expression field by field and watches the text and explanation stay in sync. Non-goals: running or scheduling real jobs, six/seven-field dialects, Quartz extensions, remote crontab management, and converting between timezones (times are shown in the browser's local zone only, labelled as such).

Assumptions: a modern desktop browser; expressions are typed or pasted by the user; "now" means the device's clock; no network at runtime.

## 2. Scope and functional distinction
Included: (a) five-field parsing per section 4 including names, ranges, lists, steps and the seven `@` macros; (b) deterministic explanations: one line per field plus one whole-schedule sentence, in zh-TW and English with identical semantic content; (c) next-ten-runs enumeration from now or from a user-set start moment (date/time inputs), in local time with weekday shown and the timezone named (IANA name when the platform exposes it, else the UTC offset); (d) a per-field builder (every / specific values / range / step) bidirectionally synced with the text; (e) field-precise errors; (f) a never-fires report when the search window is exhausted. Excluded: seconds/year fields, `?` `L` `W` `#` tokens (their presence is a specific "unsupported dialect token" error pointing at the help), `@reboot`, environment lines or full crontab files (input is one expression), and any execution.
Distinction from existing work: Date Calculator computes differences between dates; Meeting Overlap intersects people's availability windows. Neither parses a scheduling DSL, explains it, or enumerates firings under the DOM/DOW rule. No catalog entry, reserved specification or registry task at admission time handles cron expressions; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: the expression field contains a bundled example (`0 9 * * 1-5`) already evaluated, clearly presented as an example the user can replace — unlike tools where a placeholder fakes a value, this example is real input producing a real explanation, and editing it behaves like any input. Explanation, field breakdown and next-runs table update on every valid change (debounce ≤200 ms).
Invalid input: the results area switches to the error state naming the field (by position and name, e.g. "field 2 (hour)") and the offending token, with the dialect note when a Quartz token is detected; no partial explanation or stale next-runs remain visible.
Builder: five field rows, each a mode select (every / choose values / range / step) with the matching controls; changing any control rewrites the expression text in canonical builder form (section 4) and re-evaluates. Editing the text directly switches each field's builder row to reflect the parsed field when it matches a builder shape exactly, or to a "custom" label when it does not (the builder never silently rewrites hand-typed text it cannot represent).
Start moment: default "now"; the user may set a date/time (local) to enumerate from; a "reset to now" control restores it. The runs table shows date, weekday and time for the next ten firings strictly after the start; if fewer exist in the window, it shows those and the never/rarely note of section 4.
Nothing is stored; leaving or reloading returns to the bundled example. Identical (expression, start moment, timezone) inputs produce identical explanations and run lists.

## 4. Grammar, semantics and exact output
Fields and ranges (normative): minute 0–59; hour 0–23; day-of-month (DOM) 1–31; month 1–12 or JAN–DEC; day-of-week (DOW) 0–7 or SUN–SAT, where both 0 and 7 denote Sunday and 7 is normalised to 0 in the value set. Names are case-insensitive ASCII. A field is a comma-separated list of items; an item is `*`, a value, or a range `a-b`, optionally followed by `/step` (step is an integer ≥1). Step semantics: `*/n` steps over the field's full range; `a-b/n` steps within the range; `a/n` means `a-max/n` (Vixie behaviour, stated in help because it surprises). A field's value set is the sorted union of its items' values. Errors (each names the field and token): wrong field count (with the count found); unknown name; value out of range; range with start > end; step 0 or non-numeric; empty list item; the Quartz tokens `?`, `L`, `W`, `#` anywhere → the dialect error. Whitespace: fields are split on runs of spaces/tabs; leading/trailing whitespace is ignored.
Macros (expanded visibly to their fields as soon as entered): `@hourly` = `0 * * * *`; `@daily` and `@midnight` = `0 0 * * *`; `@weekly` = `0 0 * * 0`; `@monthly` = `0 0 1 * *`; `@yearly` and `@annually` = `0 0 1 1 *`. Any other `@…` input is an error listing the supported macros.
Day matching (normative — the rule most tools get wrong): a field is called starred when its text begins with `*` (so `*` and `*/2` are both starred). If DOM and DOW are both unstarred (restricted), a day matches when DOM matches OR DOW matches. In every other case a day matches when DOM matches AND DOW matches (with a starred field matching every day by its value set). Month, hour and minute must always match. This rule, in plain language, is a required element of the whole-schedule explanation whenever both day fields are restricted.
Next-run enumeration: firings occur at second 0 of matching minutes. From the start moment, enumeration begins at the first minute boundary strictly after the start (a start of 09:00:00 exactly does not include 09:00). The search advances minute by minute using local-time field extraction (the platform's Date semantics; a local time that does not exist due to a DST transition simply never matches, and help states this). Window: 4 years + 1 day from the start (covers the leap-day cycle). Collect up to 10 firings; if the window ends first, show those found (possibly zero) plus the note: no (further) run exists within four years — schedules such as February 31st never fire, and DOM values missing from a month (the 31st in February) are skipped for that month, which the note explains when relevant. Performance: the minute scan is at most ~2.11 million iterations of cheap set lookups and MUST complete within 1 second for the worst case (never-firing expression) on a mid-range laptop; smarter jumping is allowed only if results are identical.
Explanation content (normative elements; exact wording is the product's, in both languages, but every element is mandatory): per field — minute/hour: the value set described as "every minute/hour", a single value, a range, a step pattern ("every 15 minutes"), or an explicit list when it has ≤6 values (longer lists are summarised as "N specific values" with the full set visible in the builder/table). DOM/month/DOW likewise with names for months/weekdays. Whole-schedule sentence: combines the time-of-day pattern with the day pattern, and includes the OR-rule sentence when both day fields are restricted, and a "this can never fire" warning when enumeration from now finds no run in the window (the warning is part of the explanation, not only the table).
Builder canonical form: a field built by the controls is written as `*` when its set is the full range; otherwise as comma-joined items where maximal consecutive runs of length ≥3 collapse to `a-b`, runs of 2 stay `a,b`, and step-built fields keep their `base/n` form while in step mode. Builder edits never reorder or alter other fields.
Worked fixtures (normative; local timezone pinned by the test): start Friday 2026-10-30 16:59:00, expression `*/15 9-17 * * 1-5` → next runs begin Fri 2026-10-30 17:00, then Mon 2026-11-02 09:00, 09:15, 09:30 (weekend skipped). `0 0 29 2 *` from 2027-03-01 00:00 → first run 2028-02-29 00:00. `0 0 31 2 *` from any start → zero runs in window + never-fires note. `0 12 15 * 5` fires on the 15th of every month AND every Friday (OR rule), and its explanation contains the OR sentence. `@weekly` expands to `0 0 * * 0`. Expression `0 9 * * MON-FRI` parses identically to `0 9 * * 1-5`.

## 5. Implementation and safety
Architecture (future production): a pure core (tokeniser/parser to value sets + starred flags, explanation model producing structured per-field descriptions that the UI renders in either language, next-run enumerator over an injected clock) with zero DOM access; a controller for text/builder sync; a thin DOM layer. Runtime dependencies: none. Explanation strings are data-driven from the parsed model — the core never concatenates final prose, which is what keeps the two languages semantically identical.
Privacy/security: expressions are data rendered as text; no storage, no network; nothing is placed in the URL. No code from the expression is ever evaluated (it is a fixed grammar, parsed — `eval` and `Function` are forbidden anywhere in the product).
Bilingual and accessibility: full zh-TW (default) and English UI; weekday and month names localised in outputs; the runs table is a real table; field errors are tied to the single expression input with the field named in text (there is one text field, so the error text carries the field identity); builder controls are native selects/checkboxes/inputs with labels; keyboard-only operation completes both modes.
Performance bounds: per section 4's worst case; ordinary expressions evaluate effectively instantly; the builder sync MUST NOT trigger a full four-year scan on inputs that are invalid (parse first, enumerate only when valid). Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; parse/explain/enumerate/build all working; text↔builder sync in both directions including the custom-shape case; macro expansion visible.
- boundaries: every field's min/max and one beyond; step 0; reversed range; February 29/30/31 cases; DOW 0 vs 7 equivalence; never-firing expression reported within the time bound.
- privacy: zero network after load; no storage; expression absent from URL/title; nothing copied without a gesture (there is no copy feature in this version beyond the user's own selection).
- security: expressions render as text only; parser is a fixed grammar (no eval anywhere, verified by source inspection); no external resources.
- usability: a first-time user correctly predicts the next run of `0 12 15 * 5` after reading the explanation — the OR rule is the test case; errors let them fix the exact field without re-reading the whole string.
- accessibility: labelled controls, real table, errors in text with field identity, keyboard-complete flows in both modes.
- localization-seo: zh-TW and en pages complete and equivalent, explanations semantically identical; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; explanation templates ship as reviewable data for both languages.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; enumeration fixtures pass in a pinned timezone (tests set TZ explicitly) and the on-screen timezone label matches the platform.

## 7. Required tests and timing
Core unit tests with independently derived expectations (timezone pinned, e.g. TZ=Asia/Taipei, and fixtures stated in local time): (a) every section 4 worked fixture exactly — run lists, expansion, explanation elements present (the OR sentence present/absent as specified); (b) parser sweep: each error class with its field/token identity; names in mixed case; `a/n` expansion equals `a-max/n`; DOW 7 normalisation; starred determination for `*` vs `*/2` vs `1-5`; (c) day-matching truth table over (DOM starred?, DOW starred?, DOM match, DOW match) — all 16 rows against the stated rule; (d) enumeration edges: strictly-after start at an exact firing minute; month-length skipping (31st); leap cycle within the 4-year+1-day window; the never-firing case completing within the stated iteration bound; (e) builder canonicalisation: full set → `*`, runs of 2 vs 3, step-mode retention.
GUI/evidence tests (desktop, real browser): fixtures through the real UI in both languages with the browser timezone noted; builder round-trips; error-state screenshots; keyboard-only completion. Timing: full core suite under 60 seconds (the worst-case enumeration is part of the suite and timed); no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
