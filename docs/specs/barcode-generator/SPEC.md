# Barcode Generator (1D: Code 128 / EAN-13 / UPC-A) — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. A barcode is a promise to a scanner: this specification pins the encodings, the check digits and the physical sizing so that any independent implementation produces the same bars for the same payload.

## 1. Goal
Primary audience: small-shop and warehouse staff printing shelf and box labels, librarians and makers labelling collections, market sellers and small manufacturers needing retail-style numbers for internal use, and office staff tagging assets. The recurring problem: free online generators hide their check-digit handling, add watermarks, upload the payload, or render at an unstated size that will not scan when printed. Success is observable: the user chooses Code 128, EAN-13 or UPC-A, enters the payload, and gets a barcode whose checksum, module count and physical width at the chosen module size are all displayed and reproducible by hand from section 4 — then downloads PNG or SVG at a stated scale. Non-goals: 2D codes (QR lives in its own tool), barcode scanning/reading, batch or sequential generation, label-sheet imposition, and any claim that an internally invented EAN/UPC number is registered — the page MUST state that retail numbers are allocated by GS1 and this tool only performs the arithmetic.

Assumptions: a modern desktop browser; short payloads within the caps below; no network at runtime.

## 2. Scope and functional distinction
Included: (a) Code 128 over code sets B and C with one deterministic auto-switch rule (section 4), payload printable ASCII 32–126, length 1–48 characters, checksum mod 103; (b) EAN-13: 12 digits → the check digit is computed and appended (and displayed as a separate, labelled digit); 13 digits → the check digit is validated and a mismatch is an error naming the expected digit; (c) UPC-A: the same contract over 11/12 digits; (d) rendering options: module width X in mm (0.25–1.00, step 0.01, default 0.33), bar height in mm (10–60, step 1, default 25 for Code 128 and 22 for EAN/UPC), human-readable text toggle (default on), quiet zones included in the rendering and in the reported total size; (e) downloads: SVG in module units (viewBox width = total modules) and PNG at an integer scale of 1–10 px per module (default 3), height in px = round(barHeightMm ÷ X × scale); (f) live facts beside the preview: symbology, encoded symbol count / total module count including quiet zones, physical width = total modules × X (mm, 2 decimals), and for EAN/UPC the check digit. Excluded: Code set A and FNC characters, Code 39/ITF/Codabar and all other symbologies, logos or text inside the bars, colour options beyond black-on-white (stated: contrast is a scanning requirement, not a style choice), and persistence.
Distinction from existing work: the Offline QR Code Maker specification covers 2D QR (Reed–Solomon, masking, screen sharing); this tool is 1D only, with check-digit arithmetic and print sizing, and the two never share a payload path. Label Printer arranges text on labels but encodes no symbology; Print Size computes image dimensions, not modules. No catalog entry, reserved specification or registry task at admission time encodes 1D barcodes; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: Code 128 selected, a sample payload `SKU-1024` prefilled and rendered, facts displayed. Switching symbology keeps the text if it is valid for the new symbology, otherwise shows that symbology's own last-valid or sample value with the reason stated — the input is never silently rewritten (for EAN/UPC, a 12-digit entry stays 12 digits in the field; the appended check digit appears in the preview and facts, not inserted into the user's text).
Every edit re-encodes immediately. Error states are specific and non-destructive: empty payload; a character outside printable ASCII in Code 128 (named, with its position); letters in EAN/UPC fields; wrong digit count (expected 12/13 or 11/12, actual count shown); check-digit mismatch (expected digit shown). While an error stands, the preview shows the last valid barcode greyed with an "out of date" label, and downloads are disabled — a stale barcode must never be downloadable as if current.
Downloads produce exactly the displayed modules: SVG named `barcode-<symbology>.svg`, PNG named `barcode-<symbology>.png`. Nothing persists across reload; the payload never appears in the URL, title or any request.

## 4. Encoding rules (normative)
Code 128. Values: in set B, a character with ASCII code c (32–126) has value c − 32. In set C, a digit pair `d1d2` has value 10·d1 + d2. Control values: Start B = 104, Start C = 105, switch to C (in B) = 99, switch to B (in C) = 100, Stop = 106. Symbol patterns: each value 0–105 occupies 11 modules; the stop symbol occupies 13 modules including the final termination bar. The bar/space width patterns for values 0–106 MUST ship as a data file transcribed from ISO/IEC 15417 and verified per section 7 — reciting a partial table from memory inside code is a defect.
Auto-switch rule (deterministic, no choices): let a digit run be a maximal run of characters 0–9. A run of length ≥4 is encoded in C; if its length is odd, its first digit is encoded in B and the remaining even-length part in C. Runs of length ≤3 are encoded in B. The start set is C when the payload begins with an even-length run ≥4; B in all other cases (including an odd-length opening run ≥5, whose first digit goes in B before switching). Switching emits 99 (B→C) or 100 (C→B) at the transition; no switch is emitted after the final symbol. Checksum: check = (startValue + Σ i·value_i) mod 103, where value_i are the data and switch symbols in order and i starts at 1. Quiet zone: 10 modules each side.
Worked fixtures (normative, re-derived in drafting): (1) `ABC` → Start B; values 33, 34, 35; check = (104 + 33 + 68 + 105) mod 103 = 310 mod 103 = **1**; symbols total 5 (start, 3 data, check) → 5×11 + 13 = 68 modules, 88 with quiet zones; at X = 0.33 mm the physical width is 88 × 0.33 = **29.04 mm**. (2) `123456` → Start C; values 12, 34, 56; check = (105 + 12 + 68 + 168) mod 103 = 353 mod 103 = **44**; 88 total modules with quiet zones. (3) `AB123456` → Start B; values 33, 34, 99, 12, 34, 56; check = (104 + 33 + 68 + 297 + 48 + 170 + 336) mod 103 = 1056 mod 103 = **26**. (4) `12345AB` → Start B; values 17, 99, 23, 45, 100, 33, 34; check = (104 + 17 + 198 + 69 + 180 + 500 + 198 + 238) mod 103 = 1504 mod 103 = **62**.
EAN-13. Structure: 95 modules — left guard `101`, six left digits (7 modules each), centre guard `01010`, five right digits plus the check digit (7 each), right guard `101`. L patterns: 0 `0001101`, 1 `0011001`, 2 `0010011`, 3 `0111101`, 4 `0100011`, 5 `0110001`, 6 `0101111`, 7 `0111011`, 8 `0110111`, 9 `0001011` (1 = bar). R(d) is the bitwise complement of L(d); G(d) is the reverse of R(d). The first digit is not printed as bars; it selects the parity pattern of the six left digits: 0 LLLLLL, 1 LLGLGG, 2 LLGGLG, 3 LLGGGL, 4 LGLLGG, 5 LGGLLG, 6 LGGGLL, 7 LGLGLG, 8 LGLGGL, 9 LGGLGL. Right-side digits always use R. Check digit over the first 12 digits: weight 1 for odd positions and 3 for even positions (counting from the left, position 1 first); check = (10 − (weightedSum mod 10)) mod 10. Quiet zones: 11 modules left, 7 right. Human-readable layout (when on): first digit left of the left guard, left six digits under the left half, right six under the right half.
Fixture (normative): `590123412345` → weighted sum: odd positions 5+0+2+4+2+4 = 17; even positions 9+1+3+1+3+5 = 22, ×3 = 66; total 83; check = **7**; full code 5901234123457. First digit 5 → parity LGGLLG over left digits 9,0,1,2,3,4. The complete module string (95) is: `10100010110100111011001100100110111101001110101010110011011011001000010101110010011101000100101`. A second check-only fixture: `978020137962` → check **4**.
UPC-A. Structure: the same 95 modules; the first six digits (including the number-system digit) use L, the last six use R; guards identical. Check digit over the first 11 digits: weight 3 for odd positions and 1 for even positions (from the left); check = (10 − (weightedSum mod 10)) mod 10. Quiet zones: 9 modules each side. Fixture (normative): `03600029145` → odd positions 0+6+0+2+1+5 = 14, ×3 = 42; even positions 3+0+0+9+4 = 16; total 58; check = **2**; full code 036000291452, whose complete module string (95) is: `10100011010111101010111100011010001101000110101010110110011101001100110101110010011101101100101`.

## 5. Implementation and safety
Architecture (future production): a pure core (validators, three encoders returning a module string of `0`/`1` plus the symbol-value trace for Code 128, sizing maths, SVG/PNG serialisers) with zero DOM access; a controller; a thin DOM layer rendering bars as SVG rects (or one path) from the module string — the module string is the single source of truth for preview, facts and both downloads. Runtime dependencies: none; the Code 128 pattern table and EAN tables ship as data modules in the repository.
Privacy/security: the payload renders as text only; no network, no storage, no analytics; PNG generation uses an on-page canvas whose contents never leave the device; no eval/Function; no external fonts or images (the human-readable digits use a system font stack).
Bilingual and accessibility: full zh-TW (default) and English UI; the barcode itself is an image, so the page MUST expose its content as text — payload, symbology, check digit and size are all in ordinary text beside it, and the preview carries an aria-label naming symbology and payload. Error messages are text, linked to the field. All controls are native and keyboard-operable.
Performance bounds: encoding is trivially O(n); re-render per keystroke with no debounce needed at these sizes; PNG at scale 10 for the widest case (Code 128, 48 chars worst case modules) stays under 2,000 px wide. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all three symbologies; check-digit compute and validate paths; downloads reproduce the displayed module string exactly (SVG parsed back to modules, PNG sampled at module centres).
- boundaries: Code 128 lengths 1 and 48 and 49 refused; digit runs of exactly 3, 4, 5 and 6 at start, middle and end (switch trace verified); a character at ASCII 32 and 126 and one at 127 refused with position; EAN/UPC digit counts 11/12/13/14 as applicable; X at 0.25 and 1.00.
- privacy: zero network after load; no storage; payload absent from URL/title; canvas contents not transmitted.
- security: payload with markup characters renders inert everywhere (Code 128 accepts `<` as data — it must appear only as bars and escaped text); no external resources; no eval/Function.
- usability: a shop worker goes from opening the page to a printed-size-correct label without instructions; the GS1 note is understood as "the number is mine to allocate properly" (spot-check), not as legal threat.
- accessibility: payload/check/size available as text; labelled native controls; keyboard-complete; error text associated with the field; barcode preview aria-labelled.
- localization-seo: zh-TW and en pages complete and equivalent; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the Code 128 width table and EAN tables ship as auditable data and match the fixtures in section 4.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical module strings across browsers for the fixture corpus; PNG dimensions per the stated formula in each.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) all section 4 fixtures exactly — four Code 128 checksums and symbol traces, both EAN check digits, the UPC check digit, and both complete 95-module strings; (b) switch-rule sweep: runs of length 3 (stays in B), 4 (C), 5 at start (B digit then C), 5 mid-payload, 6 at end (no trailing switch back), and a payload of digits only with odd length 7; (c) pattern-table integrity: exactly 107 entries (0–106), each 11 modules wide except stop at 13, every pattern starting and ending per the bar-first convention, and the table's checksum recorded in the test file so a transcription slip fails loudly; (d) validators: each error class in section 3 with its exact message parameters (position, expected digit, counts); (e) sizing: total modules and mm width for fixtures at X = 0.25, 0.33 and 1.00 (2-decimal rounding, half away from zero); PNG pixel dimensions per formula.
GUI/evidence tests (desktop, real browser): enter each fixture through the real UI in both languages; download the SVG and PNG and verify them against the displayed module string mechanically; print-preview at 100% shows the stated physical width for one fixture (measured against the browser's own print CSS size, stated tolerance ±0.5 mm). A physical scan test with a phone scanner app on one printed Code 128 and one EAN-13 label is REQUIRED evidence for acceptance (it is the product's whole point) — recorded as a photo/report in the production evidence, never faked from the module string. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
