# Roman Numeral Converter — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Roman numerals invite folklore validators — regexes that accept `IIII` and reject nothing, converters that happily read `IC` as 99. This specification replaces folklore with one exact definition: the canonical form is whatever the greedy table produces, and a Roman string is valid if and only if re-encoding its value reproduces it exactly.

## 1. Goal
Primary audience: students and teachers meeting Roman numerals in class, readers decoding dates on buildings, books, films and monuments, editors checking chapter and page numbering, and clock and inscription spotters who keep meeting the famous `IIII` clock face. The recurring problem: most online converters silently accept non-canonical strings, so a user cannot tell whether `IC` is "a way to write 99" or a mistake; some also invent a Roman zero or extend to thousands with ad-hoc overlines. Success is observable: the user types an integer 1–3999 in one field or a Roman string in the other and immediately sees the conversion — always canonical — plus a breakdown table listing the symbol groups that sum to the value. A non-canonical Roman string produces a specific error naming the loose value it would have meant and showing that value's canonical form, so the user learns the rule instead of being silently corrected. Non-goals: zero, negatives and values ≥4000 (with vinculum notation), apostrophus notation, fractions, and any clock-face special mode — the page MUST state that traditional clock faces often use `IIII` for 4 as a design convention and that this tool reports the canonical form, without offering a mode that emits it.

Assumptions: a modern desktop browser; tiny inputs within the caps below; no network at runtime.

## 2. Scope and functional distinction
Included: (a) integer → Roman conversion for integers 1–3999 by the greedy table of section 4; (b) Roman → integer conversion with the strict validity rule of section 4; (c) two synchronised fields — editing either field recomputes the other and the breakdown, with the field being edited never rewritten by the tool; (d) a breakdown table listing each greedy group used, its symbol text and its value, in descending order, ending with the total; (e) a copy button for each field's current valid value; (f) the six subtractive pairs (IV, IX, XL, XC, CD, CM) shown in a static reference table of all thirteen greedy entries, so the system is fully visible on the page. Excluded: any notation beyond the thirteen table entries, lowercase as a distinct meaning (lowercase input is accepted and normalised, see section 4), persistence, and batch conversion.
Distinction from existing work: the Integer Representation Inspector (consumed specification) inspects positional bases — binary, octal, hexadecimal, two's complement widths and byte views, including integers above 2^53; Roman numerals are a non-positional subtractive system with no zero, no width and a hard ceiling of 3999 in this scope, and the two tools share no algorithm or table. The Date Calculator adds days to dates; it does not parse numeral systems. No catalog entry, reserved specification or registry task at admission time converts Roman numerals; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: integer field prefilled `1994`, Roman field showing `MCMXCIV`, breakdown displayed (M 1000, CM 900, XC 90, IV 4). Editing the integer field recomputes the Roman field and breakdown on every keystroke; editing the Roman field recomputes the integer field and breakdown. The field under the user's cursor is never reformatted mid-typing (a half-typed `MC` in the Roman field is analysed as-is and reported, not auto-completed).
Error states are specific and non-destructive: integer field — empty (neutral, outputs clear); non-digit characters (named); 0 (explains Roman numerals have no zero); ≥4000 (out of range, explains the 3999 ceiling and that overline notation is out of scope); leading zeros are accepted as the integer they denote (`007` = 7) and stated as such. Roman field — empty (neutral); a character outside IVXLCDM (named, with its position); longer than 15 characters (over the maximum possible canonical length); non-canonical (the error names the loose value and displays its canonical form, e.g. `IC` → "loose value 99; canonical form is XCIX"). While an error stands, the opposite field and the breakdown freeze at the last valid state marked "out of date", and copy buttons for stale values are disabled — a stale conversion must never be copyable as if current. Nothing persists across reload; values never appear in the URL or title.

## 4. Conversion and validity rules (normative)
Symbols and values: I=1, V=5, X=10, L=50, C=100, D=500, M=1000.
Canonical generation (the only generation rule): the greedy table, in this exact order — (1000, M), (900, CM), (500, D), (400, CD), (100, C), (90, XC), (50, L), (40, XL), (10, X), (9, IX), (5, V), (4, IV), (1, I). Repeat: while the remaining value is at least the entry's value, append its symbols and subtract. This produces exactly one string per integer in 1–3999.
Loose value (used only for validity checking and error messages): scan the string left to right; each symbol contributes its value, subtracted when the immediately following symbol has a strictly larger value, added otherwise.
Validity (normative, complete): a normalised Roman string S is valid if and only if (i) S is non-empty, (ii) every character is one of IVXLCDM, (iii) the loose value v of S satisfies 1 ≤ v ≤ 3999, and (iv) canonical generation of v reproduces S exactly. No other rule, regex or exception list may widen or narrow this definition; the familiar corollaries (at most three repeats of I/X/C/M; V, L, D never repeated; subtraction only from the next two larger symbols, i.e. exactly the six pairs in the table) follow from it and are stated on the page as explanation, not as separate checks.
Normalisation and input grammar: the Roman field is trimmed of leading/trailing ASCII whitespace and uppercased (a–z mapped to A–Z) before validation; interior whitespace is an invalid character error naming its position. Maximum accepted field length after trimming is 15 characters (3888 = MMMDCCCLXXXVIII is the longest canonical form); a longer field is the over-length error, not a validity failure. The integer field accepts ASCII digits 0–9 only, at most 4 characters; its value is the ordinary decimal value (leading zeros permitted).
Worked fixtures (normative, re-derived by script during drafting, including an exhaustive round trip over all 3,999 values): 1=I; 4=IV; 9=IX; 14=XIV; 40=XL; 44=XLIV; 49=XLIX; 58=LVIII; 90=XC; 99=XCIX; 400=CD; 444=CDXLIV; 500=D; 777=DCCLXXVII; 900=CM; 944=CMXLIV; 1994=MCMXCIV; 2026=MMXXVI; 2421=MMCDXXI; 3888=MMMDCCCLXXXVIII (15 characters, the maximum); 3999=MMMCMXCIX.
Invalid fixtures (normative — each with the loose value the error message MUST name): IIII (4, canonical IV); IC (99, XCIX); IL (49, XLIX); IIV (5, V); IXIX (18, XVIII); IXL (39, XXXIX); VX (5, V); LC (50, L); DM (500, D); VV (10, X); LL (100, C); DD (1000, M); CCCC (400, CD); XXXX (40, XL); XM (990, CMXC); MMMM (loose 4000, out of range).

## 5. Implementation and safety
Architecture (future production): a pure core (greedy generator, loose parser, validity predicate, breakdown decomposer returning the list of (symbols, value) groups used by the generator) with zero DOM access; a controller; a thin DOM layer. The breakdown MUST come from the generator's own trace, so the table can never disagree with the displayed string. Runtime dependencies: none.
Privacy/security: inputs are numbers and short strings rendered as text only; no network, no storage, no analytics; no eval/Function; no external resources. The Roman field accepts arbitrary typed characters before validation — they MUST reach the page only as escaped text in error messages, never as markup.
Bilingual and accessibility: full zh-TW (default) and English UI, including the no-zero explanation, the 3999-ceiling explanation and the clock-face `IIII` note. Both fields and the breakdown are ordinary text and a real table; the breakdown is readable without seeing the Roman string's styling. Error messages are text, linked to their field; all controls native and keyboard-operable; copy success is announced as text.
Performance bounds: conversion is O(number of symbols) ≤ 15 steps; the exhaustive production test over 3,999 values is trivially fast. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; both directions; breakdown always matches the generator trace; copy buttons copy exactly the displayed valid value; the thirteen-entry reference table complete.
- boundaries: 1 and 3999 convert; 0 and 4000 are the stated errors, not conversions; Roman length 15 accepted (3888) and 16 refused as over-length; all sixteen invalid fixtures rejected with the correct loose value and canonical form named.
- privacy: zero network after load; no storage; values absent from URL/title.
- security: Roman/integer field text containing markup renders inert everywhere including error messages; no external resources; no eval/Function.
- usability: a student converts a year (e.g. a film's copyright date) and, after typing `IC`, understands from the error why 99 is XCIX (spot-check), without reading the reference table first.
- accessibility: fields labelled; breakdown is a real table with a total row; error text associated with its field; keyboard-complete; copy feedback as text.
- localization-seo: zh-TW and en pages complete and equivalent (including the no-zero, ceiling and clock-face notes); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; the greedy table appears once as auditable data matching section 4; the exhaustive 1–3999 round-trip test is present and passes.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical strings and verdicts for the fixture corpus across browsers.

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) all twenty conversion fixtures in both directions; (b) all sixteen invalid fixtures rejected, each error naming the loose value and canonical form in the fixture list; (c) the exhaustive property: for every integer 1–3999, generate → loose-parse returns the integer, the string is valid by the section 4 predicate, and length ≤ 15; (d) normalisation: `mcmxciv` and ` MCMXCIV ` both yield 1994; interior space yields the position-named error; (e) integer grammar: `007` → 7 (VII), `0` → no-zero error, `4000` → ceiling error, `12a` → non-digit error, 5 digits → length error; (f) breakdowns: 1994 decomposes to M+CM+XC+IV summing to 1994, and 3888's breakdown has the maximal group count with a sum check on every fixture's breakdown.
GUI/evidence tests (desktop, real browser): fixtures entered through the real UI in both languages in both directions; the stale-state behaviour (type an invalid Roman string over a valid one — opposite field freezes, marked out of date, copy disabled); copy buttons verified against the clipboard contents. Timing: full core suite (including the exhaustive loop) under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
