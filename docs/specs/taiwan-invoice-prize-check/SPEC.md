# Taiwan Uniform Invoice Prize Check — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Prize names, tier rules and standard amounts below describe the long-standing Taiwan uniform invoice （統一發票） scheme as the tool's rule model; the page MUST state in both languages that the official Ministry of Finance announcement for the relevant period governs, and that this tool checks numbers the user typed — a typing error in the winning numbers produces wrong verdicts, so the setup step must be confirmed carefully.

## 1. Goal
Primary audience: anyone in Taiwan holding paper or printed uniform invoices for a bimonthly draw — individuals sorting a wallet or drawer of receipts, families checking together, small shops verifying customer-returned invoices. The recurring problem: comparing dozens of 8-digit numbers against the winning list by eye is slow and error-prone, and content-farm checking pages bury the tool under ads or ask users to type numbers into a remote form. Success is observable: the user enters the period's winning numbers once, then checks each invoice in full mode (exact tier and standard amount, with the matching rule spelled out) or clears obvious losers in seconds in quick mode (honest "possible / impossible" answers, never a fake verdict), and sees a batch summary of counts by tier and total standard prize amount. Non-goals: fetching winning numbers from any source, cloud-invoice （載具） account access, barcode/QR scanning, storing numbers, tax or prize-claim filing guidance, and checking other countries' lotteries or receipt lotteries with different rules.

Assumptions: a modern desktop browser; the user copies winning numbers from the official announcement themselves; all figures are the standard statutory amounts frozen in section 4 (the tool does not pretend to know a future period's changes).

## 2. Scope and functional distinction
Included: (a) winning-number setup for one period: special prize 特別獎 (exactly one 8-digit number), grand prize 特獎 (exactly one 8-digit), first prize 頭獎 (1–5 8-digit numbers), additional sixth prize 增開六獎 (0–4 3-digit sets); duplicate detection inside the setup (the same 8-digit value entered as both special and first prize, or repeated first-prize numbers, is an error to fix, not a silent precedence case); (b) full check of one 8-digit invoice number with exact tier resolution and the matched rule displayed; (c) quick check of a 3-digit suffix returning "still possible" (with the possible tier range) or "cannot win"; (d) batch mode: paste up to 500 lines, each classified, with per-line results, counts by tier and the summed standard prize amount; invalid lines are listed with reasons, never silently dropped; (e) clear/reset for setup and results independently.

Excluded: any network fetch or import of winning numbers; OCR/camera input; cloud invoice integration; persistence across reloads; editing announced amounts; periods other than the single loaded setup; exporting results (clipboard copy of the summary line is allowed via user gesture; no file download in this version).

Distinction from existing work: List Compare reports set membership differences between two lists; it has no tier rules, no precedence and no prize semantics. Random Groups partitions a list randomly. The Quotation/Invoice-adjacent tools issue documents; none evaluates Taiwan's suffix-tier lottery rules. The distinguishing core is the domain rule engine of section 4 — suffix-length-to-tier mapping, special/grand precedence, the additional-sixth-prize channel, and the honesty contract of quick mode. No catalog entry, reserved specification or registry task at admission time checks invoice or lottery numbers; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: setup panel open and empty, checking disabled until the setup is minimally valid (special, grand and at least one first-prize number, all well-formed and mutually distinct); the page explains in one line where to copy the official numbers from.
Setup editing validates each field on commit (blur or Enter): wrong length or non-digit content marks the field with a specific error and keeps checking disabled; fixing it revalidates immediately. A "confirm setup" summary line restates how many numbers of each kind were entered so the user can eyeball a transcription mistake before checking.
Full check: typing an 8-digit number and pressing Enter (or the Check button) appends a result row: the number, the verdict （特別獎/特獎/頭獎/二獎/三獎/四獎/五獎/六獎/未中獎）, the standard amount (0 for no win), and the rule note (e.g. "末5碼與頭獎第2組相同" or "與特別獎完全相同"). The input clears and keeps focus for rapid entry. Duplicate checking of the same number is allowed and simply appends another row (shops may hold duplicates); the batch summary counts rows, and this is stated.
Quick check: entering 3 digits returns one of two panels: "末3碼未中，可直接排除" (cannot win any tier) or "可能中獎，請輸入完整號碼確認" with the possible tiers listed (from the matched channel: sixth guaranteed-possible if a first-prize last-3 or additional set matched; special/grand possible only when their last-3 matched, requiring full-number confirmation). Quick mode NEVER prints a prize amount or a definite tier.
Batch: paste into the batch box, press check; results render as a table aligned with input line numbers; the summary (counts by tier, total amount) appears above the table. Invalid lines show "格式錯誤" with the reason in their row.
Reset: "清除結果" empties results only; "重設開獎號碼" returns to the empty setup after an inline confirmation (it is destructive to typed setup); leaving or reloading discards everything. Re-checking with identical inputs is deterministic: same rows, same order, same totals.

## 4. Input, tier rules and exact output
Data model: a winning setup W = { special: D8, grand: D8, first: [D8 ×1–5], addSixth: [D3 ×0–4] } where D8 is a string of exactly 8 ASCII digits (leading zeros significant — numbers are strings, never parsed as integers) and D3 exactly 3 digits. An invoice candidate is a D8 string (full mode) or D3 string (quick mode). Whitespace around an entry is trimmed; internal spaces or any non-digit character make it invalid with a specific message; full-width digits （０-９) MUST be converted to ASCII digits before validation (a common paste case from Chinese sources), and this conversion is stated in the UI help.
Tier resolution for a full candidate c, evaluated in this exact precedence order:
1. c == W.special ⇒ 特別獎， standard amount 10,000,000.
2. c == W.grand ⇒ 特獎， 2,000,000.
3. For each first-prize number f in W.first, let k = the length of the longest common suffix of c and f, capped at 8. If k == 8 ⇒ 頭獎 200,000. Take the maximum k over all f; if 3 ≤ k ≤ 7 the tier is: k=7 二獎 40,000; k=6 三獎 10,000; k=5 四獎 4,000; k=4 五獎 1,000; k=3 六獎 200. The rule note names the matched f (by its position, e.g. 頭獎第2組） and k.
4. Else, if the last 3 digits of c are in W.addSixth ⇒ 六獎 200, rule note "末3碼與增開六獎相同".
5. Else 未中獎， amount 0.
Precedence note: step 3's k=3 already covers the case where c's last 3 equal a first-prize number's last 3; step 4 is only for the additional sets. A candidate can win at most one tier — the first matching step in this order. Amounts are the standard statutory amounts (NT$) frozen here; the UI labels them 標準金額 and shows the governing-announcement disclaimer.
Quick mode for a D3 q: possible = (q equals last3 of W.special) or (last3 of W.grand) or (last3 of any W.first) or (q ∈ W.addSixth). If not possible ⇒ "cannot win" verdict. If possible, the panel lists channels: special/grand channels mean "could be 特別獎/特獎 only if the full number matches exactly; otherwise may still qualify via other channels" — the listed possible-tier text MUST be conservative: it names 六獎 as the minimum possible tier when a first/additional channel matched, and says the full number is required for any definite verdict.
Batch summary: counts per tier in the fixed order 特別/特獎/頭/二/三/四/五/六/未中/格式錯誤， and total amount = Σ row amounts, displayed with thousands separators; per-row amounts use the same table. The summary is a pure function of (W, input lines).
Worked fixtures (normative, synthetic): W = { special 12345678, grand 87654321, first [11112222, 33334444], addSixth [007] }. Then: 12345678 ⇒ 特別獎； 87654321 ⇒ 特獎； 11112222 ⇒ 頭獎； 01112222 ⇒ 二獎 (k=7); 00112222 ⇒ 三獎 (k=6); 00002222 ⇒ 五獎 (k=4, since suffix "2222" matches and "02222" does not); 99994444 ⇒ 六獎 (k=3 via second first number); 55555007 ⇒ 六獎 via additional set, rule note names 增開六獎； 12345679 ⇒ 未中獎. Quick: 678 ⇒ possible (special last-3); 999 ⇒ cannot win. Full-width input "１２３４５６７８" MUST normalize and return 特別獎.

## 5. Implementation and safety
Architecture (future production): a pure core (setup validation, tier engine, batch classifier, summary) operating on digit strings with zero DOM access; a controller for the three panels; a thin DOM layer. Runtime dependencies: none; string suffix comparison only — the engine MUST NOT convert numbers to integers (leading zeros are data). 
Privacy/security: zero network after load; no storage; invoice numbers appear only in the results the user generated on screen; nothing is copied anywhere without a user gesture; all rendering uses text nodes (numbers are data, never markup); no external resources.
Bilingual and accessibility: the tool's primary UI is zh-TW (its audience), with a complete English UI of identical function; tier names show both the Chinese name and, in English mode, the standard English gloss. All inputs are labelled; verdicts are never conveyed by colour alone (the tier name is text); result rows are list/table semantics readable by assistive tech; batch paste area has instructions tied via aria-describedby; keyboard-only operation completes setup, both checks and reset.
Performance bounds: batch of 500 lines against the maximum setup classifies in under 100 ms on a mid-range laptop; single checks are effectively instant; no debouncing may delay a verdict after Enter. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; setup validation and duplicate detection; full/quick/batch flows; precedence and suffix tiers exactly per section 4; summary arithmetic.
- boundaries: leading-zero numbers; full-width digit paste; 500-line batch and line 501 handling (stated limit error, not truncation); duplicate setup values; k at every length 3–8.
- privacy: zero network after load; no storage; numbers absent from URL, title and any copied text the user did not explicitly choose to copy.
- security: no markup injection via pasted lines; strict digit-string validation; no external resources; no eval-like parsing.
- usability: a first-time user completes setup from an official announcement and checks a stack of invoices without instructions; quick mode's honesty (no fake verdicts) is obvious from its wording.
- accessibility: labelled fields, text verdicts, table/list semantics, keyboard-only completion, errors announced.
- localization-seo: zh-TW and en pages complete and equivalent including disclaimers; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; tests use the section 4 fixtures verbatim plus independently derived additions.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; correct behaviour when pasting from the official announcement's typical formats (spaces/newlines/full-width digits).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) every section 4 worked fixture exactly, including rule notes' matched-channel identity; (b) suffix lengths k = 0–8 swept against a constructed first-prize number; (c) precedence: a candidate constructed to match both a first-prize suffix and an additional set takes the higher tier; special/grand exact matches beat any suffix result; (d) setup validation: duplicates across kinds, wrong lengths, non-digits, full-width conversion; (e) quick-mode truth table over the four channels; (f) batch: mixed valid/invalid lines, 500-line limit behaviour, summary counts and totals by hand-checked arithmetic.
GUI/evidence tests (desktop, real browser): transcribe a synthetic announcement into setup, run the fixtures through the real UI in both languages, keyboard-only batch flow, error announcement check. Timing: full core suite under 60 seconds; no network in any test; no real announced winning numbers used as fixtures anywhere.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
