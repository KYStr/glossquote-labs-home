# WCAG Colour Contrast Checker — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. Contrast checking is a measurement, and a measurement tool's whole value is that its number is the same number an auditor gets: this specification pins the WCAG 2.1 formula, the rounding, the alpha compositing order and the correction algorithm so two conforming implementations can never disagree about a verdict.

## 1. Goal
Primary audience: web designers and front-end developers checking their own colour choices, teachers and office staff preparing slides and documents, small businesses and bloggers auditing an existing site, and students learning accessibility. The recurring problem: eyeballing readability fails exactly at the boundary, many online checkers round the ratio before judging it (displaying "4.50 ✓" for a pair that actually fails), and translucent colours get whatever answer the tool felt like. Success is observable: the user enters two colours and receives the unrounded WCAG 2.1 ratio, a five-row verdict table (AA normal, AA large, AAA normal, AAA large, non-text), sample text at normal and large sizes, and — on failure — a deterministic minimal correction for the foreground with its own verified ratio. Non-goals: designing palettes, judging whether a colour combination is beautiful, simulating colour-vision deficiency, sampling colours from images, and certifying a whole website (the page MUST state it checks pairs, not pages, and that WCAG conformance involves more than contrast).

Assumptions: a modern desktop browser; colours typed or pasted as text; no network at runtime.

## 2. Scope and functional distinction
Included: (a) two colour inputs (foreground, background), each accepting hex `#RGB`, `#RRGGBB`, `#RRGGBBAA` (leading `#` optional in the field, case-insensitive) and `rgb(r, g, b)` / `rgba(r, g, b, a)` with integer channels 0–255 and alpha a decimal in [0, 1]; each input also mirrored by a native colour swatch picker for the opaque case; (b) the ratio and verdicts of section 4, recomputed on every edit; (c) a swap button exchanging foreground and background (the ratio is symmetric — the swap exists for the suggestion direction and the preview); (d) sample previews: one paragraph at normal size (16 px) and one heading at large size (24 px) rendered in the pair, plus a simple non-text sample (an icon-like glyph and a border swatch); (e) the correction suggestion of section 4: direction (toward black / toward white) and target (AA normal 4.5 default, AA large 3.0, AAA normal 7.0, AAA large 4.5) selectable; the suggested colour is shown as hex with its ratio, and an apply button copies it into the foreground field; (f) both effective (composited) colours displayed as hex whenever alpha is involved. Excluded: CSS named colours and hsl()/hwb() input (stated; hex and rgb cover the audit workflow), multiple saved pairs, matrix checking, browser-extension features, and persistence.
Distinction from existing work: Color Palette *generates* harmonious colour sets from a seed; it never evaluates a given pair against thresholds or repairs one. This tool only evaluates and repairs given pairs. No catalog entry, reserved specification or registry task at admission time computes WCAG contrast; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: foreground `#777777` on background `#FFFFFF` prefilled — deliberately the famous near-miss pair (4.48, failing AA normal by a hair) so the first thing a new user sees is the tool being useful — with the verdict table and the suggestion (`#767676`, t = 0.01 toward black, 4.54) already computed. Every keystroke, picker change or swap recomputes ratio, verdicts, previews and suggestion together; there is no separate "check" button.
Parse errors are per-field and specific: a channel out of range names the channel and the allowed range; malformed hex names the expected digit counts (3, 6 or 8); an alpha outside [0, 1] is named. While either field is invalid, the other field's verdicts freeze at the last valid pair, marked "out of date", and the suggestion and apply button disable — a verdict must never appear to describe colours it was not computed from.
The large-text definition is displayed next to the AA/AAA large rows: large means at least 24 px, or at least 18.66 px (14 pt) when bold. The non-text row is labelled as covering icons, control borders and chart marks (WCAG 1.4.11), so users do not apply text thresholds to a button outline. Nothing persists across reload; colours never appear in the URL or title.

## 4. Computation rules (normative)
Parsing: hex digits expand per CSS rules (`#RGB` → each digit doubled; `#RRGGBBAA` → alpha = AA/255). `rgb()` channels MUST be integers 0–255 (percentages are not accepted in this version, stated); alpha is a decimal 0–1 inclusive, also accepting a leading-dot form (`.5`). Whitespace around tokens is ignored; anything else is a parse error.
Compositing (only when an alpha < 1 is present): compositing happens in sRGB space, channel by channel, C = α·Cf + (1 − α)·Cb, in exactly this order: (1) the effective background is the background colour composited over opaque white; (2) the effective foreground is the foreground colour composited over the effective background. Luminance is computed from the unrounded composite channel values; the displayed effective hex rounds each channel half away from zero, and MUST be labelled as the rounded display of the values actually used.
Relative luminance (WCAG 2.1): for each channel, let s = channel/255 (using the unrounded composite when applicable); linear = s/12.92 when s ≤ 0.03928, otherwise ((s + 0.055)/1.055)^2.4. L = 0.2126·R + 0.7152·G + 0.0722·B. Contrast ratio = (Llight + 0.05)/(Ldark + 0.05), in [1, 21].
Verdicts and rounding: the ratio is displayed rounded to two decimals (half away from zero). Every pass/fail verdict compares the **unrounded** ratio against the threshold (≥ passes). The page states this rule in one sentence next to the ratio, because the pair `#777777`/white displays 4.48 and fails while a hypothetical 4.4999 would display 4.50 and still fail — the statement is part of the product, not fine print. Thresholds: AA normal text 4.5; AA large text 3.0; AAA normal text 7.0; AAA large text 4.5; non-text 3.0.
Suggestion algorithm (deterministic): given the effective foreground F, the effective background B, a target T and a direction D: for t = 0.01, 0.02, …, 1.00 in order, the candidate is, toward black, channel' = round(channel × (1 − t)); toward white, channel' = round(channel + (255 − channel) × t) (rounding half away from zero, per channel). The first candidate whose unrounded ratio against B is ≥ T is the suggestion; its t, hex and ratio are displayed. If the current foreground already meets T, the suggestion area says so and offers nothing. If no t reaches T (possible for AAA targets, since some backgrounds defeat both pure black and pure white — the best achievable ratio against a background of luminance L is max((L + 0.05)/0.05, 1.05/(L + 0.05)), whose minimum over L is ≈4.58 at L ≈ 0.1791), the area states that no foreground-only fix reaches the target against this background and suggests changing the background instead — it never fabricates a passing colour.
Worked fixtures (normative, re-derived by script during drafting): (1) `#000000` on `#FFFFFF` → L 0 and 1 → ratio **21.00** (all rows pass). (2) `#FFFFFF` on `#FFFFFF` → **1.00** (all fail). (3) `#767676` on `#FFFFFF` → L ≈ 0.18116 → ratio ≈ 4.5422, displayed **4.54**, AA normal **passes** — the lightest neutral grey that passes AA on white. (4) `#777777` on `#FFFFFF` → ratio ≈ 4.4781, displayed **4.48**, AA normal **fails**, AA large passes. (5) `#FF0000` on white → L = 0.2126 → ratio ≈ 3.9985, displayed **4.00**, AA normal fails (pure red on white is the classic surprise). (6) `#0000FF` on white → L = 0.0722 → ≈ 8.5925, displayed **8.59**, AAA normal passes. (7) Alpha: foreground `rgba(0, 0, 0, 0.5)` on `#FFFFFF` → effective foreground channels 127.5 (displayed `#808080`) → ratio ≈ 3.9767, displayed **3.98**. (8) Suggestions: `#777777` on white, target 4.5 toward black → t = 0.01 gives `#767676`, ratio ≈ 4.5422 ✓ (the first step already passes); target 7.0 toward black → t = 0.25 gives `#595959`, ratio ≈ 7.0047 ✓.

## 5. Implementation and safety
Architecture (future production): a pure core (parser, compositor, luminance/ratio, verdicts, suggestion search) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. All arithmetic in IEEE-754 doubles in the order written in section 4 — reordering floating-point operations to "simplify" is a defect where it changes a fixture's verdict.
Privacy/security: colours are not personal data, but the rule stands — no network, no storage, no analytics; input renders as text; the preview sets colours only through validated internal values, never by interpolating raw field text into CSS or markup; no eval/Function; no external resources.
Bilingual and accessibility: full zh-TW (default) and English UI, including the large-text definition, the unrounded-verdict sentence and the GS1-style honesty note's local equivalent (pairs, not pages). The tool about accessibility must itself be accessible: verdicts are text (PASS/FAIL words), never colour alone; the sample previews supplement, never replace, the text verdicts; all controls native and labelled; the ratio and verdict table reachable and readable by keyboard and screen reader in logical order.
Performance bounds: trivial arithmetic; the suggestion loop is at most 100 ratio computations per edit; no debounce requirement beyond ordinary input handling. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host.

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all input formats; swap; previews; the full verdict table; suggestions computed, displayed and applicable for both directions and all four targets.
- boundaries: the boundary greys (fixtures 3 and 4) judged correctly; hex lengths 3/6/8 and invalid 4/5/7; channel 0 and 255 and 256 refused; alpha 0 (foreground invisible → ratio exactly 1.00 against its own composite) and 1; a pair constructed to display 4.50 while failing (unrounded < 4.5) is reported FAIL with the explanatory sentence present.
- privacy: zero network after load; no storage; colours absent from URL/title.
- security: field text containing markup or CSS payloads renders inert and never reaches a style or markup sink unvalidated; no external resources; no eval/Function.
- usability: a designer pastes two hex values from their stylesheet and reads the verdict without instructions; the failing pair's suggestion is discoverable and its apply action obvious (spot-check).
- accessibility: verdicts as text not colour; labelled native controls incl. the pickers; keyboard-complete flow; logical reading order; focus visible.
- localization-seo: zh-TW and en pages complete and equivalent (including the unrounded-verdict sentence and large-text definition); correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output on Node 24; thresholds and formula constants appear once, as auditable data matching section 4.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; identical ratios/verdicts for the fixture corpus across browsers (floating-point determinism of the pinned operation order).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) all eight section 4 fixtures exactly — ratios to 4 decimal places, displayed strings, and verdict rows for fixtures 3, 4 and 5; (b) parser sweep: every accepted format, case-insensitivity, `#` optional, `#RGB` expansion, and each refusal class with its message parameters; (c) compositing: fixture 7, background-alpha-only, both-alpha order sensitivity (a constructed case where reversing the order changes the ratio, proving the pinned order is what the code does); (d) suggestion search: fixtures 8 (both targets), already-passing input offers nothing, both-directions on a mid-luminance background (L ≈ 0.1791) with target 7.0 produces the honest no-fix message and no colour; (e) rounding: ratio display rounding half away from zero at a constructed x.xx5 case; verdict uses unrounded value (test at the display-4.50-but-fails construction).
GUI/evidence tests (desktop, real browser): fixtures entered through the real UI in both languages, via typing and via the swatch picker; suggestion applied via the button and re-verified in place; screen-reader-visible text order spot-checked in the accessibility tree. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
