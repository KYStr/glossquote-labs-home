# PDF Page Tools: Merge, Split, Extract and Rotate — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. One deliberate deviation from sibling tools is stated up front: PDF output is required to be structurally deterministic (same pages, same order, same rotations, valid in standard readers), not byte-identical, because PDF writers embed document IDs and timestamps.

## 1. Goal
Primary audience: office workers, teachers, students and job applicants who assemble submission packets, excerpt report pages, and fix sideways scans. The recurring problem: the well-known free PDF websites require uploading contracts, transcripts and ID scans to a stranger's server, with unclear retention. Success is observable: the user selects local files, sees each file's page count and the exact output plan (page order, groups, rotations) before generating, and downloads results whose page counts and order they can verify in any reader — with nothing uploaded anywhere. Non-goals: OCR, content editing, form filling, annotation, compression or quality promises, e-signatures, redaction (this tool MUST NOT be presented as a redaction tool — moving pages does not remove content), PDF/A or archival validation, and decrypting protected files.

Assumptions: a modern desktop browser with the File API and enough memory for the stated limits; files come from the user's own device via picker or drag-and-drop; no network at runtime.

## 2. Scope and functional distinction
Included modes: (a) Merge — 2–20 input PDFs, user-ordered list (move up/down buttons and drag), one output containing all pages in list order, each file contributing its pages in original order; (b) Split — one input PDF and a range expression producing either one combined output of the selected pages or one output per contiguous group, per a user toggle; (c) Extract — one input PDF and a page selection producing one output in the selection's listed order; (d) Rotate — one input PDF, a page selection, and an angle (90/180/270 clockwise) applied on top of each page's existing rotation. Shared: per-file validation with named errors, an output-plan summary shown before generation, generated-file download(s), and a clear-all control.
Excluded: password-protected input (rejected with a specific message; no password prompt, no decryption attempt), repairing corrupt files, merging non-PDF files, editing page content, reordering pages inside merge mode beyond whole-file order, and any server processing.
Distinction from existing work: Images to PDF consumes image files and emits a new PDF; it cannot open an existing PDF. File Bundler zips arbitrary bytes without page awareness. File Checksum hashes files. None parses PDF page structure or re-emits a reordered document. No catalog entry, reserved specification or registry task at admission time manipulates PDF pages; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Initial state: mode tabs (Merge / Split / Extract / Rotate), empty file area, generation disabled. Adding files (picker or drop) validates each: valid files appear with name, size and page count; invalid ones appear in an error list with the specific reason (not a PDF, encrypted, corrupt, over a limit) and are excluded from any plan until removed — generation never silently skips a file the user still sees in the list.
Merge flow: reorder the list; the plan line states total pages and the output filename; Generate produces one download. Split flow: pick one file, type the range expression; the plan lists the groups it parsed (e.g. "1–3, 5, 8–12 → 3 groups, 9 pages") or the parse error with the offending token highlighted in text; choose combined or per-group output; Generate produces one or several downloads in sequence. Extract flow: same range grammar; plan states the resulting page order exactly. Rotate flow: pick one file, a selection, and an angle; plan states which pages and their resulting absolute rotations where known.
Progress: generation of a large job shows a determinate progress note (files/pages processed); the tab remains responsive (work is chunked; the mechanism is the implementation's choice but a frozen tab for >1 s at the stated limits is a defect). Completion offers the download(s) and a "start over" that clears file handles from memory. Leaving or reloading discards everything; file contents are never stored, and re-opening the tool starts empty. Repeating the same operation on the same inputs yields structurally identical output (page sequence and rotations equal; bytes may differ per the deviation above).

## 4. Input rules, range grammar and exact output
File validation: a file counts as a PDF only if it begins with the `%PDF-` header within the first 1024 bytes AND the vendored parser opens it and reports a page count ≥1; both checks are required. Encrypted files (parser reports encryption) are rejected as "password-protected". Limits (each violation is a named error, nothing is truncated): per-file size ≤200 MB; merge inputs ≤20 files, aggregate size ≤200 MB, aggregate pages ≤2,000; single-file modes ≤2,000 pages.
Range grammar (normative, 1-based, pages numbered as in a reader): expression = item (`,` item)*; item = `n` | `n-m` | `n-` (n through last page); ASCII spaces around items and around `-` are ignored; `n` and `m` are decimal integers ≥1. Errors (each names the token): empty expression; empty item (`1,,2`); non-numeric token; `m < n`; any page beyond the document's page count; in split mode, overlapping groups; in extract mode, a duplicated page. Split groups keep the expression's order; extract keeps the listed order including for ranges (a range contributes ascending pages). A page count is always validated against the actual opened document before planning.
Merge order: files in list order; pages within a file in original order, unrotated beyond their existing rotation. Rotate: resulting rotation = (existing + chosen) mod 360, normalised to one of 0/90/180/270; the plan shows the resulting value for the first selected page as a sample when the parser reports existing rotations, and the operation is defined on the sum regardless.
Output naming (normative): the base name is the first/source file's name without extension, sanitised: path stripped, every run of characters outside `[A-Za-z0-9._-]` and CJK replaced by a single `-`, leading/trailing `-` trimmed, truncated to 60 characters, falling back to `document` when empty. Merge → `<base>-merged.pdf` (base from the first file). Split combined → `<base>-split.pdf`; per-group → `<base>-p<first>-<last>.pdf` per group (a single-page group is `<base>-p<n>.pdf`). Extract → `<base>-extract.pdf`. Rotate → `<base>-rotated.pdf`.
Output document properties: pages carry their original content and resources (copied, not re-rendered or rasterised — text stays text); the output's Producer string is the fixed value `GlossQuote Labs PDF Page Tools`; no source document metadata (title/author) is copied; outlines/bookmarks and links internal to a source are NOT guaranteed to survive page copying and the help text MUST say so plainly (a stated limitation, not a bug). Each output MUST open without repair warnings in the reference readers of section 6.

## 5. Implementation and safety
Architecture (future production): a pure core (file validation results model, range parser, plan builder, output naming) with zero DOM access and full unit-testability; a document engine adapter over the PDF library; a controller/DOM layer. PDF engine strategy (fixed): exactly one vendored library file, pinned by version and SHA-256, with its licence and source URL recorded in a `THIRD-PARTY.md` shipped in the repository (pdf-lib, MIT, is the expected candidate; any substitute needs the same provenance record and must satisfy every rule here). Runtime dependencies beyond that file: none; the library is served from the same origin; zero network.
Privacy/security: file bytes live only in page memory; file names are rendered as text (never markup — a hostile filename cannot inject HTML); no storage, no analytics; downloads via Blob with revoked object URLs; the page MUST warn users that the downloaded output may still contain the source's hidden layers/metadata within copied pages, since page copying is not sanitisation or redaction.
Bilingual and accessibility: full zh-TW (default) and English UI; the file list is a real list with labelled move/remove buttons per row (drag is an enhancement, never the only way to reorder); range errors are tied to the input with `aria-describedby`; generation progress and completion are announced politely; every mode is keyboard-completable.
Performance bounds: at the maximum aggregate (200 MB / 2,000 pages) the UI stays responsive per section 3 and total generation time is reported in the completion note (no fixed millisecond promise is made for generation at maximum size; validation of a 200 MB file MUST complete within 10 s on a mid-range laptop). Toolchain: Node 24, zero npm dependencies (the vendored file is data, not an npm dependency), house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from a static host (file:// allowed except where browser File API restrictions apply, which the help text notes).

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; all four modes end-to-end on the synthetic fixtures; page counts, orders and rotations verified by re-opening outputs programmatically.
- boundaries: exactly-at-limit and one-over cases for files/pages/size; encrypted fixture rejected; corrupt fixture rejected; every range-grammar error class.
- privacy: zero network after load; no storage; file bytes and names absent from URL/title; memory cleared by start-over as far as the platform allows.
- security: hostile filename renders as text; no source markup path into the DOM; vendored file hash matches its provenance record; Blob URLs revoked.
- usability: a first-time user merges two files and splits one without instructions; the plan summary prevents wrong-order surprises; error list is actionable.
- accessibility: keyboard-only completion of all modes including reordering; announced progress/completion; labelled controls throughout.
- localization-seo: zh-TW and en pages complete and equivalent including limitations text; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-npm-dependency build reproduces the site from a clean checkout on Node 24; `THIRD-PARTY.md` hash/version/licence verified against the vendored file.
- compatibility: outputs open without repair in current Chrome and Firefox built-in viewers, Adobe Acrobat Reader and macOS Preview; tool works in current Chrome/Edge/Firefox/Safari desktop.

## 7. Required tests and timing
Fixtures: synthetic PDFs generated by a committed script (never real documents): A = 5 pages, B = 3 pages, each page a distinct solid colour with its page label as text ("A-1"…"A-5"); an encrypted fixture; a truncated/corrupt fixture; a pre-rotated fixture (one page at 90°).
Core unit tests: range parser — every grammar rule and every error class with exact messages' identities; naming sanitiser fixtures (CJK name, spaces, 100-char name, name that sanitises to empty); plan builder for split/extract ordering; rotation sum normalisation.
Engine integration tests (Node, using the vendored library): merge A+B ⇒ 8 pages in order A-1..A-5,B-1..B-3 verified by extracting each page's label text; split A by `2-3,5` per-group ⇒ two files of 2 and 1 pages with the right labels; extract `5,1-2` ⇒ order 5,1,2; rotate page 2 by 90 twice ⇒ 180; pre-rotated fixture +90 ⇒ 180 total.
GUI/evidence tests (desktop, real browser): full flows in both languages with the fixtures, error-list behaviour, keyboard reordering, large-ish fixture (200 pages) responsiveness note. Timing: core suite under 60 seconds; engine suite under 120 seconds; no network anywhere.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
