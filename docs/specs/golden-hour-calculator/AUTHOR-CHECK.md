- 案例推導（獨立實作，未用任何產品程式）。作者依 NOAA 公布的 fractional-year 公式原文與 PhotoPills 仰角定義，在 scratch 環境寫了兩份結構不同的實作交叉驗證：
  - 方法 A：以 `datetime` 計 doy；cosHa 用 `cos(90.833°)/(cosφ·cosδ) − tanφ·tanδ` 式；仰角時角用 `(sinα − sinφ·sinδ)/(cosφ·cosδ)` 式。
  - 方法 B：以 Julian Day Number（Fliegel–Van Flandern 式）計 doy；cosHa 與仰角時角皆用天頂角式 `(cos z − sinφ·sinδ)/(cosφ·cosδ)`，其中日出日落 z = 90.833°、仰角 α 對應 z = 90° − α。
  - 兩份對 12 個成功案例的全部輸出（日出／正午／日落／dayOffset／日長／正午仰角／四窗起訖／時長／windowStatus）逐值相同，fixtures 即採此推導值。唯一差異是診斷欄位：方法 A 在交點不存在時把 cosHα 記為 null，方法 B 保留越界的 cosHα 數值（例如雷克雅維克夏至 cosH(−4°) = −1.070）；該欄位不進 fixtures，不影響任何輸出。

- 捨入穩定性。12 個成功案例共 66 個未捨入時刻值，離 floor(x+0.5) 進位邊界最近的是赤道春分日落（未捨入小數部分距 0.5 邊界 0.0038 分，約 0.23 秒），其次為台北 2026-11-09 日落 0.0049 分（與日出日落規格所載同一值一致）；其餘皆 ≥0.025 分。正午仰角 1 位小數捨入最近的是雪梨夏至（距邊界 0.0109 個 0.1° 單位，約 0.0011°）。此量級遠大於 IEEE-754 雙精度跨引擎（JS/Python libm）的誤差（約 1e-9 分／1e-9°），故 fixtures 在任何合規實作下穩定。

- 概念筆記未固定、由作者裁決並寫入 SPEC 的事項：
  1. 黃金／藍調時刻採仰角定義（PhotoPills：黃金 −4° 至 +6°、藍調 −6° 至 −4°），不用概念筆記另一候選「日出後／日落前固定 1 小時」：fixtures 證明固定時長不成立（赤道春分黃金時刻 40 分、倫敦夏至 83 分），仰角定義是唯一能同時解釋兩者的定義；已寫入 FAQ。
  2. 太陽算法沿用日出日落規格的 NOAA fractional-year 工作表版本（γ 以當地正午取值），不用 Julian-century 的 Meeus 試算表版本：兩工具的日出／日落／正午／日長必須逐值相同，astral 的 Meeus 路線只作交叉核對，不作 fixtures 來源。
  3. 仰角為幾何仰角，不另加大氣折射修正；只有日出日落的天頂角 90.833° 含折射與太陽視半徑（依 NOAA）。此區分已寫入 SPEC 步驟 11 與精度說明。
  4. 時段不存在時以 windowStatus 三值碼判定：低界無交點 → SUN_NEVER_LOW，高界無交點 → SUN_NEVER_HIGH，兩界皆無交點時以低界為準；POLAR_DAY 四窗皆 SUN_NEVER_LOW、POLAR_NIGHT 四窗皆 SUN_NEVER_HIGH。正午仰角在極晝／極夜仍照算照回。
  5. 上午與傍晚同名時段對太陽正午對稱，durationMinutes 必然相等；SPEC 明文規定時長由未捨入值相減後一次捨入，不由已顯示時刻相減。
  6. 城市預設固定 8 個，與日出日落規格的預設表逐值相同（座標 4 位小數；雪梨預設偏移 +10:00 為標準時間，夏令由使用者改 +11:00）。
  7. 輸入欄位、文法、驗證順序、錯誤碼、捨入規則、dayOffset 語義、報告檔名與 canonical JSON 規則，全部沿用日出日落規格的釘版（步驟 1–9 逐字相同），只在步驟 10–13 加入正午仰角與仰角時段。
