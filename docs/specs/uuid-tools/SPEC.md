# UUID Generator and Inspector — full preparatory specification v0.1

Specification documentation only; no product claim, readiness event or implementation. This document is the normative contract a future production task must satisfy exactly; where it says MUST, a differing behaviour is a defect, not a variation. All UUID rules reference RFC 9562 (which obsoletes RFC 4122); where this specification makes a product choice narrower than the RFC, it says so.

## 1. Goal
Primary audience: developers, QA engineers and data engineers who need identifiers for fixtures, seeds and correlation, and who receive UUIDs from logs and need to know what they are looking at. The recurring problem: generator sites are ad-ridden and occasionally use weak randomness; and a pasted UUID carries hidden information (version, and for time-based versions a timestamp) that few tools surface honestly. Success is observable: the user generates a batch of v4 or v7 UUIDs in their chosen format and copies them at once; pastes any UUID into the inspector and learns whether it is strictly well-formed, its version and variant by name, and — for v1/v7 — the moment it encodes. Non-goals: using UUIDs as secrets (the page says plainly they are identifiers, not passwords or tokens), generating v1/v3/v5/v6/v8 (reasons stated), name-based hashing, and any storage or transmission of generated or inspected values.

Assumptions: a modern desktop browser with `crypto.getRandomValues`; no network at runtime.

## 2. Scope and functional distinction
Generator: versions 4 and 7 only. Batch size 1–1,000. Format options for a batch: case (lower default / upper), hyphens (canonical 8-4-4-4-12 default / 32-hex without). Copy-all (one per line) and download `.txt` (one per line, LF, final LF). Each Generate replaces the previous batch (with the count and version of the current batch labelled); there is no history.
Why not the other versions for generation (stated in the product help, summarised here): v1 embeds a node identifier historically derived from a MAC address (privacy) and a guessable timestamp; v3/v5 are deterministic name hashes — a different tool (a hasher) with input semantics this tool does not have; v6 is a reordered v1 kept for legacy database systems; v8 is vendor-specific by definition. The inspector still recognises all of them.
Inspector: accepts one pasted value (trimmed of surrounding whitespace); validates strictly per section 4; reports the field breakdown (time_low/time_mid/etc. generically as the five groups), version (nibble, with 1–8 named: time-based v1, DCE security v2, MD5 name v3, random v4, SHA-1 name v5, reordered time v6, Unix-time v7, custom v8; 0 reported as "0 — reserved/NIL-range", 9–15 as "reserved for future use"), variant (by the top bits of group 4: 0xxx NCS legacy, 10xx RFC 9562 standard, 110x Microsoft legacy, 111x reserved), timestamp decoding for v1 and v7 per section 4, and the special NIL (all zeros) and MAX (all F) values by name. An invalid value gets the specific failure (length, hyphen positions, non-hex character position, braces/URN forms rejected with a note that only the bare forms are accepted).
Distinction from existing work: Password Generator creates secrets with a strength model — a UUID is explicitly not that, and neither tool may borrow the other's framing. No catalog entry, reserved specification or registry task at admission time generates or inspects UUIDs; the admission check MUST be re-run against the fresh registry before production, and a collision stops the task for coordinator decision rather than a rename.

## 3. User flow and lifecycle
Layout: two panes — Generator and Inspector — usable in any order, each with its own state. Generator: version select (v4/v7), count input (default 1), case and hyphen toggles, Generate button, results list (monospace, one per line, selectable), Copy all and Download buttons (enabled only when a batch exists), and the identifiers-not-secrets note next to the results. Clicking a single UUID in the list loads it into the Inspector (a stated convenience, so generated values can be verified in place).
Inspector: one input field; analysis appears on paste/input (debounce ≤200 ms) and updates live; empty input shows the empty state, not an error. A result shows: well-formed or the specific error; canonical lowercase hyphenated normalisation of the parsed value; version and variant lines; timestamp block for v1/v7 (or "this version carries no timestamp" for others); NIL/MAX naming when applicable.
Nothing is stored; generated batches and inspected values vanish on reload or navigation and never enter the URL. Copy/download act only on explicit clicks.

## 4. Generation and inspection rules (normative)
Randomness: all random bits come from `crypto.getRandomValues` (batched: one call may fill the whole batch's byte needs; the implementation MUST NOT call `Math.random` anywhere — verified by source audit in tests). Each UUID is 16 bytes with the version nibble and variant bits then set by masking, exactly per RFC 9562 §5.4 (v4: byte 6 → `0x40 | (b & 0x0F)`, byte 8 → `0x80 | (b & 0x3F)`, all other bytes random) and §5.7 (v7: bytes 0–5 = 48-bit big-endian Unix epoch milliseconds at generation time, byte 6 → `0x70 | (b & 0x0F)`, byte 8 → `0x80 | (b & 0x3F)`, remaining bytes random). Within one batch generated in the same millisecond, v7 values share the timestamp prefix and differ only in random bits — the product makes no monotonic-order promise within a batch and the help says so (RFC 9562's counter methods are out of scope).
Formatting: canonical form is five groups 8-4-4-4-12 of hex digits joined by `-`; case option applies to the hex letters only; the no-hyphen form is the 32 hex digits. Batch text (copy/download) joins values with `\n` and ends with a final `\n`; the download filename is `uuids.txt`, MIME `text/plain;charset=utf-8`.
Count validation: the count field accepts an integer 1–1,000; 0, negative, non-integer or >1,000 input is an inline error and Generate is refused (no silent clamping).
Inspector parsing: after trimming ASCII whitespace, accept exactly (a) 36 characters with hyphens at positions 8, 13, 18, 23 and hex digits elsewhere, or (b) 32 hex digits (hyphens inserted at the canonical positions for display). Case-insensitive. Anything else fails with the first applicable specific error in this order: empty → wrong length (with the length found) → hyphen misplaced (position) → non-hex character (position and character class, never echoing more than the single character). Braces `{…}` and `urn:uuid:` prefixes are rejected by the length/hyphen rules and the help names them as unsupported wrappers.
Version/variant: version = the hex digit at position 14 of the canonical form (first digit of group 3); variant = the top bits of the digit at position 19 (first digit of group 4): 0–7 → NCS legacy (bits 0xxx), 8–B → RFC 9562 standard (10xx), C–D → Microsoft legacy (110x), E–F → reserved (111x). NIL = all digits 0 (version/variant lines replaced by the NIL explanation); MAX = all digits F (likewise). For non-NIL/MAX values whose variant is not the RFC 9562 standard, the version line carries the caveat that version semantics assume the standard variant.
Timestamp decoding: v7 — the first 12 hex digits are the 48-bit Unix millisecond timestamp; display as UTC ISO 8601 with milliseconds and as local time with the device timezone named. v1 — the 60-bit timestamp is reconstructed as time_hi (low 12 bits of group 3) ‖ time_mid (group 2) ‖ time_low (group 1), counting 100-nanosecond intervals since 1582-10-15T00:00:00Z; conversion uses exact integer arithmetic (BigInt) — the value exceeds float precision in its low digits, and the displayed time is computed by subtracting the Gregorian-to-Unix offset 122192928000000000 intervals and dividing by 10,000,000 with the sub-second remainder rendered to millisecond precision by truncation (the rule is stated, so fixtures are exact). v6 timestamps are NOT decoded in this version (the inspector says the version is recognised but its timestamp layout is not decoded here — an honest limit, since v6 reorders the v1 fields). All other versions: "no embedded timestamp".
Worked fixtures (normative): (1) Inspector on `01941f29-7c00-7abc-8123-456789abcdef` → well-formed, version 7 (Unix-time), variant RFC 9562 standard, timestamp 2025-01-01T00:00:00.000Z. (2) Inspector on `f81d4fae-7dec-11d0-a765-00a0c91e6bf6` → version 1 (time-based), variant standard, timestamp 1997-02-03T17:43:12.216Z (truncation rule applied to the .216875 remainder). (3) `00000000-0000-0000-0000-000000000000` → NIL. (4) `ffffffff-ffff-ffff-ffff-ffffffffffff` → MAX. (5) `01941f297c007abc8123456789abcdef` (32-digit form of fixture 1) → same report as (1). (6) `01941f29-7c00-7abc-8123-456789abcdeg` → invalid: non-hex character at the final position.

## 5. Implementation and safety
Architecture (future production): a pure core (byte→UUID formatting, v4/v7 construction from injected byte/clock sources, strict parser, version/variant/timestamp analysis) with zero DOM access; a controller; a thin DOM layer. Runtime dependencies: none. Randomness and the clock are injected into the core so tests are deterministic; the product adapter supplies `crypto.getRandomValues` and `Date.now`.
Privacy/security: no network, no storage; generated and inspected values render as text; the only clipboard operation is the explicit Copy all (and the user's own selection); download is a Blob of the batch text. The identifiers-not-secrets note is part of the page, in both languages.
Bilingual and accessibility: full zh-TW (default) and English UI; the results list and inspector report are labelled text regions navigable by keyboard; version/variant/timestamp lines are plain text (never colour-coded trust signals — a well-formed forged UUID and a genuine one look identical here, and the report's wording is "well-formed", never "authentic" or "valid identity"); all controls native with labels.
Performance bounds: generating 1,000 UUIDs is a single batched randomness call and string formatting — effectively instant (<100 ms); the results list renders 1,000 lines without virtualisation tricks. Toolchain: Node 24, zero npm dependencies, house layout (public/, public/en/, core modules, node:test suites, build/check/serve scripts); runs offline from file:// or any static host (CSPRNG is available in both contexts).

## 6. Independent nine-aspect product rubric
Each aspect is scored 0–100 by a reviewer who is not the author, against the same fixed candidate commit; every aspect MUST reach ≥90 with all mandatory checks complete, otherwise the verdict is revision. Unrun checks stay NOT_RUN and block acceptance.
- functionality: both languages; v4 and v7 generation in all four format combinations; batch sizes 1 and 1,000; copy/download content byte-exact; click-to-inspect round trip.
- boundaries: count 0/1/1000/1001/non-integer; inspector error order and positions; 32-digit acceptance; NIL/MAX; non-standard-variant caveat; v6 recognised-not-decoded path.
- privacy: zero network after load; no storage; values absent from URL/title; nothing copied without a click.
- security: no `Math.random` anywhere (source audit); CSPRNG only; values render as text; no external resources.
- usability: a developer generates 100 uppercase no-hyphen v4s and inspects a log UUID without instructions; the not-secrets note is noticed (comprehension spot-check in the usability evidence).
- accessibility: labelled controls and report regions, keyboard-complete flows, monospace results selectable, errors in text with positions.
- localization-seo: zh-TW and en pages complete and equivalent including help and caveats; correct lang attributes, titles, descriptions and same-language home links.
- toolchain-provenance: zero-dependency build reproduces byte-identical output from a clean checkout on Node 24; RFC 9562 cited in the shipped provenance notes.
- compatibility: current Chrome/Edge/Firefox/Safari desktop; generated v4/v7 values verified as well-formed by an independent checker (e.g. the system's own `uuidgen`/Python `uuid` module in evidence, not by the product's own parser).

## 7. Required tests and timing
Core unit tests with independently derived expectations: (a) construction: with a fixed injected byte source (bytes 0x00..0x0F repeating) v4 output is exactly `00010203-0405-4607-8809-0a0b0c0d0e0f`; with a fixed clock (1735689600000) and fixed bytes, v7 begins `01941f29-7c00-7…` with the correct masks; (b) all six section 4 inspector fixtures exactly, including the truncation fixture; (c) parser sweep: each error class with order and position, uppercase input, surrounding whitespace, brace/URN rejection; (d) version naming for nibbles 0–15 and variant naming across 0–F at position 19; (e) batch text format (joining, final LF) and count validation; (f) a distribution sanity check over 10,000 generated v4s (all unique, version/variant nibbles constant) — a smoke test, not a randomness certification, and labelled as such.
GUI/evidence tests (desktop, real browser): generate and inspect flows in both languages; copy-all pasted into a neutral editor and compared byte-for-byte; independent external validation of a generated batch (Python `uuid.UUID` parse + version assertions) recorded in evidence. Timing: full core suite under 60 seconds; no network in any test.
Explicitly NOT_RUN at specification stage: all product tests above; this document claims document completeness only.
